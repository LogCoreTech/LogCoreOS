Read the full docs set first (AGENTS/SOUL/MEMORY/TASKS/MAP/PROJECT/API/MODULE_AUTHORING/TESTING/DESIGN/COMPONENTS, the 2026-07-19 audit, README/SECURITY/CHANGELOG/RELEASING, docs/skills, docs/hooks; Daily Notes read selectively — the latest few in full, the rest grepped for MCP/API key/automation token) and wrote a plan before building.

## Same day, round three: MCP for everyone, by invitation

Owner: call them **Integrations** and **MCP**; an admin should pick which user an MCP key acts as (users can't pick or create their own), the user gets a notification to accept, and the key is handed over there and gone once copied — "this way it is safe and also allows all users to have one." Agreed, with three adjustments the owner accepted: (1) **don't put the key in the notification** — notifications are stored on disk and go out as web pushes through Google/Apple; instead the notification opens a review, and the key is *generated* only when the user accepts (password-confirmed), shown once, and Copy takes it off screen; (2) **the admin never sees an MCP key** (no quiet impersonation); (3) **pending setups expire after 7 days**. Plus: users can request access and revoke their own key, and **widening an accepted key's tools needs the user's approval again** (narrowing is immediate) so consent can't be bypassed after the fact. This explicitly supersedes MEMORY 2026-07-12 (no per-employee tokens) — recorded there and in the 2026-10-25 entry; Security Rule 22 now also says a person-bound secret goes only to that person, never into a notification/push.

**What changed**: `api_key_service` — `create_integration_key`, `invite_mcp_key` (pending, no secret), `accept_invite` (generates the secret), `decline_invite`, `update_key` (widening → `proposed_*`), `respond_to_change`, access requests (`create_request`/`list_requests`/`dismiss_request`), `revoke_key(user_id=)` for self-revoke; the file now holds `keys` + `requests`. `require_api_key`: MCP keys no longer require the user to be an admin (the user is re-fetched with their own modules/workspaces, so a key never exceeds its person). Router: user-side `/auth/me/api-keys…` endpoints; notifications use new `open_mcp_access` / `open_admin_integrations` actions (handled in `Layout.jsx`). Frontend: `ApiKeys.jsx` → `Integrations.jsx` at `/settings/admin/integrations` (requests, Integrations, MCP sections; set up = pick the person) and a new `components/settings/McpAccessSection.jsx` on Settings → Account (review/accept/decline, approve changes, revoke, request). Help section renamed and no longer admin-only.

**Verified**: 35 + 23 + 11 tests across the key/MCP/intake files; full suite green (count in TESTING.md); black/isort/eslint/build clean. **End-to-end in Chromium on a fresh local instance**: a member requested access → the admin saw the request and set it up (Tasks: read) → the member got the notification, reviewed, accepted with their password, copied the key (gone from the screen afterwards) → `curl` to `/mcp` with that key worked → the admin added tools → the member saw "more tools for…" and approved → `tools/list` showed the wider set, `add_task` worked, `list_users` refused. A notification deep link (`?mcp=<id>`) opened the review directly at phone width, and Decline worked. **Found and fixed during that run**: the member's review dialog rendered trapped inside its Settings card at phone width (backdrop-filter containing-block bug, the same one ConfirmDialog already portals around) — now portaled to `document.body`.

## Same day, round four: per-workspace MCP tools + the lead field list

Owner asked two things: how does the AI (MCP) or an integration know which fields to send, and does tool selection distinguish Business vs Personal, since data is split. Answers: **MCP already self-describes** (each tool's JSON schema goes to the client in `tools/list`); **integrations didn't** (plain REST, `/docs` off by default) — and **a key was locked to ONE workspace**, a real gap. Owner: "maximum customization."

**What changed**: MCP keys now hold **per-workspace grants** (`grants: {business|personal: {access, tool_overrides}}`, only workspaces the person has; `grants_of()` still reads the earlier single-workspace shape). `require_api_key` builds `_mcp_workspaces` (each usable granted workspace → its own disabled modules). `mcp_service` exposes every tool with an added `workspace` enum argument = exactly where that key may use it (required when >1); calls run in the chosen workspace with its module access; ambiguous/disallowed workspace → `-32602`; write audit records the workspace. Widening includes adding a workspace. Admin picker: Business/Personal tabs, each limited to modules that person has there; user review groups tools by workspace. **Lead field list**: new core `services/intake_spec.py` (`LeadIntake` with descriptions/examples + `intake_spec()`), served unauthenticated at `GET /api/v1/contacts/intake/lead` (static docs, rate-limited — added to diagnose.md's false-positive list) and shown on the admin page with a new key and under "How to send".

**Found while building it — two pre-existing agent bugs, fixed** (they'd have made per-workspace grants lie): the 9 **task agent tools ignored `workspace`** and always used Personal tasks — the in-app AI in Business has been reading/writing the wrong list since the tasks module conversion (the code even said so); and the agent's **Brain file tools crossed workspaces** — personal list/search/read walked into the nested `Business/` root (the app's own Brain browser already skipped it; the agent didn't), and `write_brain_file`/`create_brain_file` resolved against the personal root even in Business. Both fixed with regression tests (`test_tasks_agent_tools_workspace.py`, `test_agent_brain_workspace.py`); the MCP test that writes in Business and lists Personal is what caught it.

**Verified**: full backend suite green (count in TESTING.md); black/isort/eslint/build clean. **End-to-end in Chromium on a fresh local instance**: created an integration (field list + example shown with the key, and under "How to send"); set up MCP for a member with both workspaces — Business: Tasks read + write, Contacts read; Personal: Tasks read — via the tabs; the member's review grouped tools by workspace; accepted + copied. `curl` to `/mcp`: `list_tasks` advertised `["business","personal"]` (required), `add_task` only `["business"]`; `add_task` without a workspace landed in Business, `add_task` in Personal was refused, `list_tasks` without a workspace was refused as ambiguous, and Business/Personal listings returned their own tasks only. `GET /contacts/intake/lead` returned the field list without a key.
