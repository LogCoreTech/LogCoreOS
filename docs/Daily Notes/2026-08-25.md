only copied `icon`/`label`/`defaultLayout`/`Component` across, silently dropping `shape`/`chromeless`/

immediately since I was converting exactly that block). Fixed by spreading every field the manifest
declares instead of hand-picking a fixed list, which also makes this correct for any future field

every scope (personal/business) has always gone through the same single `require_module("automations")`
check. Keeping a phantom toggle around after the real module converts would be more misleading, not
less, so it's gone rather than carried forward. Also found and fixed genuinely stale AGENTS.md/API.md

## Household + Team converted together — the first two-module increment, surfacing two real gaps in the module system itself

routers, the open `pool_tasks` block-ownership question, the AI-tool situation for both pools, every
frontend consumer, and existing test coverage) before writing code. Confirmed directly in code before

**Gap #1 — a shared dashboard block couldn't be gated once both pools became real modules.** The old

also closed a second, independent, previously-undocumented bug: the old resolver never checked that
`ctx.workspace` actually matched the pool it was about to read, so a stale/mixed-workspace dashboard
could have shown the wrong pool's data with zero gate — splitting into two statically-scoped
resolvers closes this for free. A migration (household's own `m023`) rewrites `pool_tasks` →
`household_tasks`/`team_tasks` **per-dashboard, based on that dashboard's own workspace** — not a
flat 1:1 rename like `home_assistant`'s `m018`, since the same old type string meant different things
depending on where it was found. Also found and fixed, the same way `m010`'s `home_favourites`
hardcode was caught during Home Assistant's own rename: core migration `m010_seed_home_dashboards`
had its own hardcoded `"pool_tasks"` literal for new business-workspace users — already-run on every
existing instance, zero risk, but would have seeded a broken block for any brand-new install going
forward if left unfixed.

**Gap #2 — the module system had no way to mark a tool admin-only.** Household owns 5 shared-task AI
tools (4 admin-only + `complete_shared_task`, member-accessible) — the first tools any module has
owned that need hiding from non-admins entirely, not just blocking at execution. `_get_tools()`'s
existing module-dispatch path offered every `owned_agent_tools` schema to any module-enabled user
regardless of role — fine for every prior module (none owned an admin-only tool), wrong here: moving
these 4 unchanged would have OFFERED their schemas to non-admin household members (the executor's own
admin check would still block execution, so no real data-access hole, but a real behavior regression
from today's `_ADMIN_TOOLS`-only visibility). Fixed generically, not per-module: `ModuleManifest`
gained `admin_agent_tools: list[str]`, `module_registry.admin_agent_tool_names()` unions it across
active modules — mirrors `read_only_agent_tools`/`read_only_agent_tool_names()`'s exact shape from
journal's own conversion.

**The `brain` test fixture had a second, related gap.** Tasks' own fix (auto-install every LOCKED
module) didn't cover Household/Team, since they're optional. Two more pre-existing tests broke for a
subtler reason: `test_new_tools_are_write_gated_by_default` and
`test_get_effective_disabled_workspace_keyed_dict` both used `"team"`/`"add_shared_task"` as arbitrary
example strings, written before either was a real discovered module — once `"team"` became real,
`get_effective_disabled()`'s not-installed union started marking it disabled in every workspace,
breaking an assertion that was never actually about Team's own semantics. Fixed both at the root: the
first now explicitly installs household before asserting on `add_shared_task`'s gating (a
meaningful, real thing to test now); the second swapped its placeholder from `"team"` to `"finance"`
— a core, never-`module_packages/` id that can't collide with this class of bug again regardless of
what converts next.

**Zero router-level test coverage existed for `routers/shared.py`/`routers/team.py` before this** —
confirmed by grep across the whole suite, closed with real CRUD/attribution/isolation tests in each
module's own `tests/`, calling endpoint functions directly with a pre-resolved user dict (this
suite's established convention). Deliberately didn't attempt to test the `require_module`/
`require_pool_edit` dependency chain itself — untestable without a `TestClient`, which has zero
precedent anywhere in this suite; a systemic pre-existing gap, not unique to this conversion.

**Goals-style precedent held without inventing anything new.** `admin/Household.jsx`/`admin/Team.jsx`
call zero household/team-owned endpoints (only the generic `priorities` client + shared
