# 2026-08-25

## Automations converted into `module_packages/automations/` (n8n Automation)

Owner: "i think it will be okay to move forward now to the next things. maybe do automations next and
convert the module name to N8N Automation probably fine to leave backend names alone and just change
forward facing names to that. do this one the same as home assistant." Taken out of the originally
planned rollout order (Calendar was next in `docs/TASKS.md`) at the owner's explicit request — updated
the tracked order to reflect it.

Full scope discovery first, same rigor as journal/Home Assistant (delegated to an Explore agent given
the size — this is the largest conversion yet, 785-line page + 3 backend service files + the first
module managing its own Docker container). Two real design decisions this conversion needed that
neither prior one did:

**Two services stay in core, one moves** — `n8n_service.py` (bundled n8n lifecycle, REST client) and
`automations_config.py` (the automation API token) both have real consumers outside the module:
`scheduler.py`'s boot/cron jobs and `infisical_loader.py`'s secrets pipeline depend on `n8n_service.py`
directly; `routers/contacts.py` and `routers/assets.py` depend on `automations_config.py` directly for
their own unrelated automation-token endpoints. Same reasoning as `ha_service.py` staying core, just
with three dependents instead of one. `automation_inbox_service.py` (renamed `inbox_service.py`) DID
move — its only real consumer is the block being converted.

**Two block types, not one — the manifest.js schema didn't support that.** `workflow_status` and
`inbox_summary` are both automations' own blocks, but `manifest.js` only ever had a singular `block:`
key (journal, Home Assistant each own exactly one). Rather than hack a one-off special case, generalized
`blocks:` to always be an array — updated journal's and Home Assistant's manifest.js files too (wrapping
their single block in a one-item array) so every converted module shares one shape, and rewrote
`blockRegistry.js`'s merge loop to iterate it. Caught a real bug in my own first draft of that loop: it
only copied `icon`/`label`/`defaultLayout`/`Component` across, silently dropping `shape`/`chromeless`/
`recordKind` — fields some block types need (`inbox_summary` needs `shape: 'list'`, discovered
immediately since I was converting exactly that block). Fixed by spreading every field the manifest
declares instead of hand-picking a fixed list, which also makes this correct for any future field
without needing another manual update.

**Removed `automations_business` rather than converting it.** A role-editor checkbox ("Business
Automations") that existed in `_CORE_MODULE_IDS`/`_BUSINESS_MEMBER`/`constants.js` — confirmed via
exhaustive grep (Explore agent) that it was **never actually checked anywhere in the backend router**;
every scope (personal/business) has always gone through the same single `require_module("automations")`
check. Keeping a phantom toggle around after the real module converts would be more misleading, not
less, so it's gone rather than carried forward. Also found and fixed genuinely stale AGENTS.md/API.md
documentation that had claimed this toggle hid a business tab client-side — it never did; `Automations.jsx`
never referenced it at all.

### A real bug found by accident: a live dev server has been running this whole session

Mid-conversion, `git status` showed an unexpected change: `brain/USERS/_template/Home/.gitkeep` deleted,
a new `brain/USERS/_template/HomeAssistant/` appeared. Investigated rather than assumed — `ps aux`
confirmed a real `uvicorn main:app` process has been running against this checkout's actual `brain/`
folder since 04:45 today (started earlier this session via the `run` skill, auto-reloading on every
file save since). That means **m016/m017 (Home Assistant's migrations) have genuinely executed against
real local data**, not just pytest fixtures, revealing a real bug in m017's own folder-rename step: its
`USERS/*.iterdir()` loop iterates *every* directory under `USERS/`, including `_template/` (the setup
scaffold, not a real user) — `_template` is a perfectly ordinary directory, so nothing stopped the loop
from "migrating" it too. Fixed by excluding `_`-prefixed names from that loop (matching journal's own
`on_install()` convention, which already excludes them for exactly this reason). Cleaned up the
already-incorrectly-renamed template folder by removing it entirely (`git rm`) — matching journal's own
precedent of not needing a template scaffold at all, since Home Assistant's favourites folder, like
journal's, is lazily created on first save, not pre-seeded.

Given this dev server has been quietly live-testing changes throughout the session without my
knowledge, everything committed today should be treated as *also* real-instance-tested in a small,
local, gitignored way — though not a substitute for the owner's own click-through, which is still the
only thing that's caught actual UI bugs so far.
