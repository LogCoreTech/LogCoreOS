# 2026-09-02

## Admin → AI Settings overhauled from free-text fields to pickers

Owner: "right now the ai section has fields to type to enter the model type and provider and all
that. we need this to be a picker for everything except the api key... lets do a overhaul on that
whole section. enter plan mode and interview me on all of it including design, security, features,
supported types, etc.." Ran a full plan-mode interview (12 `AskUserQuestion` rounds, 2 live-research
rounds) before touching any code, given how much the shape of this depended on the owner's own
preferences (provider breadth, static vs. live model lists, whether fetching should be per-provider
or universal, whether to build a compatibility ranking).

**Provider catalog.** New `services/ai_provider_catalog.py` — pure data, ~25 providers (Anthropic,
OpenAI, Azure OpenAI, Groq, Gemini, Mistral, DeepSeek, xAI, Cerebras, Together, Fireworks, OpenRouter,
local runners — Ollama, LM Studio, vLLM, llama.cpp, text-generation-webui, KoboldCpp, Jan.ai — plus a
`custom` escape hatch). Breadth escalated through the interview from the old 5 quick-guide presets to
"add as many as possible... may need you to run a websearch for them" — two rounds of live `WebSearch`
grounded the final base URLs rather than trusting possibly-stale training data.

**A real bug found and fixed as a side effect**: the old Groq quick-setup preset saved an empty base
URL, silently sending requests to real OpenAI's endpoint with a Groq-shaped key. Fixed by making the
server authoritative for `ai_base_url` on every known provider — the catalog's own URL is stored
regardless of what the client sends, closing this class of misconfiguration everywhere, not just Groq.

**The compatibility-ranking idea died on direct SDK inspection.** Mid-interview, a tiered
🟢/🟡/🔴/⚪ "compatibility score" feature was designed and even had a rubric approved — then killed
after actually checking the installed SDKs in this repo's own `.venv`: neither `anthropic`'s
`ModelCapabilities` nor `openai`'s `Model` type exposes a tool-calling field anywhere. Owner's call once
shown the gap: "lets just drop that ranking idea and just show the specs of the models." `POST
.../ai-settings/models` now returns only what a provider actually reports (context/output token
limits), with a warning string when a provider returns models but no capability data at all.

**Model fetching ended up universal, not local-only** — an idea the owner reconsidered mid-interview
("it may be best to have all providers we put in here to be able to fetch with that toggle not just
local runners... so we dont have to maintain any files"). New instance-level `ai_allow_model_fetch`
toggle (off by default) gates a live "Load Models" fetch for any provider. Owner also floated wiring
this into `docker/update.sh`'s WiFi-connected auto-update cycle; pushed back since that script has no
AI keys/concerns today and folding fetch in would make it automatic instead of an explicit click —
owner agreed ("youre right about the fetching issue. lets do your way.") and it stays a pure in-app
button, never touched by the updater.

**Security: a cross-provider key-leak guard**, new this pass. The write-only API key pattern (GET
never returns it, blank on save = unchanged) was preserved as-is — but live-fetch created a new leak
shape: an admin testing a new `custom` URL with the key field left blank (masked by design) could have
had their real, persisted key for a *different* provider silently sent to whatever host they just
typed. `_resolve_fetch_key()` only reuses the persisted key when the request's provider (and, for
`custom`, base_url) matches what's currently saved — otherwise the fetch goes out keyless and the
target's own 401 surfaces normally. Covered by a dedicated regression test. The fetch endpoint also got
its own stricter rate-limit bucket (10/60s) — a real outbound call every time, and a blunt
SSRF-probing deterrent for the free-text URL case.

**Azure OpenAI got its own shape**, not another preset row — Resource Endpoint / Deployment Name / API
Version fields, no generic model picker (Azure's model-list endpoint returns base models, not
deployments, so "Load Models" 400s for it deliberately). New `_azure_openai()`/`_azure_openai_agent()`
in `services/ai_provider.py`, client construction confirmed against the real SDK signature
(`inspect.signature(openai.AzureOpenAI.__init__)`) rather than assumed. Dispatch reworked from literal
`ai_provider` string matching to a `kind`-based branch, which needed its own stricter `_dispatch_kind()`
helper so a genuinely bogus config value still raises loudly at call time instead of being silently
absorbed by the forgiving `get_provider()` resolver used for settings display.

**Two design/implementation bugs caught before shipping, not during use.** First: the plan called for
the frontend to reconcile an old free-text `ai_base_url` against the catalog to pre-select the right
provider on load, but the catalog endpoint was first built to hide `default_base_url` from the wire —
a direct contradiction, since the frontend can't match URLs it's never given. Resolved by exposing
`default_base_url` after all (these are public, well-known API endpoints, not secrets — an admin can
already point `custom` at anything). Second: `ModelPicker.jsx` kept its own fetched-model-list state
with nothing resetting it on a provider switch, so a stale list from provider A would linger under
provider B's name until fetched again — fixed with `key={form.ai_provider}` so React remounts it
cleanly on every switch.

**A repeat of a known bug class, fixed properly this time.** `_AI_SETTINGS_PATH` in `routers/auth.py`
was a module-level constant frozen at import time — the exact shape of `routers/setup.py`'s
`TEMPLATE_PATH`, documented yesterday as a known, left-unfixed gap. New tests hit it immediately
(`PermissionError: [Errno 13] Permission denied: '/data'`, then a silent wrong-file read). Converted to
a real function, `ai_settings_path()`, called fresh on every use. `TEMPLATE_PATH` itself is still
unfixed — a gap for whenever that file gets direct test coverage.

New `routers/ai_settings.py`, extracted from `auth.py` and mounted at the same `/api/v1/auth` prefix
(matching the `infisical.py`/`features.py` precedent) — zero frontend URL changes. 29 new/extended
backend tests (`test_ai_provider_catalog.py`, `test_ai_settings_router.py`,
`test_ai_provider.py`); full backend suite 1291 passed. `black`/`isort`/`eslint --max-warnings
0`/`vite build` all clean. Docs updated: `docker/.env.example` and `docs/PROJECT.md`'s stale "only
Anthropic, Phase 6" claims, `docs/API.md`'s widened/new endpoint documentation, `CHANGELOG.md`
Unreleased entry, `docs/TASKS.md`'s Ollama item checked off. Not yet committed or pushed.
