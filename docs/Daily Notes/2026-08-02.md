# 2026-08-02

## Fixed: admins couldn't manage Notes shared into the household/team pool

Owner reported that notes shared to the household/team pool couldn't be edited or deleted, and
asked whether other modules had the same "isolated data" problem.

Audited all 4 sharing-capable modules' frontends. Root cause was isolated to `Notes.jsx`: its
context menu computed `own = !node._owner` and hid Rename/Move/Share/Delete for ANY non-owned item,
offering "Leave" instead — which doesn't make sense for a pool item (pool items are workspace-visible
collectively, not a personal accept/decline share). The backend was already correct
(`notes_service.resolve_access()`'s pool branch returns `"edit"` for `is_admin`); this was a
frontend-only bug. Fixed with an explicit `isPool` check (`_owner === 'household'/'team'`), gating
management on `own || (isPool && _access === 'edit')`, matching the pattern already used correctly
by `AssetModal.jsx`/`AssetView.jsx` (Assets), `Finance.jsx`/`BookSettings.jsx` (Finance), and
`Contacts.jsx` — none of those three had the bug.

Owner also asked for pool items to be archive-only, with hard delete requiring 2+ admins to agree.
Interviewed on scope (which modules, what happens on a single-admin instance, how the approval
mechanic would work) — the owner dropped the 2-admin-approval idea entirely mid-interview once the
edge cases were on the table. Pool hard-delete behavior is unchanged everywhere as a result. The
owner did keep wanting a minimal archive flag for Notes, though, as a standalone parity feature
(Assets/Finance/Contacts already support archiving; Notes was the one gap) — built as its own
thing, explicitly not tied to any delete restriction.

**Notes archive, as shipped**: `Notes/_archive.json` sidecar (per-node, no cascade — archiving a
folder does not archive its contents, mirroring Assets' same rule), `set_archived()`/
`load_archived()` in `notes_service.py`, `include_archived` param on `list_notes()`/
`list_visible_notes()` (default `False`, always annotates every item with `archived: bool`
regardless), new `POST /notes/archive` endpoint (edit-level gate, same as delete). Also extended
`transfer_ownership()` (built yesterday for the user-deletion feature) to carry archived-path
entries across a move, same as it already does for `_shares.json` entries. Frontend: "Show
archived" toggle in the sidebar (mirrors Assets' existing toggle), dimmed/line-through styling on
archived items, Archive/Unarchive action in the ··· menu.

**Verified**: 6 new backend tests (archive visibility toggle, unarchive, delete-cleanup for both
notes and folders, transfer carry-over), full suite 516 green (up from 510), black clean. Frontend
build + eslint clean (0 errors; only pre-existing prop-types-style warnings, same convention as
the rest of the codebase).

## Same-day correction: Notes archive should cascade like sharing, not like Assets

Shipped archiving above as per-node (mirroring Assets' explicit "archive doesn't cascade" rule,
since that was the only existing precedent in the codebase). Owner clarified same-day: they wanted
it to cascade the same way *sharing* does instead — archiving a folder should archive everything
inside it. Fixed: `_is_archived_path()` now walks up ancestors the same way `_entry_for_path`
already does for share resolution, so a note under an archived folder shows as archived even
though only the folder's own path lives in the `_archive.json` sidecar. Consequence (intentional,
matches how sharing already behaves): a child can't be individually un-archived while its parent
folder stays archived — you have to unarchive the parent. 2 new cascade tests, full suite still
516 passing (the pre-existing `test_ai_usage_service.py` UTC-day-boundary flake reappeared during
this run, confirmed unrelated — see 2026-07-30 notes on that test).
