# 2026-08-29

## Goals Round 2 — 11 owner-reported issues fixed in the same still-uncommitted changeset as the 2026-08-28 module build

The owner tried the Goals module built the previous day and came back with an 11-item list from
actually using it — bugs, real UX complaints, and two feature requests. This is that list, worked
through in one sitting, still inside the same uncommitted changeset as the original build (no commit
happened between the two rounds). Grouped below by kind rather than in report order, since several
items turned out to share a root cause once investigated.

### Bugs fixed

**Nested-modal clipping — a real, pre-existing latent bug, not something this build introduced.**
`.modal-card` (in `index.css`) applies `.card`, which uses `backdrop-blur-sm` — CSS `backdrop-filter`
on an ancestor element creates a new containing block for any `position: fixed` descendant, so a
modal that's nested INSIDE another modal's own DOM sizes and clips against the OUTER modal's box
instead of the real browser viewport. Two real instances existed: `GoalModal.jsx`'s own "+
Subgoal"/"+ Task" flows (GoalModal reopening itself, or opening TaskModal, from inside an already-open
GoalModal), and `AssetModal.jsx`'s pre-existing nested `<TaskModal>` (its own "+ Task" quick-create).
Fixed via `createPortal(..., document.body)` — not a new pattern, `components/assetDisplay.jsx`'s
photo viewer already uses the exact same trick for the exact same reason, confirmed by reading it
before writing the fix rather than reinventing one. `GoalModal.jsx` now wraps its own top-level
return in a small local `Portal` helper component, so nesting is self-solving at every depth — the
recursive "+Subgoal" GoalModal-inside-GoalModal case portals itself automatically without any special
casing — and separately portals its delete-confirmation popup. `AssetModal.jsx`'s nested `<TaskModal>`
got the identical `createPortal` treatment applied directly at its own call site. `AssetModal.jsx` has
at least 2 OTHER instances of the identical pattern (`archivePrompt`, `SaveAsTemplateModal`) —
deliberately left unfixed this round, since only the TaskModal nesting matched what was actually
reported; filed as its own small `docs/TASKS.md` Product Backlog item rather than silently expanding
scope.

**Pool task-linking now targets the correct store**, closing Round 1's own explicitly-flagged known
gap. `GoalModal`'s "+ Task"/"Link existing task" actions previously always went through the personal
`tasksApi` regardless of whether the goal being viewed was a household/team pool goal. Fixed with a
new `poolTaskApi(workspace)` helper in `GoalModal.jsx` that dynamically imports
`module_packages/household/frontend/api.js`'s `shared` client (personal workspace) or
`module_packages/team/frontend/api.js`'s `team` client (business workspace) depending on which pool
the goal belongs to. `TaskModal`'s existing `saveApi` prop and a new `listFn` prop added to
`TaskPicker.jsx` (defaults to the personal `tasksApi.list`, override-able) both thread this through.
Two small local wrapper components inside `GoalModal.jsx`, `TaskLinkPicker` and
`PoolAwareTaskCreateModal`, exist purely to resolve the async pool-client import before rendering
`TaskPicker`/`TaskModal` — both of those need a real function reference up front, not a promise, so a
tiny bit of `useState`/`useEffect` plumbing sits in between the dynamic `import()` and the actual
render.

**Appointments were already fully linkable to goals — confirmed, no code change needed.** One of the
11 items turned out not to be a bug at all: `goal_id` was added to Task unconditionally in Round 1
with no restriction by task type, and `TaskPicker.jsx` never filtered by type either, so an
appointment-type task could always be linked to a goal exactly like any other task. Verified by
direct read of both files before reporting back, rather than assuming the report was accurate.

**Weight metric gap.** The root cause: `height_cm`/`weight_kg` are built-in, always-private fields
directly on the Contact record itself (`services/contacts_service.py`'s `_PRIVATE_SHORT_FIELDS`),
invisible to Round 1's `contacts:number_field` provider, which only ever reads `contact["custom"]`.
Fixed with a new, separate metric provider, `contacts:weight` (`module_packages/contacts/manifest.py`'s
`_resolve_weight`), always resolving the caller's own self-contact — no `contact_id` override, since
the field is private by design and only ever readable by its own owner. Owner explicitly asked for
weight only, not height, so no `contacts:height` provider was built alongside it.

**A real math bug caught and fixed BEFORE it shipped, not after.** While building the weight provider,
realized every metric provider built in Round 1 (Finance's `budget_pct` aside, which is a utilization
percentage, not a goal-completion one) silently assumed "higher current value = more progress toward
target." That assumption is backwards for a weight-LOSS goal: you start ABOVE target and progress
means the current value going DOWN, so the original `current/target*100` formula would show 120%
complete on day one and get WORSE the more weight you actually lost. Fixed generically rather than as
a weight-only special case: a new shared `module_registry.directional_pct(current, target,
direction="increase"|"decrease", start_value=None)` function, living in `module_registry.py` rather
than inside `module_packages/goals/` specifically so a module registering its own metric provider —
like Contacts — doesn't have to import from a sibling module's package just for this formula.
"increase" (the default) preserves the original behavior exactly; "decrease" computes progress as
`(start - current) / (start - target)`, which needs an explicit starting point (`start_value`) since a
weight reading, unlike "pages read," has no natural zero baseline to measure from. Both Goals' own
"manual" provider and Contacts' `number_field`/`weight` providers now expose a `direction` + a
`start_value` config field (a `select` + an optional `number`) alongside their existing `target_value`,
and `goals_service.py`'s `_resolve_metric` manual branch was updated to call this shared helper instead
of its own inline `current*100/target`. Weight's own config schema gets a distinct
`_WEIGHT_DIRECTION_FIELD` rather than reusing the shared `_DIRECTION_FIELD` constant — the shared one
lists "increase" first, and the frontend `MetricPicker.jsx` pre-selects `options[0]` whenever a config
has no explicit value yet, which would have shown "Increase" pre-selected in the UI while the backend
was already silently computing "decrease" behind the scenes the moment a `target_value` was set — a
real visual/effective mismatch caught by re-reading the picker's own selection logic before shipping,
not discovered by a user afterward.

### UX rework (real design decisions from the interview, not just bug fixes)

**Tab restructure: ownership replaces depth as the tab axis.** Round 1's "ME" tab (root-level goals
only) is GONE — "ME" now shows all of the caller's own personal goals, at any depth, which is what
the old flat "Goals" tab used to show. A second tab, labeled "Household" or "Team" depending on the
active workspace (not a generic "Pool"), shows that pool's own goals — previously pool goals were
invisibly merged into the same single list, identifiable only by an `_owner` field nobody was actually
looking at, which is exactly what the owner reported as "no idea where the pool goals are." The pool
tab is hidden ENTIRELY via `useAuth()`'s `activeModuleIds`/`user.disabledModules` — the same check
`App.jsx`'s own `ModuleRoute` already uses — when Household/Team isn't installed/enabled for the
viewer; a member without the `pool_edit` write grant still sees the tab, read-only, the same as pool
tasks/notes already work today — it only disappears entirely when the underlying pool module itself
is off. This was an explicit, deliberate choice confirmed during the interview, not a default assumed
here, and it matches every other pool-visible feature's existing behavior in the app.

**Category-grouping headers removed** from the Goals list — each goal already shows its own category
badge on the card itself, so the separate grouping headers were redundant, per the owner's own
observation while looking at the page. The descriptive text that used to sit under the tab switcher
was removed at the same time, for the same reason — it no longer explained anything the UI itself
didn't already make obvious.

**Linking an existing goal as a subgoal** — previously only "+ Subgoal" (create a brand new one)
existed as an option. New `GoalPicker.jsx` (123 lines) mirrors `TaskPicker.jsx`'s own
search-autocomplete shape exactly. Its own `subtreeIds()` helper is a client-side port of the
backend's `collect_subtree_ids` cycle-guard, used to exclude a goal and its own descendants from the
picker's results — re-parenting a goal under its own descendant is guaranteed to 400 server-side
already, so there's no point offering an option that can't work. The picker explicitly ALLOWS
re-parenting any goal, including one that already has a different parent — it shows a match's current
parent title inline ("— currently under 'X'") specifically so moving an already-nested goal isn't a
surprise to whoever's doing it. No backend changes were needed at all for this —
`goals_service.update_goal`'s existing cycle guard from Round 1 already covers the re-parenting case
correctly; this was purely a missing frontend affordance, confirmed by re-reading the router/service
before assuming a backend change was required.

### New features

**Recurring-task completion log + automatic rate-based rollup contribution.** Every recurring Task
now accumulates a capped, dated completion log (`completion_log: [{"date": "YYYY-MM-DD"}]`, capped at
90 entries via `_COMPLETION_LOG_CAP` in `services/task_service.py`) — appended in `update_task()`'s
existing recurring-completion branch, the same place `streak_count`/`last_completed_date` already get
updated, with symmetric removal when a completion is undone on the same day it was logged.
`goals_service.compute_progress()`'s rollup loop (`module_packages/goals/backend/service.py`) now
checks whether a linked task is `type == "recurring"`, and if so calls a new
`_recurring_completion_rate(task)` helper — a count of `completion_log` entries falling in the
trailing 30 days, divided by 30, clamped 0-100 (`_COMPLETION_RATE_WINDOW_DAYS = 30`, a fixed default
rather than a per-goal configuration option, matching the owner's explicit "automatic, no extra
configuration step" ask) — instead of the old binary 100/0 done-check. A non-recurring linked task is
completely unaffected by any of this. Verified live via a real HTTP smoke test rather than only unit
tests: a recurring task seeded with 10 completions spread across a 30-day window correctly rolled up
to its parent goal's own displayed 33% (10/30).

**Shared tag vocabulary for Goals + Tasks.** New core `services/tags_service.py` (44 lines) —
deliberately core, not inside `module_packages/goals/`, since both Goals' own package and core
`task_service.py` need it, the same "a real external consumer keeps a service in core" test this whole
project has used consistently throughout every module conversion this session. `Tags/tags.json` per
store (personal or pool) is a real, persisted, GROWING vocabulary — not live-scanned off existing
records — since the owner specifically wanted the tag search/autocomplete to be driven by a real
accumulating list, so a tag stays suggestible even after the last record carrying it gets deleted.
`register_tags()` is a case-insensitive-dedup, case-preserving union-add (`_VOCAB_CAP = 500`, a
generous ceiling rather than a realistic limit), wired into both `task_service.add_task`/`update_task`
and `goals_service.create_goal`/`update_goal` whenever a tag not already in the vocabulary shows up.
New core `routers/tags.py` (30 lines, `GET /tags?pool=`) mirrors `routers/priorities.py`'s own
login-required-no-module-gate shape exactly, plus a new `tags` export on core `lib/api.js`.
`TaskCreateBase`/`TaskUpdateBase` (`routers/_task_models.py`) and Goals' own `GoalCreate`/`GoalUpdate`
models all gained `tags: list[str] | None`. Frontend reuses the EXISTING `components/TagInput.jsx`
component completely as-is — no changes needed there at all — its `suggestions`-provided, non-strict
mode was already exactly "shows existing tags, typing filters to the closest match, Enter/comma adds
a new one if nothing matches," which is precisely what the owner asked for, confirmed by reading the
component before assuming it would need work. Used in both `GoalModal.jsx`'s edit form and
`components/TaskModal.jsx`'s form (which gained a Tags field entirely — it didn't have one before).
Tag PILL display (not comma-separated text) plus click-to-filter was added to `GoalModal.jsx`'s view
mode, `Goals.jsx`'s `GoalCard`, and `module_packages/tasks/frontend/Tasks.jsx`'s `TaskCard` — clicking

Deliberately scoped to Goals+Tasks only this round: the owner's own broader vision — a header-level

### Bug fixed: TaskPicker.jsx's hidden result cap

**Root cause, found only by live reproduction — static reading of `TaskPicker.jsx`,
`GoalModal.jsx`, and every backend file touching task-goal linking found nothing wrong.** The
search-autocomplete dropdown filtered matches by substring, in raw array order (task creation
order), then applied a hardcoded `.slice(0, 8)`. A user with many pre-existing one-off tasks
sharing a common word with a recurring task's title would never see the recurring task in the
dropdown — even searching its exact title — because it got crowded past position 8 by older
matches. Reproduced in a fully isolated, disposable local test instance (port 8001, a scratch
brain directory seeded only with generic template files, obviously-fake local-only secrets),
driving a real headless Chromium browser (`playwright-core`) through the actual UI: registered a
test account, installed Goals/Household directly via a Python one-liner against the test brain
(a module install needs a process restart to take effect, since `register_routers()` only runs
once at boot), then seeded 12 non-recurring "Reading log N" tasks followed by one recurring
"Reading" task created LAST — confirmed the recurring task was completely absent from the
dropdown before the fix, and present (top-ranked) after. Nothing on the owner's real running
instance (port 8000, real data) was touched.

**Fix, both in `TaskPicker.jsx`:** a new module-level `_matchRank(title, q)` helper (~line 4-9)
ranks an exact title match `0`, a starts-with match `1`, any other substring match `2`; the
`matches` computation (~line 56-70) sorts by that rank before display. The `.slice(0, 8)` cap was
removed entirely, since the dropdown already had `max-h-56 overflow-y-auto` (a real scroll
container) from the original build — the cap had simply been defeating that scroll container's
purpose the whole time, an arbitrary leftover from when the component was first written, not an
intentional decision. The owner's own follow-up question — why cap at 8 instead of scrolling
through all of them? — is what escalated the fix from "add ranking, still cap at 8" to "remove the
cap for the filtered case." A first pass left the cap in place for the unfiltered browse view
(empty search text) reasoning it was an unranked "first N" list — same day, the owner pushed back
("i want the empty query field... to still scroll through all tasks. its a convenience factor for
users"), so that cap was dropped too; `matches` is now simply `q ? (filtered+ranked) : all`.

Verified live: searching "Reading" against 26 accumulated matching tasks (2 recurring + 24 old
one-offs, across test runs) rendered all 26 in the scrollable dropdown, both recurring
exact-matches sorted to the top. No backend change — purely `TaskPicker.jsx`, one file.

### New feature: optional recurring-task rollup contribution (`counts_toward_goal`)

**A linked recurring task's contribution to its parent goal's rollup percentage is now optional
per link, not automatic** — directly satisfies "only show the completion metric and not effect
rate." Owner chose via `AskUserQuestion`: newly-linked recurring tasks default to opt-in OFF (not
counting) until explicitly toggled on — not the reverse (opt-out/default-on) — so a recurring task
can be linked purely for visibility/tracking (its own rate still displays) without silently moving
the goal's overall percentage.

New Task field `counts_toward_goal: bool | None` on `TaskCreateBase`/`TaskUpdateBase`
(`routers/_task_models.py`, lines 42 and 73). Default logic lives in exactly two places in
`services/task_service.py`, not duplicated per entry point:

- `add_task()` (lines 47-54) — sets `False` when a task is created already-linked (recurring type
  + `goal_id` set at creation, e.g. the "+ Task" flow inside a goal) and the caller didn't
  explicitly pass the field.
- `update_task()` (lines 82-90) — sets `False` when an update newly sets `goal_id` (a value
  different from the task's current one) on a recurring task, and that same update payload didn't
  explicitly include the field. This single choke point covers every entry path uniformly: the
  frontend's "Link existing task" flow, the "+ Task inside a goal" creation flow, AND the AI's
  `link_task_to_goal` tool (`module_packages/goals/backend/agent_tools.py`), which already calls
  `task_service.update_task(..., {"goal_id": ...})` with no other fields and picks up the same
  default automatically — zero `agent_tools.py` changes needed.

**Backward compatibility**, matching this project's own stated care about migration correctness:
a recurring task linked BEFORE this feature shipped has no `counts_toward_goal` key in its stored
JSON at all. `goals_service.compute_progress()`'s rollup loop (`module_packages/goals/backend/service.py`,
line 345) treats a missing key as `True` via `task.get("counts_toward_goal", True)`, so existing
goals' already-computed progress percentages don't silently change the moment this ships — the
opt-in-off-by-default behavior only applies to newly linked recurring tasks going forward,
confirmed by `test_recurring_task_default_missing_field_still_counts`, which strips the field back
off a task record to simulate pre-feature legacy data.

`_recurring_completion_rate` was renamed to `recurring_completion_rate` (dropped the leading
underscore, `service.py` line 305) since `router.py`'s `GET /goals/{id}` handler (line 212) now
calls it too, not just `compute_progress()` internally — each recurring linked task in that
endpoint's `linked_tasks` response gets an attached `recurring_rate` field (rounded 0-100), so the
frontend can show a recurring task's own 30-day rate even when it's not counting toward the goal's
percentage. `compute_progress()`'s rollup loop (lines 341-348) now only appends a recurring linked
task's rate to `children_pct` when `task.get("counts_toward_goal", True)` is true — skipped
entirely when explicitly `False`; if it was the only linked item, the goal's progress source falls
back through the existing chain (metric wins, else weighted rollup of children, else manual
pending/done toggle) with one fewer contributing child, potentially zero.

**Frontend (`GoalModal.jsx`):** new `toggleTaskCounts(taskId, current)` (line 163, mirrors the
existing `unlinkTask`'s pool-aware API resolution pattern) — calls
`api.update(taskId, { counts_toward_goal: !current })`. The linked-tasks list (previously a
single-line `<li>` per task) was restructured: each recurring task now shows
`(recurring — N% / 30d)` next to its title (line 335, using the new `recurring_rate` field), plus
a checkbox row below it, "Counts toward this goal's progress" (lines 339-348) —
`checked={t.counts_toward_goal !== false}`, so a MISSING field renders as checked/on, matching the
backend's own `True` fallback. **A real bug caught and fixed before shipping, not after**: an
earlier draft used `t.counts_toward_goal ?? false`, which would have shown every pre-existing
linked recurring task as unchecked in the UI even though it still counted server-side — a visual
lie. Non-recurring linked tasks are unaffected — the checkbox and rate badge only render
`{t.type === 'recurring' && ...}`.
