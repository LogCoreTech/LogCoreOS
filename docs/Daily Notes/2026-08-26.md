## Chat converted into `module_packages/chat/` — the second LOCKED module, and the first where the module's own orchestration engine needed zero changes

Owner, after confirming Household+Team looked good: "good. then that coversion looks good. lets move
on" — proceeded straight into Chat per the tracked rollout order (the second LOCKED module, after
Tasks, with no cross-module import entanglement forcing an earlier slot — a good next proof that
"locked" doesn't require dependency-driven urgency the way Tasks had). Same upfront research pass
every increment gets before writing code, this time specifically aimed at settling one open question
from the plan doc: does `services/agent_service.py` — the actual AI orchestration engine, not the
`routers/chat.py` HTTP wrapper around it — need to change at all, or does it stay core?

**`agent_service.py` stays 100% core — confirmed by direct code read, not assumed from the plan
doc.** Grepped the whole file for router imports (zero), HTTP-shape assumptions (`Request`/
`HTTPException`/`Depends` — zero), and any module-gating logic of its own (`require_module` is
purely the router's job — zero). Independent, pre-existing confirmation this split was already
correctly anticipated: `module_registry.py`'s own `register_routers()` docstring had already named
"Tasks, Chat, Dashboards" as deeply load-bearing modules before this conversion touched a single
line. Only `routers/chat.py` (675 lines, a thin HTTP wrapper) moved to
`module_packages/chat/backend/router.py` — the smallest single-file move of any conversion so far,
since there was no service file of Chat's own to leave behind or bring along, unlike every prior
conversion.

**Session/pending-turn/presence bookkeeping stays core as one unit with the loop itself, not just
because of "who calls it."** `save_pending_turn()` is called from *inside* `run_agent()`'s own step
loop (3 call sites) — you cannot split session bookkeeping out from the loop that produces it
without breaking the loop. This settles the question more concretely than a simple consumer-count
argument would have.

**Gap #1 — two of Chat's own 11 endpoints were never actually gated on the module.** Found during
the same research pass that confirms every conversion's file inventory: `GET /chat/runs` and
`GET /chat/runs/{run_id}` used plain `Depends(get_current_user)` instead of `Depends(_require_chat)`
— the only two exceptions in the whole router. A user with chat disabled via their feature role
could still read past agent tool-use run history through these two. Fixed by switching both to
`_require_chat`, matching the other 9. A real pre-existing bug this conversion happened to be
positioned to catch, not something it introduced.

**Gap #2 — chat's own Brain folder had zero protection, unlike every other module's owned data.**
`routers/brain.py`'s skip-list (`_ALWAYS_SKIP = {"Tasks", "Business"}`, unconditional/structural) was
never the whole story — `brain_paths_for_disabled()` unions it with every *disabled* module's own
`owned_brain_paths`, the same mechanism Journal/Home Assistant/Notes/etc. already use to hide their
folders from the Brain browser and the AI's own `list_brain_files`/`read_brain_file`/`search_brain`
tools when disabled. Chat's manifest had declared no `owned_brain_paths` at all before this
conversion — meaning a disabled user's own `Chats/` archive folder was fully readable both ways
regardless of chat's module state, a real, previously-open gap this conversion happened to close, not
one it created. Closed by declaring `owned_brain_paths=["Chats"]` — the generic gap-closing machinery
built once for Journal (increment 1) closed a real hole in a completely different module the moment
its manifest finally declared what it owns, with zero new code required.

**Dead code found and removed, not left as a TODO.** `routers/suggestions.py` defined
`_require_chat = require_module("chat")` but never called it anywhere in that ~100-line file — a
leftover from an earlier draft, confirmed by exhaustive grep before removing both the assignment and
the now-unnecessary `require_module` import.

**Test-file split, same pattern as Household's `test_agent_member_resolution.py` move.**
`tests/test_chat_sessions.py` (24 tests before this conversion) split into
`module_packages/chat/tests/test_chat_router.py` (14 tests exercising the moved router:
`_write_chat_archive`, `POST /chat`'s session-creation/reuse/error-recovery paths,
`GET /chat/pending/{chat_id}`'s live-card/question-derivation logic, resume-history alternation edge
cases, presence-gated notification skip/send) and a trimmed `tests/test_chat_sessions.py` (10 tests,
pure `agent_service.py` session-index/presence coverage, no router involved). The `brain` fixture's
Tasks-era fix (auto-installs every `uninstallable=True` module) paid off immediately here too — zero
explicit `mark_installed` calls needed anywhere in the moved test files, confirming that fix was
genuinely generic, not tuned to Tasks specifically.

## Real-instance bug report: compact-density users had a broken AI Chat composer app-wide

Owner, before moving to the next Mod Store increment, reported the chat composer "sunk into the
footer" (partly hidden behind the mobile bottom nav) on their own personal instance specifically —
remembered it as a possible regression from the 2026-08-22 fix that removed Chat's duplicate
mobile-nav-clearance spacer (`db521d2`).

**Two dead ends, reported honestly rather than silently dropped.** First checked whether that spacer
had come back or whether today's Chat module-package move touched anything relevant — diffed the
moved `Chat.jsx` against the pre-move committed version; only import paths differed, nothing in the
returned JSX. Then chased a nav-label-wrapping theory (the same class of bug that hit "n8n Automation"
on 2026-08-25) — rendered the owner's own real pinned shortcuts (`Dashboard`/`Tasks`/`AI Chat`/
`Household`, read directly from `auth.json`) against the real compiled CSS at every mobile width from
320px to 430px. Never wrapped. Told the owner this theory was disproven rather than shipping a fix for
it anyway; did apply a small, independently-justified hardening (`min-w-0` + `truncate` on nav labels,
per the owner's own pick between two proposed approaches) since it forecloses the wrap class of bug for
good with zero downside, but was explicit that it wasn't confirmed to be the actual fix.

**The owner's own follow-up broke the case open**: they'd opened the *other* instances on the *same*
phone and confirmed those rendered correctly — ruling out device/browser/PWA-vs-tab theories in one
message, since a client-side quirk can't explain two different results from the same client. That
reframed the search from "what's different about this device" to "what's different about this
account." `brain/_system/auth.json` showed the answer immediately: this personal-instance account has
`density: "compact"` set, the only account on the instance that does.

**Root cause**: `index.css`'s compact-density override, `html.compact main { @apply p-3 md:p-4; }`,
used the `padding` shorthand. That selector's specificity (element + class + element) beats a single
Tailwind arbitrary-value utility class like `.pb-\[calc\(4.5rem+env\(safe-area-inset-bottom\)\)\]`
regardless of source order — so the shorthand's `padding-bottom: 0.75rem` (12px) silently won over
`<main>`'s intended ~72px+safe-area mobile-nav clearance, for every compact-density user, on every
page. Chat's bottom-anchored composer just made it visible first, same pattern as the original
2026-08-22 report. Fixed by scoping the override to `pt-3 px-3 md:pt-4 md:px-4` — top/left/right only,
never touching `padding-bottom`.

**Verified**: measured `getComputedStyle(main).paddingBottom` under `html.compact` directly in a
headless browser against the real compiled CSS — 12px before, 72px after, matching `<main>`'s own
intended value. `eslint`/`vite build` clean. Since the personal instance bind-mounts this exact
checkout (see 2026-08-22's own gotcha on this), the fix is already live there the moment the build
ran — the owner can confirm with a normal reload, no deploy step needed.
