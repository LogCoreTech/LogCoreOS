## Real-usage bug report: five issues, two led to a second bug apiece

Owner tested the shipped work live and reported five things in one message: the
dashboard block-button color picker was unreadable; Chat's "Thinking…" bubble
doesn't survive a reload/reopen while the agent is genuinely still running; blank
assets have no way to add custom fields ("which is mandatory"); no way to delete a
contact anywhere; the presence dot isn't visible anywhere in the UI. Full writeup in
`docs/MEMORY.md`'s Key Decisions Log, "2026-08-17 (third)" entry.

Two of the five each uncovered a second, more severe bug while investigating the
reported one:
- **Blank assets**: the missing custom-fields UI was real (added a freeform
  label/value repeater, `assets_service._validate_fields()` relaxed for a genuinely
  template-less asset). But `update_asset()` was ALSO silently rejecting every save
  of a blank asset with `"Template None no longer exists"` (`resolve_template()`
  conflated "no template at all" with "a template that used to exist and got
  deleted") — blank assets had been fully uneditable since they shipped earlier
  today, not just missing a feature.
- **Contacts delete**: `DELETE /contacts/{id}` always worked; the frontend never had
  a button wired to call it, anywhere. Added to `ContactModal.jsx`, gated exactly
  like `AssetModal.jsx`'s own Delete button (self-contact never; pool contact
  admin-only; personal contact needs edit access).

The other three: color picker replaced with a compact swatch-popover (mirrors
`EmojiPicker.jsx`'s existing pattern); Chat's running-state restoration via a new
`restoredRunningIds` poll that re-syncs against `GET /chat/sessions` until a reopened
conversation's status moves off `"running"`; presence dot wired into
`contacts_service.annotate()` (`_online` field) and a small overlay in
`ContactAvatar.jsx` — this was the known, deliberately-deferred back half of Item 9,
not a new bug, now that the Contacts pool rework it depends on is done.

Full backend suite green (748 passed, up from 743), `black`/`isort`/frontend
`lint`/`build` all clean. New/rewritten backend tests for both real bugs found
(`test_blank_asset_custom_fields_survive_update_and_can_be_cleared`,
`test_resolve_template_distinguishes_blank_from_stale_reference`) plus the presence
wiring. The Chat fix and the two pure-UI additions (color picker, Delete button) have
no automated coverage — this codebase has no router/component-level test harness —

## Presence dot still wrong after a few minutes — the real cause, plus a last-seen tracker

Owner, after testing the presence fix above for a few minutes: "the presence dot is
still red." Full writeup in `docs/MEMORY.md`'s Key Decisions Log, "2026-08-17 (fourth)"
entry. Traced the whole ping chain (router registration, endpoint, `Layout.jsx`'s ping
effect, `api.js`'s export) before touching anything — all correct. The real cause:
`Contacts.jsx` had no refresh mechanism at all, unlike Dashboard (which got the
identical class of fix earlier today) — the ping was working the whole time, the
already-rendered page just never asked again. Fixed with a 60s poll-while-visible,
same pattern as Dashboard, plus re-syncing the separately-held `detail` (open contact
panel) state, which `load()` never touched before.

While diagnosing, owner asked for a "last seen" tracker — clicking the dot pops a
small tag below it with a relative time (minutes for the first hour, hours up to a
day, days uncapped after that, per owner's exact follow-up spec). Backend exposes the
raw timestamp (`presence_service.last_seen_iso()` → `_last_seen` on the contact,
alongside `_online`); frontend does the relative-time formatting
(`components/contacts/presence.js`). Found a real markup bug before shipping: the
dot's clickable trigger can't be a real `<button>`, since `Contacts.jsx`'s `ContactRow`
already renders the whole row as one — used a `<span role="button">` instead.

Two immediate owner follow-ups on the same feature, same day: "can you make it where
it shows the time tag when clicking the profile photo instead of the dot. the dot is
too small" — click target moved from the 10px dot to the whole avatar
(`pointer-events-none` on the now-decorative dot so it doesn't intercept). Then: "also
need it to open the tag to the right and not the left cause it opens half off screen"
— the popover was anchored `right-0` (grows leftward), which runs off-screen for any
avatar near the left edge of the viewport; swapped to `left-0` (grows rightward).

Full backend suite green, new tests for `last_seen_iso()` and the `_last_seen`
annotate wiring. The refresh-cadence fix and the click-popover interaction are
UI-only — flagged for the owner's own confirmation.

## Convert a personal contact to pool, single + bulk

Owner: "i dont see a button or anything that can convert personal contacts to pool
ones? also would like a way to bulk convert since i have so many." Full writeup in
`docs/MEMORY.md`'s Key Decisions Log, "2026-08-17 (fifth)" entry.

No new transfer mechanism needed — `contacts_service.transfer_ownership()` already
existed (previously only called from account-deletion handling) and already did
exactly this. Two new endpoints reuse it directly: `POST /contacts/{id}/convert`
(single contact, self-service — `edit` access, not admin-only, a deliberate departure
from Assets' own admin-gated convert-to-pool, reasoned as consistent with pool-contact
*creation* already being open to any user) and `POST /contacts/convert-bulk`
(`{contact_ids?}`, omit for "convert everything eligible," returns
`{converted, skipped}`). Frontend: a "→ Household"/"→ Team" button in
`ContactModal.jsx`'s edit view, plus a toolbar button on `Contacts.jsx` opening
`BulkConvertContactsModal.jsx` — a checklist defaulting to everything selected, since
the owner's own framing was "I have so many," not "let me pick a few."

Caught before shipping: the single-convert endpoint's first draft returned
`{"ok": true}`, which would have broken `ContactModal.jsx`'s save flow (it expects a
real annotated contact back to re-sync the open detail panel). Fixed to return the
full annotated contact, same shape every other mutation endpoint uses.

Full backend suite green (750 passed), `black`/`isort` clean, frontend `lint`/`build`
clean. No new automated coverage for the two router endpoints themselves — this
codebase has no router-level test harness (confirmed again: zero `TestClient`/RTL
usage anywhere in `tests/`) — flagged for the owner's own click-through.
