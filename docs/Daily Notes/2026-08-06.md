# 2026-08-06

## Bug fix: mobile drag armed and followed the finger but never actually moved the block

Owner tested yesterday's press-and-hold mobile drag on a real device and reported: "the hold and
drag works as intended but the grid doesnt unlock so the blocks cant be moved." The arming/visual
feedback half of the mechanism was confirmed working; the actual move wasn't sticking.

**Root cause**, found by re-reading `DashboardGrid.jsx` rather than guessing: `commitDrag()` (added
yesterday) computes the new grid position correctly and calls `onLayoutChange`, but that prop only
ever updates `Dashboard.jsx`'s `pendingLayouts` state — nothing fed it back into `DashboardGrid`'s
own `layouts`, which is (and was) computed purely from the `blocks` prop via `useMemo`. The instant
`clearGesture()` removed the CSS-transform "ghost drag" that had been visually tracking the finger,
the block re-rendered from `layouts` — still reflecting the *old*, unchanged `blocks` — and snapped
straight back to its starting position. The pending change genuinely existed the whole time (Save
Layout would have persisted it correctly), it just never *looked* like it did. Desktop mouse
dragging never had this problem: `react-grid-layout`'s own drag mechanism holds a dropped position
in its own internal state independent of props, and this hand-rolled touch path had no equivalent
of that guarantee.

**Why yesterday's Playwright pass didn't catch this**: every assertion checked the position *after*
clicking "Save Layout," never in the gap between release and save — exactly where the bug lived. A
genuinely useful lesson for testing this class of interaction going forward: a passing "final value
is correct after an explicit save" check says nothing about whether the UI looked broken in between.

**Fix** (`DashboardGrid.jsx`): a new `localOverrides` state (`{[breakpoint]: {[blockId]: {x,y}}}`),
merged into `layouts` inside the same `useMemo`, set by `commitDrag()` alongside the existing
`onLayoutChange` call so the grid's own rendering reflects the dropped position immediately —
matching what `react-grid-layout` already does for free on desktop. Cleared via a `useEffect` on
`blocks` itself, since once the server-authoritative data changes (Save Layout persisting, or
switching dashboards) the override is redundant.

**Verification**: isolated backend + synthetic brain + Playwright/CDP touch dispatch, same
methodology as yesterday, but checking the actual `getBoundingClientRect()` position at the exact
gap the previous round missed — immediately after `touchend`, before any Save Layout interaction.
Confirmed: the block holds its new position right away (no snap-back), stays stable a further
800ms (not a transient render artifact), and round-trips correctly through Save Layout and a fresh
page reload. `npm run build` and eslint clean, no new warnings.

**Not verified, same caveat as every mobile-PWA claim in this project**: the fix closes a real,
confirmed bug in the mechanics, but whether a held touch feels right on real iOS Safari standalone
still needs the owner's device — nothing here changes that.

- Docs: `docs/MEMORY.md` (new Key Decisions Log entry), `docs/TASKS.md`

Redeployed via `bash launch.sh --skip-build` and committed.

## Same day, second follow-up: text-selection popup during the hold, and "moves up/down but not left/right"

Owner tested the fix above and reported two more things: "the touch and hold makes the select text
thing pop up and looks terrible," and "now it moves up and down but not left and right." One was a
real, unambiguous bug; the other turned out — after actually checking rather than assuming — to be
correct, expected math, not a defect.

**Text-selection callout**: a long-press on anything with text is *also* the browser's own gesture
for text selection — the magnifying-glass loupe and Copy/Select All popup on iOS, similar treatment
on Android — and nothing in the press-and-hold implementation ever suppressed it, so it could win
the race against the drag-arm timer. Standard, well-known fix: `-webkit-touch-callout: none`,
`-webkit-user-select: none`, `user-select: none` on `.block-drag-handle` (`index.css`) — applied to
the handle unconditionally, not scoped to `.touch-drag-armed`, since the callout can appear *during*
the hold itself, before the block ever arms.

**Horizontal movement**: rather than assume the drag math had an axis-specific bug, spun the
isolated Playwright/CDP harness back up and tested directly — dragged a narrow (`w:6` of 12 mobile
columns) block and a full-width (`w:12`) block sideways under the same conditions. The narrow block
moved and persisted correctly (`sm.x` 0→4, survived Save Layout and a fresh reload); the full-width
block correctly could not move at all. Root cause isn't a bug: `commitDrag()`'s own bounds clamp,
`Math.max(cols - moved.w, 0)`, evaluates to `0` when a block's width equals the grid's column count
— there is nowhere left or right for a block exactly as wide as the grid to go. `m012` (yesterday)
unconditionally normalized every pre-existing block's mobile width to full (`w:12`) as part of
making `layout.sm` genuinely readable for the first time — a safe default at the time, but it means
every block on any dashboard from before this week's mobile-editing work is currently full-width and
mathematically stuck until resized narrower. The resize handle was never gated behind the
press-and-hold requirement (only *dragging* the whole card was), so it already works immediately on
touch — the actual gap here is discoverability, not mechanics, and the fix is explaining it rather
than changing correct code.

**A real lesson, twice over**: the first attempt at verifying this made it briefly *look* like a
genuine drag bug — the test dragged a narrow block, watched `commitDrag()`'s own debug log show the
right numbers (`nextX: 4`, no overlap), then checked the API and saw `x` still at 0. The test had
simply forgotten to click "Save Layout" before checking — the exact same class of mistake as
yesterday's first verification round, just in the opposite direction (there it was an unnecessary
save that broke a later test; here it was a missing one that made a working feature look broken).
Fixing the test showed the mechanism working correctly the whole time. Worth remembering going
forward: an unexpected result from a hand-written verification script is at least as likely to be a
script bug as an app bug, especially when the same script already has one save/edit-mode-state
mistake on record from the round before.

**Verification**: `npm run build` and eslint clean (0 new warnings). Isolated Playwright/CDP
confirmed both the callout-suppression CSS ships in the built bundle and the horizontal-drag
mechanism itself (narrow block moves and round-trips through save + reload; full-width block
correctly can't).

### Files updated

- Frontend: `app/frontend/src/index.css` (touch-callout/user-select suppression on the drag handle)
- Docs: `docs/MEMORY.md` (new Key Decisions Log entry), `docs/TASKS.md`

No `DashboardGrid.jsx` changes this round — the drag math itself needed no fix, only the CSS above.

## Same day, third follow-up: the horizontal-movement diagnosis was right, but there was a bigger bug hiding behind it

Owner pushed back on the "resize narrower first" explanation with the actual reproduction: "i think
its not 'saving' that i resized them. so it wont let me move them over. example i resize one and
then select another and the first one goes back to original full size." That single example
unlocked the real, general bug — the previous fix (the first section above) was necessary but not
sufficient, and this is the reason resizing looked broken too.

**Confirmed the theory wrong the fast way — read the library, don't keep guessing at the app.**
Grepped `node_modules/react-grid-layout` a second time and found `ResponsiveReactGridLayout.js` has
its *own*, separate `getDerivedStateFromProps` — distinct from the inner grid's `activeDrag`-aware
one documented in the first section above. This outer one has no concept of an active gesture at
all: the instant the `layouts` prop changes for *any* reason relative to what it last saw, it
regenerates its entire internal layout fresh from that prop, discarding whatever the inner grid was
independently holding from a resize or a native mouse-drag. Since resize and native desktop
drag never fed their result back into that prop — only into `Dashboard.jsx`'s separate `pendingLayouts`,
same gap as the touch-drag bug from yesterday — the prop stayed stale indefinitely, *as long as
nothing else touched it*. The moment something did (dragging a second block, exactly "select
another"), the whole layout got rebuilt from the stale prop, and the first block's resize vanished.

**Fix**: generalized yesterday's `localOverrides` (renamed `pendingLocalLayouts`) so it's populated
by *every* layout report, not just the hand-rolled touch-drag's. A new `reportLayoutChange()` wraps
both `commitDrag()`'s own commit and `<ResponsiveGridLayout>`'s native `onLayoutChange` (which fires
for ordinary mouse-drag and resize on both breakpoints) — so the prop handed back to
`react-grid-layout` is never stale for any block, regardless of which of the three mechanisms
(native mouse-drag, native resize, hand-rolled touch-drag) touched it last.

**Verification**: isolated Playwright, testing the owner's exact reproduction — resized a block via
the desktop mouse handle (confirmed it visually shrank), then dragged a *second*, unrelated block,
then confirmed the first block's size was unchanged (previously this is exactly where it would have
reverted). Both changes persisted correctly through Save Layout. Re-ran the horizontal- and
vertical-drag mobile checks from the previous two rounds against the new code path, including
back-to-back drags (a second drag preserving the first drag's already-saved axis) — all green.
`npm run build` and eslint clean.

**How this changes the read on the earlier "resize narrower first" explanation**: still correct as
far as it went — a full-width block genuinely cannot move sideways, that math was never wrong — but
it wasn't the whole story, and the owner's own reproduction (resize, then select another) was the
thing that actually pointed at the real, bigger bug. Worth remembering: a technically-correct partial
explanation can still leave the door open for the real bug to hide behind it.

### Files updated

- Frontend: `components/dashboard/DashboardGrid.jsx` (`pendingLocalLayouts` now fed by every layout
  report — native drag/resize via a new `reportLayoutChange()`, not just the hand-rolled touch-drag)
- Docs: `docs/MEMORY.md` (new Key Decisions Log entry), `docs/TASKS.md`

## Same day, fourth follow-up: ✎/✕ stopped responding to touch entirely

Owner: "next is the delete and edit buttons seem broken. i cant delete blocks or open edit. im
wondering if there is a permission issue." Not a permission issue — a real regression from the
touch-drag work two rounds ago, found by testing rather than guessing at the cause.

**First, ruled out a testing artifact, not a real fix.** A first pass using Playwright's `.click()`
on both ✎ and ✕ failed on desktop too — but that specific method is already documented earlier this
week as unreliable against this exact grid (it simulates a small mouse movement before clicking,
which `react-draggable` can interpret as a drag attempt). Switching to a raw DOM `.click()` bypass
showed desktop working fine. Mobile needed a different check: Playwright's own `locator.tap()` API,
confirmed first against a plain, unrelated HTML button (so a failure couldn't be blamed on the test
method itself) — and *that* still failed against the real ✕ button, confirming a genuine app bug,
not another test-tooling quirk.

**Root cause**, found by reading `react-draggable`'s source a third time this week: `DraggableCore.
handleDragStart` — which runs on every `touchstart` matching `draggableHandle`, independently of
this app's own touch-interception code — calls `e.preventDefault()` unconditionally on touchstart,
before ever checking whether a real drag follows. `preventDefault()` on `touchstart` is exactly what
suppresses the browser's own tap-to-click synthesis. Since every ✎/✕ button, and a chromeless
`nav_button`'s own `<Link>` pill, lives inside `.block-drag-handle`, every tap on them was being
silently eaten. A first attempt at a fix — excluding buttons/links inside this app's *own*
`onTouchStartCapture` — didn't help, because it only stops this component's own code from reacting;
`react-draggable`'s own listener, attached separately, still sees the same touchstart and still
calls `preventDefault()` on it regardless of anything this app's code decides to do.

**Fix**: `draggableCancel="button, a"` on `<ResponsiveGridLayout>` — the library's own exclusion
mechanism (mirrors `draggableHandle`), checked *inside* `handleDragStart` *before* the
`preventDefault()` line. This is the same mechanism already used to exclude the resize handle
(`GridItem.mixinDraggable` already prepends `.react-resizable-handle` to `cancel`) — buttons and
links just never got the same treatment when the touch-drag system was first built.

**A second thing chased down in the same report, and ruled out as a real bug**: an early test showed
tapping ✕ apparently deleting all 3 blocks instead of one. Traced to the tapped button rendering
right at the bottom edge of a completely *unscrolled* viewport — `document.elementFromPoint` at that
exact position showed the fixed mobile footer nav's own "AI Chat" link as the true topmost element,
not the button underneath it. The tap navigated to `/chat`; the dashboard "losing all its blocks"
was just the wrong page rendering, not a deletion. Scrolling `<main>` to its maximum moved the same
button to a clearly clickable position — this page already has the standard footer-clearance spacer
(`<div className="h-20 md:hidden">`) other pages in this app use, and normal scrolling behavior
already covers it. Recorded as a finding, not fixed, since there was nothing to fix.

**Verification**: `locator.tap()` on both ✎ and ✕ now works correctly on a regular block and a
chromeless one; re-ran the full drag/resize regression suite from the previous two rounds
(horizontal drag, vertical drag, resize-persists-across-other-interactions) against the same build —
all still green. `npm run build` and eslint clean.
