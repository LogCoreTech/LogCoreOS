# 2026-08-06

## Bug fix: mobile drag armed and followed the finger but never actually moved the block

Owner tested yesterday's press-and-hold mobile drag on a real device and reported: "the hold and
drag works as intended but the grid doesnt unlock so the blocks cant be moved." The arming/visual
feedback half of the mechanism was confirmed working; the actual move wasn't sticking.

**Root cause**, found by re-reading `DashboardGrid.jsx` rather than guessing: `commitDrag()` (added
yesterday) computes the new grid position correctly and calls `onLayoutChange`, but that prop only
ever updates `Dashboard.jsx`'s `pendingLayouts` state — nothing fed it back into `DashboardGrid`'s
own `layouts`, which is (and was) computed purely from the `blocks` prop via `useMemo`. The instant
`clearGesture()` removed the CSS-transform "ghost drag" that had been visually tracking the finger,
the block re-rendered from `layouts` — still reflecting the *old*, unchanged `blocks` — and snapped
straight back to its starting position. The pending change genuinely existed the whole time (Save
Layout would have persisted it correctly), it just never *looked* like it did. Desktop mouse
dragging never had this problem: `react-grid-layout`'s own drag mechanism holds a dropped position
in its own internal state independent of props, and this hand-rolled touch path had no equivalent
of that guarantee.

**Why yesterday's Playwright pass didn't catch this**: every assertion checked the position *after*
clicking "Save Layout," never in the gap between release and save — exactly where the bug lived. A
genuinely useful lesson for testing this class of interaction going forward: a passing "final value
is correct after an explicit save" check says nothing about whether the UI looked broken in between.

**Fix** (`DashboardGrid.jsx`): a new `localOverrides` state (`{[breakpoint]: {[blockId]: {x,y}}}`),
merged into `layouts` inside the same `useMemo`, set by `commitDrag()` alongside the existing
`onLayoutChange` call so the grid's own rendering reflects the dropped position immediately —
matching what `react-grid-layout` already does for free on desktop. Cleared via a `useEffect` on
`blocks` itself, since once the server-authoritative data changes (Save Layout persisting, or
switching dashboards) the override is redundant.

**Verification**: isolated backend + synthetic brain + Playwright/CDP touch dispatch, same
methodology as yesterday, but checking the actual `getBoundingClientRect()` position at the exact
gap the previous round missed — immediately after `touchend`, before any Save Layout interaction.
Confirmed: the block holds its new position right away (no snap-back), stays stable a further
800ms (not a transient render artifact), and round-trips correctly through Save Layout and a fresh
page reload. `npm run build` and eslint clean, no new warnings.

**Not verified, same caveat as every mobile-PWA claim in this project**: the fix closes a real,
confirmed bug in the mechanics, but whether a held touch feels right on real iOS Safari standalone
still needs the owner's device — nothing here changes that.
