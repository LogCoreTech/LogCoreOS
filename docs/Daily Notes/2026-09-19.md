# 2026-09-19

## Homes v1.1 — maintenance reminders, Home Health block, Assets/Contacts tabs

Following up on yesterday's Homes module launch, owner asked what other common home-management apps (HomeZada, Centriq, Sortly/Encircle, Angi/Thumbtack) do that would be worth adding, picked four of the ideas offered (skipping a fifth, home-value tracking, since it would force a cloud-API dependency), and asked to plan then build all four in one pass. Went through a full plan-mode round first — two parallel research agents (Dashboard block config wiring, Tasks' recurrence schema) plus a design-validation agent, each verified directly against real code before trusting it — before writing anything.

One real design pivot came out of that process: the initial assumption was that the new "Home Health" dashboard block would need `due_date`/`status`/`amount_cents`/`date` added to 4 search providers (mirroring yesterday's `start_date`/`end_date` fix). Checking every existing `dashboard_block.py` in the codebase first showed none of them route through `search_service.search()` at all — each reads its own service's raw records directly, since `BlockRenderCtx` doesn't carry a full `current_user` dict the way `search()` needs. Dropped the search-provider extension entirely; the block's resolver just calls `task_service`/`events_service`/`finance_service` directly, which is both smaller and more consistent with precedent.

Also resolved, on the way: whether "documents" (leases, deeds, insurance policies) need their own bespoke concept. Decided no — Assets already supports PDF attachments (up to 20/record, 10MB each) and already tags/searches correctly; once Assets got its own Homes tab, a tagged lease PDF just shows up there. Building a parallel document store would have duplicated real, working file-handling code for no gain.

**What shipped:**
- **Maintenance reminder presets** — a "+ Reminder" dropdown on a home's Tasks tab (HVAC filter monthly, gutter cleaning/smoke detectors every 6 months, water heater yearly, or Custom) opens the real `TaskModal.jsx`, pre-filled, mirroring Goals' own "+ Task" button exactly (`TaskModal.jsx` gained `defaultTitle`/`defaultTags`/`defaultRecurrence` props, following the same idiom `defaultAssetId`/`defaultGoalId` already used).
- **Home Health dashboard block** — new `module_packages/homes/backend/dashboard_block.py`, a new `find_home()` two-tier (own store, then household/team pool) resolver in `homes/backend/service.py`, and the full frontend picker-registration chain (`HomePickerField.jsx`, a new `case 'home'` in `BlockPicker.jsx`, a `blocks` entry in `homes/manifest.js`, `HomeHealthBlock.jsx`).
- **Assets and Contacts tabs** on `HomeDetail.jsx` — zero backend change needed; both already fold pool visibility into their own single search provider, so the `itemKind()` helper (added yesterday for the household/team events bug) already classified them correctly. This is also the "document vault" and "preferred contractors" ideas — no new fields, just tagging.

13 new backend tests (`find_home()` × 4, `resolve_home_health` × 7, service-level). Full backend suite: **1581 passed, 0 failed**. black/isort/eslint/build all clean.

## A real infrastructure finding while redeploying

Rebuilding and restarting the `app` container the same way as every prior restart this session (`docker compose build app && docker compose up -d app`) produced different output than usual — `docker compose` reported creating the network from scratch and `logcore-tunnel` wasn't in the running container list at all. Checked `docker ps -a`: the tunnel container didn't exist even in a stopped state. Checked host `uptime` (4 days, no reboot) and `docker info`'s system time to rule out a host restart or Docker daemon crash as the cause — neither happened. The most likely explanation is a `docker compose down` run from elsewhere (the owner runs parallel sessions) that hadn't been followed by a subsequent `up`, leaving the entire stack — not just `app` — down before this session touched anything tonight; `docker compose up -d app` only starts the named service plus its own declared dependencies, not sibling services like `tunnel` that aren't in `app`'s own dependency chain.

Brought `tunnel` up explicitly (`docker compose up -d tunnel`) once this was noticed — reconnected cleanly, 4 registered edge connections, clean logs. Verified end-to-end afterward: `GET /api/v1/health` → 200, clean `app` startup logs, and `home_health` confirmed present in the live container's `services.dashboard_blocks.registry.REGISTRY` (not just locally). Flagged to the owner immediately rather than assuming the unusual `docker compose` output was normal — this is exactly the kind of unexplained state-on-a-live-instance situation this session's own standing practice is to pause and report on, not push through silently.
