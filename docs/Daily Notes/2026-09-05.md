## Accessibility audit — real keyboard-nav gaps found and fixed

Continued into the item flagged open at the end of 2026-09-04. Rather than guessing at what a
"keyboard-nav/focus audit" should cover, checked for concrete, evidence-based gaps first (grep, not
speculation) — three real ones found, all fixed:

**1. No modal in the entire app trapped Tab focus.** A keyboard user could Tab straight past the last
focusable element in an open modal into the page content behind the overlay — incorrect per the ARIA
Authoring Practices Dialog pattern, and genuinely disorienting. New `lib/useFocusTrap.js`, same
"hook every modal wires in individually" shape `useEscapeToClose.js` already established (no shared
`<Modal>` wrapper exists in this codebase for either concern to ride on). Built and verified by hand
on `ConfirmDialog.jsx` first, then delegated the retrofit across the other ~41 modal instances to two
parallel background agents (31 more files, split ~15/15) — every diff read and verified directly
before trusting it, not just the agents' own summaries.

Several files needed real judgment beyond the mechanical ref-plus-hook-call pattern, and both agents
got them right: a modal whose card element changes *within one persistent component instance* rather
than fresh-mounting needed the hook's `active` param tied to that same condition, so the trap's effect
tears down and re-attaches to the newly-rendered card each time — `Notes.jsx`'s 6 mutually-exclusive
form blocks (newNote/newFolder/rename/move/deleteNote/deleteFolder) share one `modalCardRef`, gated on
`!!modal`; `TaskModal.jsx`'s view/edit mode switch, gated on `mode !== 'view'` (and correctly placed
*before* its own early return to `<TaskView/>`, respecting Rules of Hooks); `GoalModal.jsx`'s delete
popup (a second, separate card), gated on `showDelete`; `WelcomeBackPopup.jsx`'s self-toggled
visibility (mounted unconditionally by `Layout.jsx`, decides its own `if (!state.show) return null`
internally), gated on `!!(state && state.show)`. A few files also had non-`.modal-card` root elements
(`Automations.jsx`'s `LogsModal`/`ImportModal`, `GoalModal.jsx`'s delete popup's own `.card` class,
`assetDisplay.jsx`'s portal-based `ImageLightbox` with no separate overlay/card split at all) — both
agents correctly targeted the real content root in each case rather than blindly assuming `.modal-card`
everywhere.

**2. No skip-to-content link.** A keyboard user had to Tab through the entire sidebar (or mobile
header) on *every single page* before reaching real content. Added to `Layout.jsx` — visually hidden
(`sr-only`) until focused, then jumps to a new `id="main-content"` on `<main>` (also gained
`tabIndex={-1}` so it's actually focusable via the jump — a bare `<main>` isn't natively focusable and
some browsers won't move focus to a fragment target that isn't).

**3. `TagInput.jsx`'s own text input had `outline-none` with nothing replacing it anywhere** — the
wrapping pill/tag field had no `focus-within` styling at all, so a keyboard user tabbing into a tag
field (used across Contacts' Core Values, Assets' template fields, sharing pickers) got zero visual
indication of where focus landed. Fixed with `focus-within:ring-2 focus-within:ring-orange-500` on the
wrapper, matching `index.css`'s own standard `.input` focus-ring exactly rather than inventing a new
style.

**Deliberately left as lower-priority/open**, not chased further this pass: full ARIA-Tabs arrow-key
navigation on Goals'/Finance's own custom tab-switcher widgets (already keyboard-reachable via real
`<button>` elements and Tab+Enter, just not the enhanced arrow-key pattern), and a broader unbounded
page-by-page audit beyond the three concrete gaps found above.

`eslint --max-warnings 0` across the full `src` tree and `vite build` both clean throughout.

## Owner-reported bug: confirmation popups not fixed on screen, background kept scrolling

Owner: "it appears that the 'are you sure' toasts... are not fixed on the middle of the screen they
are attaching to whatever page they are on... they all need to be separately fixed and stop all other
scrolling while it is open. please check all items."

Root cause: the exact same pre-existing "nested-modal clipping" bug already documented in `docs/MEMORY.md`
for `assetDisplay.jsx`'s `ImageLightbox` and `GoalModal.jsx`'s own `Portal` — `.modal-card` applies
`.card`'s `backdrop-blur-sm`, and `backdrop-filter` on an ancestor creates a new containing block for
`position: fixed` descendants, so a modal rendered nested inside another already-open `.modal-card`
resolves its own "fixed" positioning against that OUTER modal's scrolled box instead of the true
viewport — it visually rides along as the outer modal's own content scrolls. This time it was hitting
`ConfirmDialog` itself, made dramatically more visible by #9's own work earlier this same batch: #9 added
a "Discard changes?" `ConfirmDialog` to six major edit forms, meaning `ConfirmDialog` now opens nested
inside an already-open modal far more often than the handful of pre-existing "Delete this?" call sites
ever did. A pre-existing, narrow bug became a routinely-hit one because of work shipped the same day —
worth naming plainly rather than glossing over.

**Fix, at the root rather than per-call-site**: `ConfirmDialog.jsx` now always renders via
`createPortal(..., document.body)` — this alone fixes every current and future call site (there are
~40) regardless of nesting, permanently, without needing to find and patch each one individually. New
`lib/useScrollLock.js` locks the app's single scrollable `<main>` container while open — module-level
reference-counted (not per-instance state) so a dialog stacked on top of an already-open modal doesn't
prematurely re-enable scrolling when the inner one closes while the outer one is still open.

**"Check all items" — a real, systematic sweep, not just the one reported symptom.** Grepped for every
file with more than one `.fixed inset-0`/`.modal-overlay`-shaped block (the fingerprint of a nested
popup) and checked each candidate by hand rather than assuming the bug was ConfirmDialog-only:
- `AssetModal.jsx`'s `archivePrompt` and `SaveAsTemplateModal` — the *exact two instances* flagged as
  known-unfixed back on 2026-08-29 (`docs/TASKS.md`'s own Product Backlog said so explicitly) — both
  now portaled, closing a documented, aged gap rather than a new one.
- `AssetView.jsx`'s mute-notifications popup — same bug, not previously flagged anywhere; found fresh.
- Along the way, found a *second*, related bug in the same files: `AssetModal.jsx`'s main editor
  (`useFocusTrap(cardRef)` with no `active` tied to its own `mode` view/edit toggle — TaskModal got
  this right during yesterday's retrofit, AssetModal didn't), its own `archivePrompt`, `AssetView.jsx`'s
  mute popup, and `RecurringPanel.jsx`'s two form popups all had a *stale* focus trap: the hook's effect
  (deps `[threshold, enabled, containerRef]`) only ever ran once, at the persistent parent component's
  own mount — while the popup's ref was still null — and never again, since none of those deps change
  when an internal toggle later opens the popup. All four fixed by adding the missing `active` argument
  (mirroring how Notes.jsx/GoalModal.jsx/WelcomeBackPopup.jsx were already correctly handled in
  yesterday's own retrofit — this was a real miss in that pass, not a new class of bug).
- Checked whether `RecurringPanel.jsx`'s/`InvoicesPanel.jsx`'s own popups needed portaling too, not
  just the stale-trap fix — confirmed they don't: neither `RecurringPanel` nor `InvoicesPanel` is
  itself nested inside another modal (both render as normal in-page panel views on the Finance page),
  so their own popups were never subject to the containing-block bug, only the separate stale-trap one.
- Two unrelated findings surfaced during the sweep, deliberately **not** fixed here (a different bug
  class, out of scope for this specific report): `Journal.jsx`'s history drawer and `Tasks.jsx`'s
  reorder-priorities modal have no Escape-to-close, focus-trap, or scroll-lock at all — neither is
  nested inside another modal, so neither has the containing-block bug; they were just apparently
  absent from Tier 1's original retrofit file list. Filed in `docs/TASKS.md`'s Product Backlog rather
  than silently fixed, so the owner can decide whether it's worth a pass now or later.
