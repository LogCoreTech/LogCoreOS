# 2026-08-05

## Dashboard: real pickers for record-linked blocks + finer grid

Owner opened by asking for "significant changes" to both the Dashboard module and the overall
app layout, and explicitly asked to be interviewed extensively rather than have anything assumed.
First interview round covered sequencing, app-layout customization philosophy, and the desktop/
mobile dashboard split — owner's answers narrowed scope hard: **drop the app-wide layout reflow
entirely**, and build the dashboard's customizable-positioning piece first, checking how it looks
on PC before deciding anything about a separate mobile layout. A second, tighter round nailed down
grid granularity ("much finer, still snapped" — explicitly not true free-form) and picker rollout
("all block types in one pass").

Used `/plan` for this one given the file count involved. A Plan agent reviewed the design against
the actual codebase and caught a real gap: every already-saved dashboard has its block positions
stored in the *old* 12-col/80px grid units — rescaling the grid without a data migration would have
made every existing dashboard render as tiny misplaced slivers on next load. Folded into the plan
as a new migration (`m011`). The owner then rejected the plan twice via `ExitPlanMode` — not to
reject the direction, but to sharpen it: (1) "make sure blocks can be put at any point... and
resized easily" surfaced that `react-grid-layout`'s default auto-compaction would silently move a
block after it's dropped, undermining "any point"; (2) "that also should include putting ones side
by side too" surfaced the separate `preventCollision` default, which would displace a neighbor
instead of stopping at a shared edge. Both fixed as explicit `compactType={null}` +
`preventCollision={true}` settings, with the trade-offs (gaps don't auto-fill; swapping two blocks
takes two moves) called out plainly in the plan rather than left as a silent side effect. Plan
approved on the third pass.

**What shipped**: grid moved from 12 cols/80px rows to 36 cols/24px rows (all 28 block types'
`defaultLayout` rescaled ×3 to keep proportions); every record-linked block field (task, contact,
asset, calendar event, finance book, note, n8n workflow) now uses a real search/tree/select picker
instead of a raw ID/path text box — new `TaskPicker`, `EventPicker`, `NotePicker`,
`WorkflowPicker`, `FinanceBookPicker`, `AssetPickerField` (wraps the existing `AssetTreePicker`
using the same inline-toggle idiom `AssetModal.jsx` already uses for its own parent picker); existing
`ContactPicker` reused with one additive fix (resolves a display name from an id-only value, for
prefill). Also added, since a picker fix is incomplete without it: an "✎" edit-config button per
block so a wrong pick can be corrected without deleting and re-adding the block (flagged to the
owner in the plan as slightly beyond the literal ask; not cut). `m011_rescale_dashboard_grid_units`
migration rescales every already-saved dashboard's block layout ×3. Backend block resolvers
untouched — `config` was already an opaque id/path dict; only how it's entered on the frontend
changed.

**Explicitly out of scope this pass** (owner sequencing, not forgotten): any app-wide page
layout/reflow work, and building independent desktop-vs-mobile dashboard layouts — owner wants to
use the desktop grid/picker work first before that design gets scoped.

**Testing**: full backend suite 557 green (16 pre-existing `test_dashboards_service.py` tests + 1
new `test_m011_rescales_existing_dashboard_grid_units`, which also documents that the migration is
deliberately not idempotent — a second run scales again, matching this codebase's existing
migration risk pattern). `npm run build` clean. `eslint` clean on every new/touched file (two
pre-existing, unrelated warnings in `Dashboard.jsx` — an unused `navigate` import and an unescaped
apostrophe — left alone, not introduced by this work).

**Follow-up same session: live browser verification (isolated backend + synthetic brain +
Playwright, same methodology as the scroll-containment audits below)** — registered a fresh throwaway
user against a clean starter brain (explicitly rebuilt from only the generic `_template`/system
files after discovering the repo's own `brain/` folder has real seeded demo accounts with real
password hashes — did not touch those). Live-confirmed end-to-end: creating a dashboard, adding a
"Single Task" block and getting a real search picker (not a text box), searching/picking a
just-created task, saving, and the block correctly flipping from a locked placeholder to resolved
data; the "✎" edit-config button appearing exactly once (gated correctly on `isConfigurable()`);
reopening it and confirming the previously-picked task's title displays via the id-only-prefill fix
(the one actual behavioral change to `ContactPicker`'s sibling logic in `TaskPicker`); and the
add/edit dual-mode `BlockPicker` correctly hiding "Back" in edit mode.

Drag/resize mechanics were NOT cleanly confirmed via automation despite several attempts — root
cause turned out to be twofold and worth recording for next time: (1) Playwright's synthetic
mouse-move-then-click on the ✎/✕ buttons was being swallowed by `react-grid-layout`'s drag-handle
wrapper interpreting the simulated movement as a drag attempt (worked around via a raw DOM `.click()`
once diagnosed — a real user's stationary click doesn't trigger this); (2) a full drag gesture visibly
engaged (ghost element + drop placeholder rendered correctly, following the cursor to the intended
target) but reverted immediately on mouseup unless "Save Layout" was explicitly clicked afterward —
this turned out to be pre-existing, correct app behavior (`onLayoutChange` only stores a *pending*
layout; nothing re-renders the grid from it until `saveLayout()` round-trips through the backend),
not a bug, just something the test script wasn't doing.

While chasing that, found something genuinely unresolved: the dashboard grid's container measured a
fixed ~558px wide in this isolated test regardless of viewport width (1000/1400/1920px all gave the
same number) — meaning it would be stuck on the narrow "sm" 2-column breakpoint instead of the
intended 36-col desktop grid. Traced the CSS mechanism (a flex shrink-to-fit interaction between
`Layout.jsx`'s `<main class="flex flex-col">` and `Dashboard.jsx`'s `<div class="max-w-5xl mx-auto">`
— neither touched this session) but **did not fix it** — plausibly a sandbox-only artifact (the
isolated environment had a directly-observed, unrelated Google Fonts load failure — no internet
access), and this exact DOM structure predates today's work entirely, so if it's a real bug it
already affected the original 12-col grid too and nobody reported it after the 2026-08-04 ship.
Documented in `docs/MEMORY.md` Known Gotchas rather than guessed at further; **flagged for the owner
to do one quick real-browser check** rather than claimed as fixed or dismissed as a non-issue.

## Same-day follow-up: real-device bug reports from the owner

Owner tested on their actual instance and reported four things: the edit-mode Delete button not
reliably showing on mobile, the "✎" edit button "not there either on pc or mobile," blocks not
resizable "unless the method to resize isn't normal," and no "dashboard settings." Investigated each
rather than assuming the earlier session's work was broken:

- **Edit button**: owner confirmed this was their own mistake after re-checking (their existing
  default blocks — Top 3 Tasks, Due Today, etc. — have no configurable fields, so correctly show no
  ✎; it only appears on record-linked blocks).
- **Cache ruled out**: owner confirmed a full close/reopen, still saw issues — real code investigation
  warranted, not a stale-PWA-cache dismissal.
- **Resize handle**: root-caused for real. `react-resizable`'s default corner icon has a 30% opacity
  baked directly into its image data (not overridable via CSS `opacity`), making it very easy to miss
  entirely — exactly matching "unless the method isn't normal." Replaced with a clearly visible
  accent-colored corner bracket in `index.css`.
- **"Dashboard settings"**: owner wanted a real per-dashboard options menu — rename, icon, plus the
  existing Share/Set as default/Delete buttons consolidated into one place instead of a flat row.
  Built `components/dashboard/DashboardSettingsModal.jsx` (name field, `EmojiPicker` reused for the
  icon, then Share/Set as default/Delete as action rows) and wired it in behind a single "⚙ Settings"
  button, replacing the 3 separate buttons. This also plausibly explains the mobile Delete-button
  report as a side effect — a 5-button wrapping row is exactly the kind of thing that overflows
  awkwardly on a narrow phone; the new toolbar is 2-3 buttons.

**Verification this time deliberately included a real mobile-viewport check** (390×844, an actual
iPhone-sized `browser.newContext({viewport})`, not just desktop) after the first verification pass
only tested desktop widths — confirmed `body.scrollWidth` exactly matches the viewport width (no
horizontal overflow) and the Settings button renders fully on-screen. Also hit two of my own
test-script bugs while verifying, worth recording since they'll recur: (1) a generic `.modal-card
input` selector silently grabbed `EmojiPicker`'s own manual-icon-entry `<input maxlength="3">` instead
of the intended name field (it renders first in the DOM) — briefly looked like a broken rename feature
until re-selecting by `maxlength` attribute proved the actual name field worked correctly the whole
time; (2) `context.newPage({viewport})` silently no-ops — viewport must be set on `browser.newContext()`
instead, so an earlier "mobile" screenshot was actually still full desktop width.

Rebuilt (`index-CfqX0Fbq.js`, a genuinely new hash confirming real content changes) and relaunched via
`bash launch.sh --skip-build`.

## Third follow-up round, same day: delete button still invisible, proportions, and a picker-mismatch report

Owner tested again and reported: Delete dashboard still invisible on mobile ("may be the same color
as the card"), wanted "Edit Layout" renamed to "Edit Dashboard", the Settings modal's icon field was
taking too much space from the name field, and — separately — "the linked contact block pulls up the
picker to pick an asset not a contact... a lot of the record based blocks use the asset picker instead
of having its own."

- **Delete button**: root cause this time was real — the button had `text-red-500` with no background
  at all, relying purely on text-color contrast against the modal card, which on mobile (no `:hover`
  state to fall back on) gave it essentially no visual distinction. Gave it a persistent
  `bg-red-50 border-red-200` (dark-mode equivalents) treatment so it reads as an unmistakable danger
  zone regardless of theme — confirmed via a real 390×844 screenshot this time, not just a bounding-box
  number.
- **Icon/name proportions**: `EmojiPicker`'s own manual-entry `<input>` has an internal `flex-1` with
  no outer width constraint from the component itself, so placed directly next to another `flex-1`
  name field, the two competed for space unpredictably. Fixed by wrapping `EmojiPicker` in a fixed
  `w-28` container in `DashboardSettingsModal.jsx` (not touching the shared component, which is also
  used by `TemplateManager.jsx`) so the icon area stays compact and the name field's own `flex-1`
  genuinely takes the rest, as asked.
- **"Asset picker instead of its own"**: checked every flagged resolver against the actual backend
  code before touching anything, rather than assuming the report was correct. All of them —
  `linked_contact`, `linked_assets`, `linked_deals`, `linked_tasks`, `documents` — already request
  exactly the field their own resolver logic needs (e.g. `resolve_linked_contact`'s docstring is
  literally "Asset -> its own contact-type template field"; `resolve_linked_assets`'s is the mirror,
  "Contact -> reverse lookup of Assets referencing it"). Not a bug in the picker-kind mapping — a
  naming-clarity issue predating this session (a block named "Linked Contact" that asks you to pick
  an asset is a reasonable thing to misread as broken). Fixed the two genuinely confusing ones with
  clarifying field labels instead of changing any block's actual behavior: `linked_contact`'s field now
  reads "Asset (shows its linked contact)", `linked_assets`'s reads "Contact (shows the assets linked
  to them)".

All four re-verified live (isolated backend + synthetic brain + Playwright) on both desktop and a real
390×844 mobile viewport before shipping — including a visual screenshot of the Delete button's
background actually rendering pink against the modal's gray, not just a computed-style string.
Rebuilt (new hash each time — `index-QB0gFDHE.js` for this round) and relaunched.

## Fourth follow-up round, same day: the share picker never existed, and the ~558px grid bug was real

Owner reported two more things: "the share page user pickers dont work," and — much more significant
— that the grid "only has 2 columns... needs many more... much finer control," which is *exactly* the
symptom of the still-open, previously-unconfirmed ~558px-container-width finding from earlier today.
The owner hitting this independently on their real device (not the sandbox) settled that question: it
was never a sandbox artifact.

- **Grid container width — root-caused and fixed for real.** `Dashboard.jsx`'s root
  `<div className="max-w-5xl mx-auto">` had no explicit `width`, which (per the CSS flexbox spec)
  disables `align-items: stretch` for a flex item with auto cross-axis margins — it shrinks to fit its
  content instead of filling available space, and since `react-grid-layout`'s own wrapper contributes
  no natural width (everything inside it is `position: absolute`), the whole chain collapsed to
  whatever an unrelated sibling needed. One-word fix: `w-full` alongside the existing classes. Verified
  across three viewport widths (900/1100/1920px) that the grid now scales proportionally and caps at
  exactly 1024px instead of sticking at ~558px — this directly explains "only 2 columns," since a
  sub-768px container falls onto `react-grid-layout`'s `cols.sm: 2` mobile fallback even on a desktop
  browser window.
- **Share picker — there wasn't one.** `DashboardAccessModal.jsx` (built 2026-08-04, never touched
  before today) used a bare free-text `<input placeholder="user name">` for choosing a share target —
  no autocomplete, no member list, unlike every other module (Assets/Finance/Contacts/Notes all have
  `/members` + `/roles` endpoints backing a real picker). Added `GET /dashboards/members` and
  `GET /dashboards/roles` to `routers/dashboards.py` (verbatim mirror of `assets.py`'s versions), wired
  them into a `<select>` for the target field (options: real member names + `household`/`team` + `role:`
  entries) and a `TagInput` (`strict` mode, matching `AssetModal.jsx`'s exact `hidden_from` pattern) for
  the "Hidden from" field, which was also a raw comma-separated text box before.
- **Same-turn follow-up**: owner immediately flagged the new picker row's proportions — the access-level
  `<select>` (read/contribute/edit) and the target `<select>` were both fighting for width because the
  shared `.input` utility class bakes in `width: 100%`, so neither had a clear "natural" size. Fixed by
  giving the access-level select a fixed `!w-32` (the `!` override matching the exact pattern
  `EmojiPicker.jsx` already uses for the same reason) and letting the target field's `flex-1` genuinely
  win the rest of the row — confirmed via bounding-box measurement (target ended up ~2x the access
  select's width) and a visual screenshot.

Also fixed while rewriting `DashboardAccessModal.jsx` from scratch: four pre-existing (not
newly-introduced) `react/no-unescaped-entities` lint errors on lines I was rewriting anyway, since
leaving them wasn't costing anything extra given the full-file rewrite.

Full backend suite re-run after adding the two new endpoints: 556 passed. Rebuilt (new hash each
round) and relaunched.

## Fifth follow-up round, same day: action buttons + full mobile editing

Owner came back once the grid/picker/share fixes above were confirmed working: "it looks great. now
are we able to make the mobile version accept the custom shapes and all that now too? also would like
to add a new set of things. like custom buttons with in app actions... changing the status of certain
assets or users with a single button block, going to certain pages with buttons and unlimited
variations with custom buttons. and make it all click to pick not entering data stuff except button
names and such obviously." A short interview narrowed scope before planning: status actions cover
Tasks/Contacts/Assets (not literal user accounts), nav buttons cover both module pages and specific
records, and — the one point flagged back with an explicit risk statement rather than assumed — full
touch drag/resize on mobile, the same as desktop, not a safer tap-based fallback, with the owner
choosing that knowing this app has a real, four-times-documented history of iOS-standalone-PWA-only
touch/scroll bugs that Chromium/Playwright has never once been able to reproduce. Planned (a Plan-agent
review, spot-checked directly against the actual code afterward rather than trusted blind) and approved
as two independent parts landing together.

**Part 1 — Action Buttons.** Two new block types, both `category: "action"`: **Navigate To…**
(`nav_button`, jumps to a module page or a specific record) and **Status/Archive Action**
(`status_button`, one click to mark a task done/pending/skipped, archive/unarchive a contact or asset,
or set one of an asset's own fields). Both resolvers are new, display-only backend code
(`services/dashboard_blocks/_actions.py`) — they exist purely to label the button (a record's name, its
current status) through the same read-through gate every other record-linked block already uses; the
actual write a click performs never runs through the dashboard at all.

- **The status/enum tension**: task `status` is a real fixed enum, trivially pick-based. Contact
  `status` turned out to be genuinely freeform text (`contacts_service.py`, `.strip()[:40]`, no enum) —
  can't be picked without typing, so excluded outright. Contacts get **archive/unarchive** instead: a
  clean zero-typing binary, and arguably the semantically-right "status" concept for a contact anyway.
  Assets get archive/unarchive *or*, since asset `select`-type template fields already carry their own
  `options: list[str]`, setting one of those fields to one of its own predefined values — also fully
  pick-based, via a new two-stage `AssetSelectFieldPicker.jsx` (pick the field, then one of that field's
  own options).
- **New generic mechanism, not a one-off**: `status_button`'s task/contact/asset branches need
  different config keys, not just different values under one key, so `BlockPicker.jsx` gained
  conditional field visibility (`showIf: {key, equals}`), filtering `CONFIG_FIELD_SCHEMAS` entries
  before rendering. No new picker `kind`s were needed for the enums/toggles themselves — the existing
  generic `select` with a static `options` array already covers those — only two genuinely multi-stage
  composite pickers were new: `ModuleAndRecordPicker.jsx` (nav_button's target: pick a module, then
  optionally a specific record via whichever of the 7 existing pickers matches) and the asset-field one
  above.
- **The security call — no new unified write endpoint.** `status_button`'s click calls each target
  module's own existing, already-differently-gated endpoint directly from the browser's own session —
  `tasksApi.update`, `contactsApi.archive/unarchive`, `assetsApi.archive/unarchive/update` — verified
  against the real gates first: contact archive needs strict `edit`, asset archive needs the stricter
  `can_manage`, asset field-set is capped by `caps.fields` for contribute-level access and re-validated
  server-side against the template's own `options` regardless. Building a `/dashboards/...` unified
  action endpoint would have meant duplicating or reimplementing every one of those thresholds — the
  kind of knowledge that rots the moment it exists in two places. Calling the real endpoint directly
  means the dashboard's own access model and its `share_underlying_data` toggle are structurally never
  in the write path at all — correct for free, nothing new to keep in sync. Recorded as a standing
  design rule in `docs/MEMORY.md` Core Design Decisions, not just a one-off choice for this feature.
- **A real gap found while building nav buttons, not before**: checked all seven modules with an
  existing picker for actual deep-link handling before assuming it existed everywhere — only Assets,
  Contacts, and Finance actually read their `?asset=`/`?contact=`/`?book=` query param
  (`useSearchParams`); Tasks, Calendar, and Notes had zero handling despite already having the matching
  modal-open state to land on. Added the same `useSearchParams` → find-in-list → open-modal →
  strip-param `useEffect` pattern to all three (`?task=`, `?event=`, `?path=`), mirroring `Assets.jsx`
  exactly rather than inventing a second convention. Automations stays module-page-only in this pass —
  it has no per-workflow detail view to land a deep link on yet. Pulled the URL-building rule itself
  into one shared `lib/deepLinks.js` (`deepLinkUrl(module, recordId)`) so `Layout.jsx`'s notification-bell
  `navTarget()` and the new nav-button picker both build URLs the same way instead of two conventions
  that could drift apart later.
- **First write-capable block in an otherwise entirely passive system** — needed real click feedback,
  not a silent no-op. New `StatusButtonBlock` in `blocks.jsx` runs an idle → "Working…" → "✓ Done" /
  real-error state machine (no confirmation dialog — archive/unarchive is symmetric and reversible,
  unlike delete, and a single click is the explicit point of the feature). A successful click threads an
  `onAction` callback up through `BlockRenderer.jsx` → `DashboardGrid.jsx` → `Dashboard.jsx`, which
  refetches the dashboard the same way `saveBlocks()` already does — so the button's own state reflects
  reality immediately instead of needing a manual refresh. `NavButtonBlock` stays passive, reusing the
  existing `LinkedContactBlock` link pattern.

**Part 2 — Full mobile editing.** Reading `DashboardGrid.jsx` closely before touching it turned up the
real finding: the `sm` breakpoint layout was **hardcoded to always auto-stack**
(`sm: blocks.map((b,i) => ({x:0,y:i*9,w:2,h:9,...}))`), silently ignoring any saved `b.layout?.sm`
entirely — the per-block mobile slot has existed in the data model since Custom Dashboards first shipped
on 2026-08-04, it had simply never once been read. Fix was mechanical once that was clear: `cols.sm`
2→12 (checked the resulting column width lands in the same ballpark as desktop's ~28px/col at a
~1024px cap — 12 cols over a 375–414px phone is ~31–35px/col), `sm` now genuinely reads/writes
`b.layout?.sm` the way `lg` already did, and the `!isMobile` conditions gating `isDraggable`/
`isResizable`/the drag-handle class are gone — which also made the `isMobile` state, its resize
listener, and the `MOBILE_BREAKPOINT` constant dead code, removed rather than left dangling.
`MOBILE_COLS` is now exported so `Dashboard.jsx`'s `addBlock()` sm default imports it instead of
re-hardcoding the number a second place.

- **A second migration, different reasoning than `m011`.** Every stored `layout.sm` predates `sm` ever
  being read, all at the old `w:2` scale — at `cols.sm:12` that renders as a ~17%-width sliver until
  someone happens to re-edit on mobile. The plan's first-pass suggestion was a straight ×6 multiply
  (mirroring `m011`'s ×3 for the desktop rescale), but that turned out to be wrong once traced through
  carefully: `m011` had *already* blindly multiplied every stored `sm.w` by ×3 earlier the same day even
  though `sm` was never read at the time, so by the time `m012` runs, a given stored `sm.w` could be `2`
  (never touched), `6` (a dead-data artifact of `m011`'s own blind multiply), or something else again if
  a block was added via the UI between deploys with an unfixed default — three possible provenances with
  no reliable way to tell which applies to a given block. `m012_rescale_dashboard_mobile_grid_units`
  **normalizes** instead of multiplying — unconditionally sets `x:0, w:12` — which is correct regardless
  of prior provenance, and, as a bonus `m011` doesn't have, genuinely idempotent. Same three-places-move-
  together rule as `m011` applied here too: `Dashboard.jsx`'s `addBlock()` sm default and
  `dashboards_service.py`'s `_validate_blocks()` sm fallback both moved `w:2→12` alongside the migration
  itself.
- **Touch-scroll risk stated plainly, not softened.** `react-draggable`/`react-resizable` already attach
  touch listeners out of the box, so nothing is structurally broken by dropping `!isMobile` — but a
  `touchstart` on a drag handle is inherently ambiguous between "start a drag" and "the browser's own
  scroll," precisely the bug class `docs/MEMORY.md` documents four separate times on this exact app,
  never once reproducible in Chromium/Playwright, every past fix needing real on-device confirmation
  regardless of how clean an automated pass looked. Added the standard mitigation proactively —
  `touch-action: none` on `.block-drag-handle` and `.react-resizable-handle` — but said so directly
  rather than implying it's settled: **real on-device iOS PWA verification is the one item this pass
  could not close**, and no tool in this environment can close it.

**Bugs hit while building, worth recording**: (1) an `Edit` meant to insert the new `m012` test right
after the existing `m011` test instead orphaned `m011`'s own trailing idempotency-check lines outside
any function entirely, producing `NameError: name 'm011_rescale_dashboard_grid_units' is not defined` —
caught by the test run itself, fixed by moving those lines back inside `test_m011_rescales_existing_dashboard_grid_units`
rather than leaving a duplicate at the end of the new test. (2) Verifying the action buttons hit the
same drag-handle/Playwright friction noted for drag-and-resize earlier today, in a new form: a button
rendered inside `.block-drag-handle` had its simulated click silently swallowed, because
`react-grid-layout` interprets Playwright's synthetic mouse-move-then-click as a drag attempt. A raw DOM
`.click()` bypass proved the underlying app logic was already correct, and the real verification pass
was done clicking outside edit mode instead — which is also the actual, realistic way anyone would use
an action button day-to-day.

**Verification**: full backend suite 555 passed (2 pre-existing, unrelated `test_ai_usage_service.py`
UTC-day-boundary flakes deselected — same known issue documented in the 2026-08-04 note, not touched
this session), `npm run build`/lint clean. Isolated backend + synthetic brain + Playwright (same
methodology as every round today) confirmed both new blocks against real effects, not just UI state: a
`status_button` click genuinely flipped a real task from `pending` to `done` with `completed_at` set,
verified via the actual `PATCH /tasks/{id}` response and a follow-up `GET`, not just the button's own
"✓ Done" text; a `nav_button` click genuinely navigated to and opened the correct asset's detail modal
through the real deep-link mechanism; a mobile-viewport (390×844) resize gesture was confirmed to
actually change the saved `layout.sm` values via the API, even though the *feel* of a touch gesture
itself isn't something any tool here can judge.

## Sixth follow-up round, same day: press-and-hold to drag on mobile, and bare-pill action buttons

Owner tried the mobile editing + action buttons from the round above and came back with two more
refinements: "the mobile drag portion would be good to restrict it to press and hold for a few
seconds before opening the move feature. so users can still swipe the whole screen to scroll while
in edit mode," and the action buttons should be "a tiny button only block. no other text or
anything only the pill button so there can be many of them added on a small space." Their message
cut off after "also" with nothing following — flagged back rather than guessed at, in case there
was a third item.

**The real problem, found by reading `DashboardGrid.jsx` again**: "full parity with desktop" meant
the entire block card was the drag surface (`draggableHandle=".block-drag-handle"` on the whole
wrapper div), and `touch-action: none` was applied unconditionally to make touch dragging work at
all — which also meant *any* touch on a block while editing, including a plain scroll swipe, was
captured as a move attempt. The obvious-looking fix — start a timer on `touchstart` and flip
`isDraggable`/`disabled` to `true` once it fires — turned out to be a dead end: reading
`react-draggable`'s actual source (`node_modules/react-draggable/build/cjs/Draggable.js`) confirmed
`DraggableCore.handleDragStart` checks its `disabled`/`handle` props exactly once, synchronously, at
the real `touchstart` DOM event, and only *then* attaches the document-level `touchmove`/`touchend`
listeners that do the dragging. Flipping a prop later, mid-gesture, does nothing — there's no second
`touchstart` for it to re-evaluate against. That ruled out every "just delay enabling it" approach
and meant touch dragging had to be taken over entirely, by hand, rather than tuned via a prop.

**What shipped** (`DashboardGrid.jsx`): a single delegated `touchstart` listener on the grid
container, registered in the **capture phase**, calls `e.stopPropagation()` for every touch landing
on `.block-drag-handle` (skipping `.react-resizable-handle` — resize is untouched, its own touchstart
was never ambiguous with a scroll the way dragging the whole card was). Capture-phase on an ancestor
is enough to keep `react-draggable`'s own listener — bound to the grid-item node itself — from ever
seeing the touch, on any device; mouse is completely unaffected since only `touchstart` is
intercepted. In its place: a plain 550ms hold timer with a 10px movement tolerance. Move past that
tolerance before the timer fires and the gesture is abandoned untouched — critically, `preventDefault`
was never called during that window, so the browser's own native scroll (never blocked, since
`touch-action` on `.block-drag-handle` is no longer unconditionally `none`) takes over exactly as if
JS wasn't involved at all. If the hold completes, the block "arms" — `touch-action` switches to
`none` for that one block only, via a CSS class driven by React state, which is safe to flip at that
exact moment specifically because the finger has necessarily been still through the whole hold, so no
native scroll has started yet to interrupt — and further movement drives a CSS `transform` "ghost
drag." That transform has to live on an *inner* wrapper, not the grid-item root: `react-grid-layout`
clones that exact node every render and overwrites its own `transform`/`width`/`height`/`position`
via inline style (`GridItem.createStyle()`, confirmed in `node_modules/react-grid-layout`) — putting
the offset there would just get silently clobbered. The real grid position is only computed
(px→column/row via the same formula `react-grid-layout` itself uses, confirmed against its source)
and committed — with a manual bounds + overlap check mirroring `preventCollision` — on release,
through the exact `onLayoutChange` shape `Dashboard.jsx` already consumed, so no parent-side changes
were needed.

**Action Buttons → bare pills**: `blockRegistry.js` entries can now set `chromeless: true`;
`BlockRenderer.jsx` checks it and skips the card/header wrapper entirely for that type, replacing it
with a small absolutely-positioned ✎/✕ overlay while editing — the only remaining way to configure or
remove a block that has no header row. `NavButtonBlock`/`StatusButtonBlock` moved onto a new
`.btn-pill` class (always fully rounded — `border-radius: 9999px` regardless of the user's
corner-style theme setting, since the pill shape itself is the point) and `StatusButtonBlock` dropped
the record-title line it used to show above the button, moving that context into the button's own
`title` tooltip instead so the block really is just the button. Both blocks' default grid size
shrank to the grid's own `MIN_W`/`MIN_H` floor.

**Verification, and a real lesson about testing this kind of thing**: isolated backend + synthetic
brain + Playwright, this time driving raw touch input via CDP's `Input.dispatchTouchEvent` (Playwright's
own touchscreen API has no way to express "hold for N ms, then move," so this needed direct protocol
access). First full run showed 3 failures — a quick swipe not registering as a scroll, and the
long-press drag not arming at all — that looked like the mechanism was broken. It wasn't: both
failures were bugs in the *test*, not the app, and both are worth remembering. (1) The scroll check
read `window.scrollY`, but this app deliberately makes `<main>` — not `window`/`body` — the scrolling
element (the whole point of the iOS-PWA scroll-containment work documented elsewhere in this file);
checking `document.querySelector('main').scrollTop` instead showed the swipe scrolling the full
available range (0 → 199px) exactly as it should. (2) The long-press test ran right after the swipe
test, and the script clicked "Save Layout" in between (harmless, since nothing had actually changed)
to double check via a fresh load — except `saveBlocks()` calls `loadCurrent()`, and `loadCurrent()`
unconditionally calls `setEditing(false)` (`Dashboard.jsx`) on every reload. The save silently
exited edit mode, and the long-press test that followed was — correctly! — a no-op, because dragging
while not editing isn't supposed to work at all. Removing the unnecessary save (nothing had changed;
the API already confirmed that) made the long-press test pass cleanly: the block visually arms after
the hold, and a held-then-moved gesture produces a real, persisted `layout.sm.x` change matching the
drag direction. Desktop mouse dragging re-verified as a regression check (still instant, no hold
needed). Both pill blocks confirmed to render with no `.card` ancestor, a >9999px border-radius, and
the ✎/✕ overlay while editing, on both breakpoints. `npm run build` and eslint clean (0 new warnings
beyond this file's existing, pre-existing lack of PropTypes on every block component).

**Not verified, stated plainly, same as every mobile-PWA claim in this file**: how a real held touch
actually *feels* on iOS Safari standalone — whether 550ms reads as comfortable, and whether anything
here interacts with the documented scroll-hijack history elsewhere in this doc. Synthetic CDP touch
events proved the state machine and the persisted result are correct; they cannot judge feel, and
this app has been wrong about "should be fine" on iOS touch behavior before.
