### Item 2 — Dashboard: generic, user-built action buttons on any block

The largest dashboard change this pass, and the piece with the most existing precedent to reuse rather than
reinvent. Any block type opts in by declaring a `recordKind` (`task`/`asset`/`contact`/`event`/`note`, new
`actionKinds.js`) in `blockRegistry.js`; the user then authors `actions: [{id, kind: 'nav'|'status', ...}]`

not a per-block-type special case**: `shape: 'list'` blocks render the actions once per row (substituting
that row's own record id); `shape: 'detail'` blocks render them once against the block's single record — one
rule covers both of the owner's own named examples (a Notes block button that opens that note; an Assets
block button that updates status) without a single new per-module branch. `BlockActionButtons`/

logic, so a click still calls `tasksApi`/`assetsApi`/`contactsApi` directly from the browser — never a new
dashboard-owned write path, following this app's own standing design rule from the prior session.

No backend resolver changes were needed for the mechanism itself — `block.config` (including `actions`)
already shipped to the frontend in the render response before this change (confirmed by reading `render.py`
directly rather than assuming). What *did* need building: there was no general "list of contacts" block

**Circular-import fix**: `blockRegistry.js` imports render components from `blocks.jsx`, so `blocks.jsx`
can't import back from `blockRegistry.js` — but both needed the same action-kind/preset constants. Extracted

New tests added to `test_agent_dashboard_tools.py`, `test_dashboards_service.py`. **Verification gap, stated

### Item 0b — Push notifications: diagnose real delivery, don't rebuild what exists

Since Web Push already worked in the code, the actual investigation was "why might a real device not be
receiving it." Most likely cause found: `VAPID_SUBJECT` (`config.py`) defaulted to the placeholder
`"logcore@localhost"` and was never exposed as a real env var anywhere — some push services (Apple's
included) can reject a send whose VAPID `sub` claim isn't a real `mailto:`/`https:` URI. Fixed the config gap
(`docker/.env.example` now documents `VAPID_SUBJECT`; `_build_vapid_jwt` only prepends `mailto:` if the
configured value isn't already a URI) and the diagnosis gap (`POST /push/test` now returns a distinguishable
`400` "no subscription on file" vs `502` "push service rejected or failed the send" instead of a collapsed
generic error, so future diagnosis doesn't need shell/log access). **Explicitly not done this pass**:
removing ntfy or touching `docker-compose.yml`'s `depends_on` — the owner's own answer made that
conditional ("if we can do that then we can consider removing it"), a decision for once delivery is
confirmed working on a real device, not something to build blind now. New `test_push_service.py` (5 tests).
**Cannot be closed out from this environment** — confirming actual arrival on the owner's own iPhone needs
their real device; logged in `docs/TASKS.md`.

**Files:** `app/backend/services/push_service.py`, `app/backend/config.py`, `docker/.env.example`,

### Item 6 — AI Chat: background execution + full multi-conversation UI

The largest single piece of this pass — comparable in size to the Custom Dashboards module itself.
Confirmed the load-bearing facts before designing anything: no `AbortController` exists anywhere in the
frontend (an in-flight `/chat` request is never client-cancelled by navigation), and Starlette doesn't
auto-cancel a handler on client disconnect by default — so `POST /chat` deliberately **stayed fully
synchronous** rather than becoming a fire-and-forget/polling architecture; going genuinely async would have
meant solving orphaned-run cleanup as a brand-new problem for no real UX gain, since "background" is fully
satisfiable by state management alone.

**The mechanism**: every conversation gets a stable `chat_id` (`crypto.randomUUID()`, minted client-side the
moment a genuinely new conversation starts), now **required** on `ChatRequest`. A new workspace-scoped
session index, `USERS/{name}/agent/chat_sessions.json` (`agent_service.py`: `load_sessions`/`get_session`/
`upsert_session`/`mark_session_read`/`delete_session_by_filename`, capped at 50, most-recent-first — the same
convention `runs.json` already used), tracks `status` (`idle`/`running`/`awaiting_approval`/`awaiting_answer`)
+ `unread` + a preview per conversation. `routers/chat.py` computes `effective_workspace` once right after
`resume_payload` resolution and threads it through every session call — **caught mid-implementation**: the
session functions initially took a bare `user_name` like `runs.json`'s helpers do, but chat archives
themselves live under `ws_path(...)/Chats/`, so an un-scoped index could point one `chat_id` at two different
physical files if the workspace changed mid-conversation; fixed before writing any tests by re-deriving every
session function to take `workspace` explicitly. The handler marks the session `"running"` before calling
`run_agent()`, resets it to `"idle"` on an unhandled exception (so a crash never leaves it stuck), and calls
`notify_user()` unconditionally on success — this doubles as the "last opened chat" pointer the owner asked
for (most-recent `updated_at`), so no separate pointer file was needed.

**Frontend**: `Chat.jsx`'s "Chats" button/drawer stays exactly where it was (owner's explicit instruction) but
now reads `GET /chat/sessions` and opens a conversation directly on click — the old two-step
history-preview-then-"Continue →" flow is gone. Each row shows an active indicator (`status: "running"`) and
a distinct unread badge, cleared via `POST /chat/sessions/{chat_id}/read` on open. Message state is keyed by
`chat_id` (`chatIdRef` mirrors `chatId` state for stale-closure safety inside async callbacks), with a
`loadingIds: Set<chat_id>` tracking which conversations are actively running — so switching to a different or
brand-new conversation never blocks on one still working, satisfying "multiple at once." `newChat()` is the
one and only thing that starts a conversation over, matching the owner's explicit instruction that closing/
reopening the app should reopen the last chat, not reset to blank.

**Caught via direct code review before running tests**: an early draft of `routers/chat.py` only defined
`datetime`/`ZoneInfo` imports inside the `else` branch of an `if existing_session` check, then referenced a
nonexistent `_dt_now_iso()` helper unconditionally later — fixed by moving the imports/timestamp computation
to the top, unconditional, right after `resume_payload` resolution.

New `test_chat_sessions.py` (12 tests) — calls the real router `chat()` function directly with
`agent_completion` mocked, so the "mark running → reset on exception → notify on success" flow is genuinely
exercised, not just each helper in isolation. **Verification gap, stated honestly**: the actual AI-response
flow (a session reacting to a real completion) could not be live-browser-tested at all in this environment —
no Anthropic API key available, the same limitation noted earlier this week — so confidence here rests on
the 12 backend tests plus a confirmed-working UI shell (drawer renders, rows navigate, active/unread styling
correct) from an isolated instance.

**Files:** `app/backend/services/agent_service.py` (new session-index functions), `app/backend/routers/
chat.py` (substantially restructured — new `_write_chat_archive()` helper, required `chat_id`, new `GET
/chat/sessions`/`POST /chat/sessions/{chat_id}/read`), new `app/backend/tests/test_chat_sessions.py`,

## Real-instance outage: `ALLOWED_ORIGINS=*` refuse-to-start guard had no migration path for existing installs

Owner relaunched their own real, already-deployed instance (domain on file in `brain/hosting.json` — not
named here, see the standing no-tenant-details rule in `docs/MEMORY.md`) after the pass above installed new
frontend dependencies — the app came back
completely unreachable, on localhost and the tunnel both. Not a Docker-permission environment here (no
`docker` group membership, no passwordless `sudo` in this sandbox — confirmed both, ruling out direct
`docker compose logs` as an option), so diagnosis had to work from what was readable: `ss -tlnp` showed
port 8000 never listening at all (`ntfy`/`n8n` were both up), which pointed at the app container failing
during startup rather than merely misconfigured. `docker/.env` had `ALLOWED_ORIGINS=*` — the exact
condition `main.py::_startup_checks()` (shipped 2026-08-12, see `docs/MEMORY.md` rule 4a) `sys.exit(1)`s
on. Fixed the instance directly by setting `ALLOWED_ORIGINS` to the real domain already on file in
`brain/hosting.json`'s `domain_url`, then handed the actual container recreation back to the owner (no
Docker access from here): `docker compose -f docker/docker-compose.yml up -d app`.

**Owner then asked the real question: how do all the *other* instances get fixed after their updater
relaunches them?** Traced both restart paths in the actual scripts rather than assuming:
- `docker/update.sh`'s `compose_up()` → `wait_healthy()` (120s) → on failure, automatic
  `git reset --hard` to the previous commit + rebuild. So an auto-updating instance genuinely never goes
  *down* over this — but it also means it silently re-installs the same pre-2026-08-12 commit forever,
  since the new commit's health check will keep failing for the same reason every single time. No signal
  to the operator that anything's wrong beyond an update that never seems to "take."
- `launch.sh`'s `main()` only ever writes `ALLOWED_ORIGINS` inside `generate_env()`, which is gated on
  `docker/.env` not existing yet — for any pre-existing install (i.e. literally every instance that existed
  before 2026-08-12) it hits the `else` branch (`"docker/.env exists — skipping setup"`) and never touches
  the file. `wait_for_health` just warns and exits 0 regardless. No rollback, no fix, just an outage —
  exactly what happened here.

So the honest answer was: **nothing fixes it automatically today.** Every instance still on the old default
is one relaunch away from either this exact outage or a silently-stalled updater, and this was a real,
un-tracked gap in the 2026-08-12 hardening pass, not a one-off. Owner said to fix it and log it.

**The fix**, mirroring `sync_tunnel_token()`'s existing exact shape (already reads `brain/hosting.json` and
writes into `docker/.env` for an existing install — so this isn't a new pattern, just a second use of one
already proven): new `migrate_insecure_cors()` in both scripts. If `ALLOWED_ORIGINS` is still `*`, auto-set
it from `hosting.json`'s `domain_url` when one's on file; otherwise print the actual cause and the fix
instead of a generic timeout. Wired into `launch.sh` right after `sync_tunnel_token()` (before
`launch_containers`) and into `update.sh` at the very top of `do_update()` (before the backup/fetch/rebuild
steps, so a real update actually lands instead of failing its health check and rolling back again).
Smoke-tested the actual `env_get`/`env_set`/`sed` logic against throwaway scratch copies of `.env` +
`hosting.json` for both scripts' code shapes before trusting it, confirmed both produce the identical
correct result, then confirmed it against this real instance's already-fixed `.env`/`hosting.json` pair
(same domain, so the migration is idempotent/no-op there now).

**Residual gap, stated plainly rather than overclaimed**: this doesn't retroactively unstick an instance
already caught in the auto-updater's rollback loop — that instance is still running the *old* `update.sh`
(the rollback resets the whole repo, migration function included), so the fix has to land via one manual
`git pull && bash launch.sh` (or a one-line `docker/.env` edit) before it can start applying itself on every
run after that. Logged in `docs/MEMORY.md` rule 4a's entry rather than `docs/TASKS.md`, since there's
nothing left to schedule — it's fully shipped, just not silently retroactive.

**Files:** `launch.sh`, `docker/update.sh`. `bash -n` syntax-checked both; no `shellcheck` available in this
environment. `docs/MEMORY.md` (extended rule 4a), `CHANGELOG.md` (new `[0.6.0]` Security bullet), this file.
Uncommitted, same standing rule as above.

## Live bug-report round two: 6 reported bugs + 2 mid-turn adds, all on the real instance this time

Owner reported 6 more issues after actually using the real (now-reachable) instance on a phone: the image
lightbox not centered for square images, AI Chat not reloading the last chat on workspace switch, the Chat
composer not rising above the keyboard, push test returning a real 502 now (progress from last round's
crash), Finance transfers auto-popping the number keyboard, and transfer deletion still not removing both
sides. Mid-turn, two more landed: "the ai chat is supposed to save the approve, askuser, and all those
things" (a real, previously-logged TASKS.md backlog item — interactive cards not persisting across a
reload) and a scrollbar sitting partly behind page content on mobile.

**Lightbox centering** — `.modal-overlay`'s `items-end md:items-center` (a deliberate bottom-sheet-on-mobile
treatment for *forms*) was being reused for the image lightbox, so a square/non-tall image sat in the bottom
half of the screen on mobile instead of centered. Gave the lightbox its own always-`items-center` overlay
instead of reusing that class — a photo viewer should always be centered regardless of viewport size.

**Chat workspace-switch not reloading the last chat** — traced to two compounding bugs in the
background-multi-chat work from earlier today. First: the `useEffect(..., [workspace])` that's supposed to
reset the conversation on a *real* workspace switch also fires once after the initial render (a
dependency-array effect always does), so it was wiping the just-restored chatId/messages on every single
mount before they ever reached the screen — fixed with a `useRef` first-run guard. Second: the "last chat"
localStorage pointer was a single global key, not scoped per workspace, so even once the mount-wipe bug was
fixed, switching workspaces still always landed on a blank chat rather than that workspace's own last
conversation (a chat_id belongs to exactly one workspace's Chats/ folder). Fixed by keying the pointer
`lc_chat_last_id_${workspace}` and extracting the restore logic into one `restoreForWorkspace(ws)` function
called from both the mount effect and the (now correctly guarded) workspace-switch effect.

**Chat composer not rising above the keyboard** — root cause: Chat.jsx's own page container isn't the actual
scrolling element — Layout.jsx's `<main>` is (`overflow-y-scroll`) — so the composer, a plain flow child,
only stayed "at the bottom" when `<main>`'s scroll position happened to already rest there; focusing the
textarea and triggering the keyboard could leave it scrolled such that the composer sat below the visible,
keyboard-shrunk viewport. Changed to `sticky bottom-0` against `<main>` — pins it to the real scrolling

## Round five: a third attempt at the keyboard problem, this time built to not need the same assumption

Owner's own idea, in response to the round-four investigation report: "what if we only make the box itself
move up when the keyboard goes up?" — i.e., stop trying to make the whole page resize correctly and instead
directly measure and compensate for the keyboard on just the one element that needs it.

This is a materially different approach from both prior attempts, not a variation on either: attempts 1 and
2 both assumed the *page* would resize correctly in response to `interactive-widget=resizes-content` and
tried to make the composer sit correctly *within* that assumed-correct resize. The investigation last round
found real reasons to doubt that assumption held on the owner's device at all (the `html`/`body` oversizing
hack, the Safari 17.4 version-support question). This attempt sidesteps needing the assumption to be true:
a new `useEffect` in `Chat.jsx` reads `window.visualViewport.height`/`offsetTop` directly (supported since
iOS 13, long before `interactive-widget`) and computes `window.innerHeight - (vv.height + vv.offsetTop)` —
the actual gap between what the page's own layout claims is visible and what's really visible right now —
then applies that as a `transform: translateY()` directly on the composer via a new `composerRef`. This is
self-adapting: if the page-resize assumption *does* hold, `window.innerHeight` shrinks in step with the
visual viewport and the computed gap is ~0 (correctly a no-op); if it doesn't, the gap correctly equals the
real keyboard height regardless. Deliberately scoped to `Chat.jsx` alone, not `Layout.jsx` — a mistake here
can't spread to Notes the way attempt 2's shared-layout change did.

**Verified what's mechanically verifiable, honest about what isn't.** Spun up another isolated instance
specifically to confirm the wiring actually works: the effect mounts with zero console errors, `composerRef`
resolves to the one real `<textarea>` on the page (confirmed no selector ambiguity), and manually driving
the exact transform the effect would compute produces the correct `matrix(...,-300)` and cleanly resets to
`none` (had to add a short wait after each style write the first time — the composer's own CSS transition
was catching mid-animation reads on the first attempt, giving misleading intermediate values, not a real
bug). What this does **not** and cannot verify: Chromium has no real on-screen keyboard and doesn't decouple
`window.innerHeight` from `visualViewport.height` the way an actual device does, so the live
`resize`-event-driven trigger path itself — the part that actually matters — is still unverified against
real hardware. Same fundamental limitation as both prior attempts; stated plainly rather than glossed over.

## Round six: real-device feedback on attempt 3 — window.innerHeight wasn't a reliable reference at all

First real feedback from an actual phone: "that fix kinda worked... most of the time it didn't do anything.
sometimes it will move only that box up and it will be way above the keyboard. other times it will move
the whole page up footer and all." Genuinely useful signal, not just "still broken" — three distinct
symptoms map cleanly onto three distinct ways `window.innerHeight` can mislead the gap calculation:

- **"Most of the time nothing happened"** — presumably the cases where iOS's own native behavior (a real
  resize, or scroll-into-view) already revealed the composer correctly; `window.innerHeight` shrinking in
  step with `visualViewport.height` correctly computed a ~0 gap. Not actually a bug in these cases.
- **"Sometimes moved way above the keyboard"** — attempt 3's formula assumed *the entire* keyboard-covered
  height needed compensating, when in fact only *part* of the composer might have been hidden (e.g. if
  native behavior already handled most of it, or the composer sits higher up than the very bottom edge) —
  a flat "full keyboard height" correction overshoots whenever the true overlap is smaller than that.
- **"Other times moved the whole page up, footer and all"** — iOS natively panning the entire visual
  viewport (this app's `position: fixed` body means a native pan visually shifts everything, footer
  included, as a unit) — attempt 3's correction then stacked ON TOP of that native pan instead of accounting
  for it, since `window.innerHeight` gave no signal that the native pan had already happened.

**Root cause, in one line:** `window.innerHeight` is not a reliable "what should be visible" reference on
real mobile Safari — it can lag, stay unchanged during a pure pan, or simply not reflect what the browser
actually did. Every one of the three symptoms traces back to trusting it.

**Attempt 4 drops `window.innerHeight` entirely**, replacing it with a direct, same-coordinate-space
comparison: `composerRef.current.getBoundingClientRect()` (layout-viewport-relative, unaffected by a native
pan) against `visualViewport.offsetTop + .height` (the actual current visible area, also layout-viewport-
relative). The gap between them is exactly how much of the composer is hidden *right now*, regardless of
whether that's from a resize, a pan, or native scroll-into-view already having done some of the work.
Whatever transform is already applied gets added back onto the freshly-measured `rect.bottom` before
comparing (since the rect reflects the post-transform position) — this is specifically what makes it
mathematically incapable of double-compensating on top of a native pan the way attempt 3 could.

**Verified the formula itself in isolation** (pure math, not a live DOM) against four scenarios modeling
all three reported symptoms plus a clean keyboard-close retract — each computes the mathematically correct
result. Also re-confirmed the mechanical mount check (no console errors, composer ref resolves correctly)
in a fresh isolated instance. Same fundamental limitation stated again, not glossed over: Chromium has no
real on-screen keyboard and can't reproduce iOS's actual inconsistent behavior, so the live trigger path
itself is still unverified — this is genuinely iterative, real-device-feedback-driven debugging, and each
round narrows the gap between "verified mechanically" and "actually correct," not a guarantee of the latter
without another round of the owner's own testing.

own) — technically correct math, visually still broken. Attempt 5 keeps attempt 4's proven-correct gap
formula (still measured from the composer's own position, since it's still the element that has to clear
the keyboard) but applies the resulting transform to the whole page's top-level container instead —
`composerRef` demoted to measurement-only, new `pageRef` holds the actual transform. The bottom tab bar
needed zero special handling: it's rendered by `Layout.jsx` entirely outside this page, so shifting Chat's
own container never touches it — the keyboard just covers it once it's tall enough, which is exactly the
owner's own framing of the fix.

**Caught a real regression before shipping, same class of bug as the image lightbox earlier this session.**
The Chats drawer (`fixed inset-0 z-50`) was a descendant of the same container now getting the transform —
`transform` creates a new containing block for `position: fixed` descendants, so the drawer would have
rendered relative to the shifted page instead of the true viewport the instant a keyboard-driven shift was
active. Restructured the component's return into a fragment with the drawer as a sibling of the transformed
container, not a child. Verified mechanically: opened the drawer, applied a manual shift to the page
container, confirmed the drawer's `getBoundingClientRect()` still exactly matches the true viewport
regardless (`{top:0, left:0, width:390, height:844}` matching the real viewport size in the test).

**Owner's live real-device report, mid-verification: "it seems to work most of the time."** Genuinely
different from every attempt before it — the first time any attempt has been reported as more-right-than-
wrong rather than fully broken. Owner's own follow-up suspicion for the remaining rough edge: "it may be a
good idea to restrict all scrolling while the keyboard is up for chat.js" — the messages list's own scroll
plausibly interacting with the keyboard-driven reposition, since `visualViewport` fires both `resize` and
`scroll` events and a user scroll gesture on the messages list while the keyboard is up could trigger a
spurious recompute mid-gesture. Added `keyboardOpen` state (derived from the same `reposition()` call that
already knows whether a shift is currently active) that swaps the messages container from `overflow-y-auto`
to `overflow-hidden` while the keyboard is up — chosen specifically because `overflow-hidden` only disables
scroll *input*, it doesn't reset `scrollTop`, so the exact prior scroll position returns once the keyboard
closes and `overflow-y-auto` comes back.

## Round eight: attempt 5 + scroll-lock made things worse on the real device — reverted all JS transform code (attempt 6)

Owner sent a real-device screenshot of the Chat page with the keyboard open: the composer was sitting well

**Root-cause theory.** `index.html`'s viewport meta already declares `interactive-widget=resizes-content`
(added earlier this session — see the Round with the "check deeper, don't change it" investigation). On
Safari 17.4+, that makes the browser shrink the *layout* viewport itself when the keyboard opens — this
page's own `flex flex-col flex-1 min-h-0` layout would already reflow to fit above the keyboard with zero
JS. Attempt 5's `reposition()` was computing and applying an *additional* shift on top of whatever the
native resize already did, using `getBoundingClientRect()` vs `visualViewport` — both of which would
already reflect the *post-native-resize* state once the browser catches up. If `reposition()` ran on a
stale read (before the native reflow fully settled) or simply computed a shift on top of an already-correct
position, the two corrections stack — which matches the observed overshoot (dead space exactly where the
native resize had already made room) precisely. The scroll jitter is consistent with the same
double-correction compounding on every `visualViewport` `scroll` event, which fires during ordinary
scrolling, not only keyboard transitions.

**Five attempts of guessing without being able to see the real device is enough** — each guess this session
has either not fixed the original problem or introduced a new one. Rather than build a sixth guess on top of

no JS positioning of any kind — this now tests the native `interactive-widget=resizes-content` behavior in
total isolation, which none of attempts 3-5 actually did (their own JS was always layered on top, masking
what the native behavior alone does). Kept the Chats-drawer fragment/sibling restructuring from attempt 5 —

no transform currently applied.

## Round nine: attempt 7 (owner's idea — scroll the composer into view instead of computing a transform)

Owner's next idea, right after attempt 6's revert: "what about just making the page auto scroll to the
bottom when the keyboard is open?" A fundamentally different mechanism from every attempt since 3 — instead
of measuring a gap and applying it via `transform` (a value our own code captures once and can get stale or
stack on top of a native correction it doesn't know already happened — exactly what broke attempt 5), just
ask the browser to scroll the composer into view. `composerRef.current.scrollIntoView({ block: 'end',

composer's bottom edge flush with the bottom of the visible area is exactly "scroll to the bottom" for this
layout. Idempotent when already in view, so firing on keyboard-close too is harmless — no state, no
scroll-lock, no math to get wrong.

Re-added a `composerRef` (removed in attempt 6) purely as a `scrollIntoView` target — no transform applied
to it or anything else this time.

## Round ten: attempt 7's smooth scroll caused a cooldown + glitch — switched to instant scroll

Owner's real-device report: attempt 7 worked on the first keyboard open, but closing and reopening the
keyboard within roughly 10 seconds left it not working again — "like its on cooldown which it shouldnt be."
Separately (owner explicitly flagged as probably unrelated, "just saying if its fixable"): "the entire page
glitches down all of a sudden when the keyboard opens."

Both point at `behavior: 'smooth'`. WebKit has a known quirk where a `smooth` scroll on a container,
interrupted by another scroll command before its animation finishes, can leave that container refusing new
scroll commands for several seconds until the stale animation resolves — a near-exact match for the
"cooldown" symptom (close then quickly reopen = a second resize event landing mid-animation). An animated
scroll racing the browser's own native scroll-into-view-on-focus behavior (which fires on its own the moment
an input is focused, independent of our code) is also exactly what a visible glitch/double-jump would look
like — so despite the owner's own hunch that the glitch was unrelated, it's plausibly a side effect of the
same `smooth` option. Changed `scrollIntoView({ block: 'end', behavior: 'smooth' })` to
`behavior: 'instant'` — removes the animation entirely, so there's nothing to get interrupted or race
against. Also objectively better UX for this case regardless of the bugs: the composer should snap into
place as the keyboard appears, not glide.

### Verification

`npm run lint` and `npm run build` both clean.

### Honest caveat, logged in TASKS.md

If the cooldown persists even with instant scroll, the next most likely explanation is a different, harder
problem: a WebKit quirk where `visualViewport`'s `resize` event itself doesn't fire reliably after rapid
focus/blur cycles, independent of what our handler does with it. That would need a debounced poll rather
than a pure event listener to work around — a real architecture change, not a one-line tweak — so flagged
now rather than discovered later if this round doesn't fully resolve it.

**Files:** `app/frontend/src/pages/Chat.jsx` (`behavior: 'smooth'` → `'instant'`). Docs: `docs/MEMORY.md`

**Reasoned conclusion.** Safari already auto-scrolls a focused input into view natively, on its own, the

scroll shortly after Safari's own already ran — regardless of whether that second scroll animates
(`smooth`) or snaps (`instant`), two scrolls in sequence still look like a double jump. And `visualViewport`'s
`resize` event is a documented-flaky trigger on iOS — not guaranteed to fire on every keyboard open/close —
which lines up with "only works every few seconds" being about the event not firing every time, not about
anything our handler does once it does fire.
