# 2026-09-04

## AI Settings picker: fixed a real 502 the owner hit switching providers before saving

Owner reported, from real manual testing of the 2026-09-02 AI Settings overhaul: "after i hit load
models for anthropic it loaded them then after i switched to provider on the picker any other attempt
to load returns a 502 error."

Confirmed the root cause with the existing test suite before touching code, rather than guessing —
`test_load_models_never_leaks_a_different_providers_saved_key` already proved the exact failure shape:
switching the picker's provider without saving first, then clicking "Load Models" before typing a
fresh key, makes the cross-provider key-leak guard correctly withhold the old provider's key, but the
code then fell through to the openai-compatible branch's `key or "ollama"` fallback unconditionally —
meant only for genuine keyless local runners, but applied to every provider. A real cloud provider
(whichever one the owner switched to) rejects that fake `"ollama"` key, and the resulting auth failure
got caught by the broad `except Exception` and turned into an opaque 502 with no hint a key was ever
missing.

**Fix**: `load_models()` in `routers/ai_settings.py` now checks the catalog's `list_requires_key` field
right after resolving the key — `False` only for providers with a genuinely public/keyless model list
(local runners, OpenRouter) — and 400s with a clear "type an API key for X first" message instead of
ever attempting the request when no real key is available. Deliberately checked `list_requires_key`,
not `needs_api_key`: OpenRouter needs a key to chat but not to list models, so gating on the wrong field
would have broken its legitimately-keyless fetch. Applies to the Anthropic branch too, not just the
openai-compatible one.

Existing key-leak-guard test updated to assert the new 400 (a stronger proof than before — the fake
client is now never even constructed when no real key exists). Two new tests: one reproduces the exact
reported scenario end-to-end, one confirms genuine local runners (Ollama) are unaffected and still get
the placeholder fallback. 31 AI-settings tests passing, full backend suite reconfirmed clean, `black`/
`isort` clean. No frontend changes needed — the clearer message reaches the UI through the existing
`data.detail` → error-message plumbing already in place. See `docs/MEMORY.md`'s 2026-09-04 entry.

## AI Settings: 400 message clarified to say it's the provider's own requirement

Owner asked whether keyless model fetching was possible at all for providers that need auth, then:
"can you make that clear in the error for those providers that they require it not us." Confirmed first
(Q&A) that this was already provider-by-provider correct — OpenRouter and every local runner already
fetch without a key via `list_requires_key=False`; everything else needs one because that provider's own
`models.list()` endpoint is authenticated, not because of any policy LogCoreOS imposes.

Reworded the 400 from `routers/ai_settings.py`'s `load_models()`: now reads "{label} requires an API
key to list its models — that's a requirement of their API, not ours. Type one in above..." instead of
the more neutral "No API key available for {label}." Tests still pass unchanged (the existing assertion
only checks the provider's label appears in the message). `black`/`isort` clean.
