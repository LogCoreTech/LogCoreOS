## Two more real bugs found and fixed live against the real instance, with explicit authorization at each step

Owner deployed the boot-time fix above themselves and reported it still hadn't fixed anything. Owner
then explicitly authorized touching the real instance directly: "you are currently on my desktop...
run it, see if it actually repairs it, and try figure out why the other thing failed."

**Bug 1 — the boot-time jobs never actually fired, on any deploy, ever.** Got real `docker`/`exec`
access via `sudo -n -u "$(id -un)" docker ...` (the same trick `launch.sh` itself uses — re-exec as
self, not root, so PAM re-initializes docker group membership without a password). Proved with an
isolated marker job (no app code) that APScheduler's background thread was alive but never dispatched
anything, in the container specifically (identical test ran clean locally). `DEBUG` logging surfaced
the real number: a job set for 3 seconds out computed an 18000-second (5-hour) wait instead. Root
cause: all 5 boot-relative jobs used naive `_dt.now()` for their `run_date`, but they're registered via
the `"date"` string alias, which APScheduler auto-labels with `scheduler.timezone` (America/Chicago) —
mislabeling a UTC-valued naive clock reading instead of converting it. Fixed all 5 to
`_dt.now(scheduler.timezone)`. Verified twice against the real container with a throwaway seeded test
task (deleted after): broken before the fix (sat untouched through a restart), self-corrected
automatically after redeploying with the fix — no manual intervention. Full writeup in
`docs/MEMORY.md`'s own entry, including exactly why yesterday's own reasoning about these jobs being
"safe by design" was wrong.

**Bug 2 — the missed-task branch skipped today entirely, landing on tomorrow instead.** Owner caught
this directly after the manual data repair: "it updated but to the wrong day. It skipped today and
went to tomorrow." `recurring_service.py`'s missed branch called `next_occurrence(today, rule)` —
designed for chaining from a real prior occurrence, wrong here since today hasn't happened yet and can
itself be valid. Swapped in the already-existing `first_occurrence_on_or_after(today, rule)` instead
(built the prior day for a different purpose, already has the right inclusive semantics — no new code
needed). Two new tests prove the exact reported symptom. The 5 real tasks this had already mis-advanced
were individually corrected with a narrow, targeted script (matched only tasks carrying the specific
bad log entry from that exact repair run), not a blanket recompute.

**Real data directly repaired this session**, with authorization at each step: ran
`recurring_service.process_all_users()` straight against the real Brain (no Docker needed — `brain/` is
a plain bind-mounted host folder) to fix every real recurring task across both real family members'
accounts, twice — once for the general stale-data catch-up, once more narrowly after finding Bug 2.
Final state verified directly: all recurring tasks show correct due dates, no data loss (task counts
unchanged before/after).

## Two real IPs + a client's name found already leaked in git history — scrubbed

While writing up the above, noticed `docs/MEMORY.md` had briefly carried the demo host's real IP/SSH
details before being caught and sanitized (session memory, not this repo, is where that belongs — an
existing rule, re-confirmed). Checking further turned up something older and worse: two Daily Notes
from weeks ago (`2026-07-30.md`, `2026-08-22.md`) had the demo VPS's real IP, a real managed-hosting
client's server IP, AND that client's actual name — all **already pushed** to `origin/master`. Owner
was fine leaving the demo IP (public marketing infra, not sensitive) but wanted the client's IP+name
actually gone — "its not access for anyone. they just know it exists. and i can change it later."

Editing the current file isn't enough once something's pushed — still visible via `git log -p`. Ran
`git filter-branch --tree-filter '<sed script>' --prune-empty -- --all` (476 commits, every branch/tag)
replacing the client's IP and name everywhere; cleared the `refs/original/*` backup refs `filter-branch`
leaves behind and `git gc --prune=now` to actually drop the old objects, since a rewrite alone keeps the
originals fully intact and reachable through those. **Real near-miss along the way**: today's whole
uncommitted session (including 2 brand-new untracked test files) was stashed first for a clean tree —
`git stash push -u` — but `filter-branch`'s `--all` also rewrote `refs/stash` itself, and the stash's
untracked-files component didn't survive that cleanly. Both new test files vanished from disk after
popping the stash — caught immediately by checking `git status` right after, not assumed. Recovered
losslessly via `git fsck --unreachable --dangling` (gc hadn't swept the newly-unreachable blobs yet) —
grepped dangling blobs for known file content, `git cat-file -p <hash> > <path>` restored both files
byte-for-byte, confirmed via their own tests passing again unchanged. Lesson recorded in
`docs/MEMORY.md` for next time this comes up: exclude `refs/stash` from a `--tree-filter -- --all` run,
or save untracked work to a plain directory copy instead of trusting a stash to survive a concurrent
rewrite of its own ref.

`git filter-repo` (the modern replacement for `filter-branch`) wasn't installable here (no `pip` in
this environment) — `filter-branch` was the only viable built-in path. `/tmp` is mounted noexec here,
so the tree-filter had to be invoked as `bash <script path>` rather than relying on the executable bit.
Verified clean: `git log --all -S "<string>"` empty for both the IP and the name across every real
branch/tag/remote after cleanup; full backend suite still passing; formatting/lint/build all clean.
**Not pushed** — the rewritten history now diverges from `origin/master`, so publishing needs an
explicit force-push, deliberately held for whenever the owner is ready to push (they want more

## Fixed 2 flaky tests found while re-running the suite after the history rewrite

Full backend suite came back 1258/1260 right after the rewrite — the 2 failures
(`test_get_overview_sums_personal_and_business`/`test_get_user_rows_includes_every_registered_user` in
`test_ai_usage_service.py`) were unrelated to anything today (neither `ai_usage_service.py` nor
`auth_service.py` was touched this session, and both reproduce in complete isolation with nothing else
run). Root cause: both bucket a message/token write by `today_for_user()`, which falls back to UTC for
a test user with no real timezone set, then check the result against the test's own `date.today()`
(system-local) or `get_user_rows()`'s own `date.today()`-based default — the two disagree for a few
hours around UTC midnight in any timezone west of UTC, and the suite happened to run right in that
window tonight (19:32 CDT = 00:32 UTC, confirmed directly: local date `2026-08-31`, UTC date already
`2026-09-01`). An earlier test in the same file (`test_record_tokens_accumulates_personal_and_business`)
already had the correct fix for this exact issue with a comment explaining it — the two failing ones
just hadn't gotten the same treatment. Fixed identically: both now derive their own date/month
expectation via `today_for_user(USER)` instead of raw `date.today()`. All 21 tests in the file pass;
`black`/`isort` clean. `docs/TASKS.md`'s note on this removed now that it's fixed.
