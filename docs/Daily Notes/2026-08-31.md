## Recurring-processor boot-time run, closing the "restart still doesn't fix it" gap

Owner deployed last night's fixes (pushed + rebuilt themselves) and reported at 4:33am: the morning
notification still didn't send, and daily recurring tasks were still marked overdue with stale dates.
Correctly self-diagnosed: "now it's running right code but not fixed the issue itself yet... assuming
it will fix when it hits midnight again."

Confirmed against `recurring_service.py`: the self-heal logic for a stale/overdue recurring task
(logs a missed occurrence, advances the due date) already existed and was correct — it just only ran
via the nightly `_cron(hour=0, minute=1)` trigger, so a task that went stale while the app was down or
running old/buggy scheduling code would sit wrong for up to 24h after any restart.

**Fix**: `scheduler.py` gained a boot-time one-shot run of the same job (`id="recurring_boot"`,
`run_date=now()+15s`) — the same boot-then-periodic shape this file already uses for
`workflow_sync`/`simplefin`/`n8n_reconcile`. `process_user()` is idempotent (a task with nothing stale
is a no-op), so this can't double-process anything even landing right next to the nightly run. New
assertions in the existing `test_every_start_job_trigger_uses_scheduler_timezone` test confirm both
`recurring`/`recurring_boot` register. Full backend suite: 1248 passed.
