## Recurring-processor boot-time run, closing the "restart still doesn't fix it" gap

Owner deployed last night's fixes (pushed + rebuilt themselves) and reported at 4:33am: the morning
notification still didn't send, and daily recurring tasks were still marked overdue with stale dates.

it will fix when it hits midnight again."

Confirmed against `recurring_service.py`: the self-heal logic for a stale/overdue recurring task
(logs a missed occurrence, advances the due date) already existed and was correct — it just only ran
via the nightly `_cron(hour=0, minute=1)` trigger, so a task that went stale while the app was down or
running old/buggy scheduling code would sit wrong for up to 24h after any restart.

**Fix**: `scheduler.py` gained a boot-time one-shot run of the same job (`id="recurring_boot"`,

`workflow_sync`/`simplefin`/`n8n_reconcile`. `process_user()` is idempotent (a task with nothing stale
is a no-op), so this can't double-process anything even landing right next to the nightly run. New
assertions in the existing `test_every_start_job_trigger_uses_scheduler_timezone` test confirm both
`recurring`/`recurring_boot` register. Full backend suite: 1248 passed.

## Two more real bugs found and fixed live against the real instance, with explicit authorization at each step

Owner deployed the boot-time fix above themselves and reported it still hadn't fixed anything. Owner
then explicitly authorized touching the real instance directly: "you are currently on my desktop...
run it, see if it actually repairs it, and try figure out why the other thing failed."

**Bug 1 — the boot-time jobs never actually fired, on any deploy, ever.** Got real `docker`/`exec`
access via `sudo -n -u "$(id -un)" docker ...` (the same trick `launch.sh` itself uses — re-exec as
self, not root, so PAM re-initializes docker group membership without a password). Proved with an
isolated marker job (no app code) that APScheduler's background thread was alive but never dispatched
anything, in the container specifically (identical test ran clean locally). `DEBUG` logging surfaced
the real number: a job set for 3 seconds out computed an 18000-second (5-hour) wait instead. Root
cause: all 5 boot-relative jobs used naive `_dt.now()` for their `run_date`, but they're registered via
the `"date"` string alias, which APScheduler auto-labels with `scheduler.timezone` (America/Chicago) —
mislabeling a UTC-valued naive clock reading instead of converting it. Fixed all 5 to
`_dt.now(scheduler.timezone)`. Verified twice against the real container with a throwaway seeded test
task (deleted after): broken before the fix (sat untouched through a restart), self-corrected
automatically after redeploying with the fix — no manual intervention. Full writeup in
`docs/MEMORY.md`'s own entry, including exactly why yesterday's own reasoning about these jobs being
"safe by design" was wrong.

**Bug 2 — the missed-task branch skipped today entirely, landing on tomorrow instead.** Owner caught
this directly after the manual data repair: "it updated but to the wrong day. It skipped today and
went to tomorrow." `recurring_service.py`'s missed branch called `next_occurrence(today, rule)` —
designed for chaining from a real prior occurrence, wrong here since today hasn't happened yet and can
itself be valid. Swapped in the already-existing `first_occurrence_on_or_after(today, rule)` instead
(built the prior day for a different purpose, already has the right inclusive semantics — no new code
needed). Two new tests prove the exact reported symptom. The 5 real tasks this had already mis-advanced
were individually corrected with a narrow, targeted script (matched only tasks carrying the specific
bad log entry from that exact repair run), not a blanket recompute.

**Real data directly repaired this session**, with authorization at each step: ran
`recurring_service.process_all_users()` straight against the real Brain (no Docker needed — `brain/` is
a plain bind-mounted host folder) to fix every real recurring task across both real family members'
accounts, twice — once for the general stale-data catch-up, once more narrowly after finding Bug 2.
Final state verified directly: all recurring tasks show correct due dates, no data loss (task counts
unchanged before/after).

Full backend suite passing after both fixes. `black`/`isort` clean. Not yet re-committed — that's the

## Live click-through feedback + natural-language recurrence picker

Owner clicked through the Mod Store and the new Task/Goal `HistoryCalendar` view for the first time
("the mod store was good on click through. the deal with the task/goal calendar click through") — the
only gap found was cosmetic: day cells had no visible day-of-month number, making it hard to find a
specific date at a glance. Fixed in `HistoryCalendar.jsx`'s `Cell` component — a new `showDayNumber`
prop renders the date's day-of-month centered in the cell (white text on a filled/colored cell, muted
gray on an empty one), wired on for the month view only (the year-view strip's `w-2.5 h-2.5` cells are
too small to hold a legible number, left as-is). `TASKS.md`'s live-verification item narrowed
accordingly — Mod Store and the calendar view are now confirmed; `MetricGraph`, the manual-metric
Graph/Calendar toggle, the bigger tree chevrons, and Tasks' click-card-to-open are still unconfirmed.

Then moved on to the next open backlog item per the owner's own "let's move on to the natural language
picker when you are ready": built and fully verified `lib/parseRecurrence.js`, an offline regex/keyword
parser translating free text ("every 2nd Tuesday", "monthly on the 15th", "every 2 weeks on Friday", ...)
into the same `RecurrenceRule` shape `RecurrencePicker.jsx` already produces, wired in as a quick-entry
field above the structured controls. Caught and fixed two real bugs before shipping (a `\bmonth\b` regex
that doesn't match "monthly," an over-complicated weekday-lookup expression), then verified clean against
20+ target phrases — see git history for the full parser if it's ever worth resurrecting.

**Reversed same day, before committing.** Owner asked directly whether the feature was actually helpful
for non-technical users or just redundant, prompting a harder look: the structured picker (dropdowns,
weekday toggles, an explicit "On day" vs. "On the Nth weekday" mode switch) is arguably the MORE
foolproof interface for someone unfamiliar with the app, since every option is a visible click with
nothing hidden behind guessed syntax — a free-text field can only fail silently on phrasing outside its
recognized vocabulary ("twice a month," "biweekly," "on weekdays"), which reads as a worse experience for
exactly the audience "natural language" was meant to help, not a better one. Owner agreed and asked to
remove it and put the effort into clearer in-app help text instead. Reverted `RecurrencePicker.jsx` to
its pre-parser state, deleted `lib/parseRecurrence.js` outright (no dead code, no feature flag — this
project's own convention). Net effect: the structured rrule-style picker from 2026-08-30 is the only
recurrence-entry mechanism, same as it's been since it shipped.

**Help text expanded instead** (`module_packages/tasks/manifest.py`'s `help_section`): the Tasks page's
"Set Type to Recurring..." `howto` bullet previously just said "pick exactly which days it repeats on"
without describing the picker's own controls. Rewritten to spell out the actual UI: the Daily/Weekly/
Monthly/Yearly + "Every N" interval row, weekday toggles for Weekly, and the "On day" vs. "On the Nth
weekday" mode switch (with "Last day of month") for Monthly/Yearly — the concrete alternative to a
natural-language field for a user who doesn't already know the picker's shape. `pytest -k help` (15
tests) still passes; `py_compile` clean.
