# 2026-09-18

## Homes module — designed and shipped

Owner asked for a new module to manage houses (rented or owned, one or several), pulling in tasks/notes/events/money already tracked elsewhere via a tag each house generates on creation, with the design explicitly left to me for the first pass.

Went through a proper plan-mode pass rather than guessing: 3 parallel research agents covered the tags system, Finance's multi-book pattern (the closest precedent for "multiple owned sub-entities"), and how cross-module data gets aggregated elsewhere in the app — each finding independently verified against real code before trusting it (`search_service.py:78`'s exact empty-query/empty-tags short-circuit, Goals' `_pool_user`/`_pool_id`/`_require_pool_write`/`_store_for` read byte-for-byte, `deepLinks.js`'s auto-discovery confirmed directly). Owner reviewed the plan and gave two pieces of feedback before approving: the frontend shouldn't read as "a dashboard with a list on it," and to make sure security/hardening was actually considered, not just implied — both incorporated into the plan before writing any code (a real per-house identity banner + tabbed sections instead of a flat list; an explicit Security & Hardening section covering IDOR, tag-spoofing, contact-link validation, rate limiting, and AI-tool write-gating).

**What shipped**: `module_packages/homes/` (manifest, service, router, trash_handlers, agent_tools, 35 tests), a small backward-compatible extension to `services/search_service.py` (`per_provider_cap`/`total_cap` keyword overrides), `services/file_service.py`'s `homes_path()`, and the frontend (`Homes.jsx` switcher + create modal, `HomeHero.jsx`, `HomeDetail.jsx` with its Overview/Tasks/Notes/Money/Events tabs, `TaggedItemRow.jsx`, `api.js`, `manifest.js`). Full backend suite: 1558 passed, 0 failed. Frontend eslint/build clean. Full writeup of every design decision and the one real bug caught during review (a wrong mental model about how pool search providers work, corrected before it shipped): `docs/MEMORY.md`'s 2026-09-18 Key Decisions Log entry.

## Icon collision + a real "create silently does nothing" bug, both from first real usage

Owner tried the module for real right after it went live and reported two things. First, the icon: Homes' default `🏠` was a straight duplicate of Household's own icon — an oversight, not intentional overlap; changed to `🏘️` everywhere (backend manifest, frontend manifest, every default-icon fallback) except the one spot that's SUPPOSED to say "🏠" — the household-pool-ownership badge on a home chip, which correctly still matches Household's icon on purpose.

Second, and more important: creating a house did nothing — no error, nothing saved. Ruled out the backend first and fastest: `docker logs` across the container's entire history since restart showed zero `POST /api/v1/homes` requests, not even a failed one — so this was never a persistence bug. Found and fixed one real code smell along the way (the create modal's focus-trap was wired to a plain `{ current: null }` object instead of `useRef(null)`, recreated fresh every keystroke) — genuinely wrong, but NOT the actual cause, and said so rather than declaring victory prematurely. The owner's own follow-up ("it created one after I left that blank") pinpointed it: they'd typed "1,617" into the monthly payment field, a plain `<input type="number">`. HTML5's native form validation blocks submission outright the instant a number input's text isn't parseable — before React's `onSubmit` ever fires — so the component's own error handling never even ran. Fixed both layers: every money input in Homes switched from `type="number"` to `type="text" inputMode="decimal"`, and the backend now strips `,`/`$`/whitespace from money fields before parsing regardless of caller (covers the AI agent tools too, which take this same field from natural language). New test (`test_comma_formatted_money_field_accepted`) locks in the backend tolerance. Full writeup + the "how to apply" for any other numeric field in this codebase: `docs/MEMORY.md`'s new Known Gotchas entry. A grep for other `type="number"` inputs elsewhere in the app turned up 6 more files, none touched — flagged to the owner rather than either silently fixing everything or silently saying nothing.

Both fixes rebuilt and redeployed to the owner's live instance the same way as the earlier restart (`docker compose build app && docker compose up -d app` for the backend; `npm run build` for the frontend, already-authorized to redeploy live). Backend suite: 1559 passed (36 Homes tests, +1 for the comma test), 0 failed.

## Tagged calendar events not showing up — a bug outside Homes entirely

Owner reported that events they tagged with a home's tag "have the tag but don't show up on the homes." Read `_search_calendar` (Calendar's own search provider) and `search_match()` end to end — both correct on static review — before finding the real cause one layer over: `household/manifest.py`'s and `team/manifest.py`'s own `_search_household_events`/`_search_team_events` (the providers that make a *shared* household/team calendar event show up in any tag search at all) both matched every event's tags against a hardcoded `[]` instead of the event's real `tags` field — copy-paste drift from `_search_household_tasks`/`_search_household_goals`, which read the field correctly. A household/team event could carry a home's tag and still never match, exactly as reported. Fixed both providers, added `test_household_search.py`/`test_team_search.py` (new files, 4 tests) confirming a tagged pool event now matches and an unrelated tag doesn't.

## A second live bug, reported mid-fix: creating a lender contact from a personal home

Owner: "I tried to add lender and it created a new contact but then said I don't have access to it." Traced it to `ContactPicker.jsx`'s "+ Create contact" flow — it always calls `contactsApi.create({ name, type: 'person' })` with no `pool` field, so it inherits the Contacts backend's own default (`pool: true` — new contacts default to the household/team pool everywhere else in the app, a deliberate design choice there). Homes' own contact-link validation is deliberately stricter (`docs/MEMORY.md`'s Security & Hardening writeup): a personal home's `landlord_contact_id`/`lender_contact_id` must resolve in the caller's *personal* store specifically. The mismatch meant a lender created from a personal home's edit form landed in the pool, then Homes' own save correctly rejected it as inaccessible — both sides were behaving as designed, just against different assumptions about where the contact would land. Fixed by giving `ContactPicker` an optional `pool` prop (undefined by default, so every other caller — Finance, Goals, Automations, Dashboard — keeps the exact existing pool-default behavior); `HomeDetail.jsx` now passes `pool={!!pool}`, matching whichever store the home itself resolves to.

## Feature: convert a personal home to a shared household/team home after creation

Owner: personal homes need a way to become shared after the fact, not just a checkbox at creation time. Added `POST /homes/{id}/convert-to-pool`, mirroring the existing `convert_contact_to_pool`/`assets_service.convert_to_pool` precedent exactly (self-service, edit-access gated via the same `_require_pool_write` check creating a pool home already uses — not admin-only). `homes_service.convert_to_pool()` moves the record between the two stores' JSON lists and deliberately preserves both `id` and `tag` — regenerating the tag would silently orphan every task/note/event/transaction already tagged with it — and registers the tag into the pool's own vocabulary too, so other household/team members' tag pickers offer it immediately. Like Contacts/Assets, there is no reverse endpoint anywhere in this app; going back to personal means delete (Trash-recoverable) + recreate, and the frontend's confirm dialog says so before sharing. Frontend: a "Share with Household/Team →" button on `HomeDetail.jsx`, shown only to admins/pool-edit grantees on a home that isn't already pool-owned; `Homes.jsx`'s own `canCreatePool` check was also fixed to be workspace-aware (`household` vs `team`) rather than hardcoded to `household`, a real latent gap for business-workspace users that the new button's gating would otherwise have inherited.

6 new backend tests (convert-to-pool: service-level move/tag-registration + router-level permission/404/IDOR). Backend rebuilt and redeployed the same way as the day's earlier restarts (`docker compose build app && docker compose up -d app`); verified `(healthy)`, clean startup logs, and real traffic (including a live `GET /api/v1/homes/.../items` from the owner's own session) served correctly on the new image.

## A fourth bug, found by fixing the first one: household/team items in the wrong tab

Once the search-provider fix above landed, the owner reported household/team calendar events now appeared in Overview's "recent activity" but not the Events tab specifically. Cause: `HomeDetail.jsx`'s own tab filters bucketed items by `i._module === 'calendar'`/`'tasks'`/`'goals'` — but a pool-scoped record's `_module` is `"household"`/`"team"` (whichever module owns THAT provider), not the record-type module, since household/team declare their own separate `SearchProviderSpec`s for tasks/goals/events rather than folding into tasks'/goals'/calendar's own personal-only providers. `search_service.py` already attaches a fully namespaced `_provider` field to every result ("household:events", "tasks:tasks", "team:goals", ...) — every provider across every module uses the same key suffix for a given record type by construction, so that's the correct thing to bucket on. Fixed via a new `itemKind()` helper reading `_provider`'s suffix (falling back to `_module` if `_provider` is ever absent) instead of checking `_module` directly, applied to every tab filter and the Overview stat-chip counts.

Owner then asked to confirm Money wasn't hiding the same issue: it isn't — Finance has no separate household/team provider at all (`_search_finance` folds pool-visible books into its own single provider via the pre-existing `list_visible_books()`), so shared transactions already carry `_module: "finance"` correctly. Confirmed by reading `finance/manifest.py` directly rather than assuming from the pattern. Frontend eslint clean, `npm run build` clean, redeployed live (no backend change this time — pure frontend fix). Full writeup: `docs/MEMORY.md`'s Key Decisions Log, appended to the same 2026-09-18 entry.

## Two small follow-on requests: delete button placement, hiding past events

Owner asked for the "Delete this home" link (previously a standalone line below the whole `HomeDetail` page) to live inside the edit form instead, next to Save/Cancel — moved there, still wired to the exact same `confirmDelete()`/`ConfirmDialog` flow as before (same shape as every other module's delete confirmation, e.g. `EventModal`'s own `handleDelete`), just relocated. No new confirmation mechanism needed since one already existed.

Owner also asked for past-dated tagged calendar events to stop showing up on a home's page at all, rather than accumulating forever. `search()`'s lightweight `{title, snippet, tags, record_id}` result shape (the plan's own deliberate v1 scope) didn't carry a date to filter on — added `start_date`/`end_date` to the three event-search providers' own result dicts (`calendar/manifest.py`, `household/manifest.py`, `team/manifest.py`) rather than only one, since Homes' aggregation can surface an event from any of the three depending on whether it's personal, household-pool, or team-pool. ## A converting-to-pool bug: editing a just-shared home 404'd

Owner converted a home to household, then tried to edit it and got "Home not found." `HomeDetail.jsx`'s `save()` never included `pool` in the PATCH body at all — `HomeUpdate.pool` genuinely defaults `False` (matching `HomeCreate`'s own default), so the update looked in the caller's own personal store, which no longer held the record after conversion. `get`/`items`/`remove` were already pool-aware (the component receives `pool` as a prop); `update` was the one call site that never threaded it through. Fixed by adding `pool: !!pool` to the save payload, plus a new router-level regression test (`test_update_home_after_convert_to_pool_requires_pool_flag`) that locks in both halves of the contract: omitting `pool` on a pool home's update correctly 404s, including it correctly succeeds. 43 Homes tests pass; black/isort/eslint/build all clean. Frontend-only fix, no backend rebuild needed this time.
