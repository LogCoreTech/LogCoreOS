**The sharing mechanism, confirmed precisely before touching anything, since Assets/Contacts/Finance
will need this same pattern later**: sidecar `Notes/_shares.json` per store (content stays plain
`.md`), folder-cascade access resolution via an ancestor-walk (`_entry_for_path()` — most-specific
wins), two audience shapes mutually exclusive per path (`shared_with` for named-user handshake
shares, `contributors` for pool shares — no handshake needed, since pool = already workspace-visible
by construction), `read < contribute < edit` access rungs, and a derived owner→workspace
share-routing cache (`notes_index.py`, explicitly modeled on `contacts_index.py`). Structurally the
simplest of the four sharing modules — no per-field caps, no comments/audit-log, no cross-book
transfer complexity — a deliberate, good first proof of the pattern.

**Three enforcement gaps closed, same shape as Chat's own conversion the day before — real
pre-existing holes, not new mechanism gaps:**

1. All 7 note AI tools lived in `agent_service.py`'s unfiltered static `_USER_TOOLS` list — a user
   with Notes disabled could still list/read/create/update/delete/move notes via chat, since
   `_get_tools()` only ever filtered *module-owned* tool schemas by `disabled_modules`. Moved into
   `module_packages/notes/backend/agent_tools.py`, closing the gap as a natural side effect of the
   move. `search_brain` stays core, deliberately not moved — it also rglobs journal/memory/profile
   files, genuinely cross-cutting, not notes-owned.
2. No `owned_brain_paths` entry meant a disabled user's `Notes/` folder had zero Brain-browser/
   AI-tool protection — closed by declaring `owned_brain_paths=["Notes"]`, the same generic
   gap-closing machinery (built once for Journal) closing a real hole in yet another module the
   moment its manifest finally says what it owns.
3. `note_embed`'s dashboard block had no `module=` gate at all — the exact
   `pool_tasks`-before-Household/Team situation. Closed by adding `module="notes"` to its
   `BlockSpec` and declaring `owned_block_types=["note_embed"]` on the manifest.

**A genuinely new mechanism gap, not a per-module enforcement hole this time — the module-tool-
dispatch call site never threaded `workspace` through.** `_module_tool_dispatch()`'s fallback call
site (`execute_fn(name, inputs, user)`, 3 args) had no way to pass the caller's active workspace to
a module's own `execute()`. Harmless for every prior module: Household/Team's tools always operate
on their fixed pseudo-user regardless of workspace; Journal/Home Assistant have no workspace concept
at all; Tasks' own `agent_tools.py` docstring already documented its 9 tools as implicitly
personal-only ("not a regression introduced by this move; not fixed here either") — none of them
ever *used* workspace even before their own conversions moved them out of inline code. Notes' tools
are different: the pre-conversion inline code in `agent_service.py` genuinely threaded `workspace`
through every single `notes_service` call (a note lives in either the personal or business `Notes/`
folder) — silently dropping it during extraction would have been a real regression, not a no-op.
Fixed at the root: widened the dispatch signature to `execute(name, inputs, user, workspace)` and
updated the call site plus all four existing `agent_tools.py` modules (household/tasks/journal/
home_assistant) to accept the new parameter with a `"personal"` default, unused — signature parity
without changing any of their own documented behavior. Tasks' own workspace-blindness stays exactly
as documented, deliberately not fixed as a side effect of an unrelated module's conversion.

**A second real mechanism discovery, on the frontend**: `blockRegistry.js` already had a generic
`configSchema` merge mechanism (a converted module's own manifest block entry can carry
`configSchema`, merged into `CONFIG_FIELD_SCHEMAS[block.type]`) — but no real converted module had
ever actually used it before, since Calendar's/Automations'/Tasks' own block types aren't
record-linked/configurable that way. `note_embed`'s existing `[{ key: 'path', label: 'Note', kind:
'note' }]` entry (previously hardcoded directly in `blockRegistry.js`'s static object) is the first
real content to move through that path onto a manifest's own block entry, proving the mechanism
works end to end for the first time on real code, not just by inspection.

`module_packages/household/tests/test_agent_tools.py` (neither directory has an `__init__.py`) —
renamed to `test_notes_agent_tools.py`.

## Same-day follow-up: a fourth gap, found by directly answering a verification question

Before authorizing commit, owner asked a real question rather than just "does it look good": "does
removing notes cause any issues with any other module storing data." Direct answer: no —
`user_deletion_service.py`/`dashboard_blocks/_actions.py`'s `notes_service` calls are unconditional
by design (same "deliberate no-op" philosophy Brain export already uses — the underlying data was
never meant to be install-state-gated, only the browse/AI-tool paths to it are), and pool notes live
entirely inside Notes' own per-pool store, structurally separate from Household's/Team's own
`task_service`/`events_service` data.

Answering it properly meant re-reading `search_brain`'s full implementation rather than trusting the
"unconditional, unaffected by this conversion" claim already written into `test_agent_notes_tools.py`'s
own docstring from earlier in the day — and that re-read found a real, narrower gap the docstring's
claim had missed. `search_brain` has two halves: a plain rglob over the caller's own files (correctly
gated by `_brain_skip()`, which now includes "Notes" when disabled, exactly as intended) and a second
loop reaching shared-to-them/pool notes directly via `notes_service.list_visible_notes()` — which
bypassed `_brain_skip()` entirely, gated by nothing. A user with Notes disabled could still search
content **shared with them** (not their own) through chat, even though their own Notes/ folder was
correctly hidden by the first half.

**Fixed** by skipping the second loop outright when `"Notes" in skip` — the same skip-set the first
loop already computes, no new logic surface. **Lesson, worth remembering generically**: when a tool
reaches the same conceptual data through two different code paths (a generic file walk plus a
dedicated cross-store lookup), confirm BOTH paths are gated the same way — a docstring asserting
"this is already handled" is a claim to verify by re-reading the code, not a fact to inherit,
especially when answering a real correctness question directly.

**Files**: `services/agent_service.py` (the fix), `tests/test_agent_notes_tools.py` (docstring
corrected, new test `test_search_brain_hides_shared_note_content_when_notes_disabled_for_viewer`).
**Verified**: full suite 936 passing (935 + 1 new).

## Dashboards converted into `module_packages/dashboard/` — the third LOCKED module, and structurally the most-depended-upon module converted so far

Owner: "commit and move on to the next module" — committed Notes, then proceeded directly into
Dashboards per the tracked rollout order. Same upfront research pass every increment gets (an
Explore agent covering the full file inventory on both sides, which pieces of `components/dashboard/`
are genuinely page-owned vs. shared rendering infrastructure, every cross-module consumer of

**A real naming decision, resolved before writing any code, not assumed from the plan doc.** The
rollout plan's own table calls this module "Dashboards" (plural, matching `module_packages/dashboard/`
— singular — every other conversion's own naming convention). But the live, already-shipped module
id has always been `dashboard` (singular) — baked into `require_module("dashboard")`, `CORE_MODULES`,
`deepLinks.js`, every role's `disabled_modules` entry. `module_registry.py` hard-enforces
`manifest.id == directory name`, so `module_packages/dashboards/` with `id="dashboards"` would have
been a genuine id RENAME — the same weight as Home Assistant's `home`→`home_assistant` move, needing
its own carry-forward migration. Resolved by keeping `id="dashboard"`, directory
`module_packages/dashboard/` — zero-rename, matching Automations'/Calendar's own precedent, confirmed
correct by direct grep rather than following the plan doc's directory name blindly.

**`dashboards_service.py`/`dashboard_templates_service.py`/`dashboard_index.py` all stay core — the
strongest "stays core" case of any conversion so far.** Every prior conversion's service stayed core
because another ROUTER imported it directly. Dashboards adds a structurally stronger reason:
`migrations/runner.py`'s own core migrations (m010/m011/m012) call `dashboards_service` directly, and
migrations run BEFORE `discover_manifests()`/`register_routers()` even exist in boot order — a module
package's own service literally cannot be imported that early, independent of how many routers import
it. Household's own m023 and Home Assistant's own m018 (both carry-forward migrations) independently
import `dashboards_service._all_stores()` too. Confirmed by direct grep before assuming — the original
plan doc's own file list had missed `dashboard_index.py` entirely, a real 225-line file.

**Zero block types owned — the first locked module with no `backend/dashboard_block.py` at all.**
Dashboards is the container every other module's blocks render inside, never a `REGISTRY` entry
itself — confirmed `dashboard_blocks/` has genuinely zero FastAPI imports anywhere, the same
"plumbing every module runs on top of, owned by none" category as `module_registry.py`, exactly as
the original rollout plan's own closing note anticipated.

**Frontend: 6 of 19 `components/dashboard/` files moved, confirmed real by direct import-grep — plus
one genuine surprise.** `CreateDashboardModal.jsx`/`DashboardAccessModal.jsx`/
`DashboardSettingsModal.jsx`/`DashboardSwitcher.jsx`/`DashboardTemplateManager.jsx`/`DashboardHero.jsx`
moved; `DashboardGrid.jsx`/`BlockRenderer.jsx`/`blockRegistry.js`/`blocks.jsx`/`actionKinds.js`/
`BlockPicker.jsx` and 5 generic field-kind pickers stay core (`DashboardGrid`/`BlockRenderer` are
imported directly by `Chat.jsx`'s own live pending-write preview; `blocks.jsx` by every converted
module's own block components). **`DashboardPicker.jsx`, despite its name, is NOT page-owned** —
reached only via `BlockPicker.jsx` → `ModuleAndRecordPicker.jsx`'s `dashboard: DashboardPicker`
kind-map entry, never imported by `Dashboard.jsx` itself. Exactly the kind of thing name-pattern-
matching alone would have gotten wrong.

**A genuinely new structural problem no prior conversion needed to solve: the app's own home route.**
`App.jsx`'s `<Route path="/" element={<Dashboard />} />` was never wrapped in `ModuleRoute` —
confirmed why: `ModuleRoute` redirects to `/` when a module is disabled, so a user with `dashboard`
disabled would hit a self-targeting redirect loop while already AT `/` if this route went through the
generic `MODULE_PACKAGES.map()` loop the normal way. Fixed by keeping the hardcoded, unwrapped route
(import path updated only) and filtering the generic loop
(`MODULE_PACKAGES.filter(pkg => pkg.to !== '/')`). Related: the manifest.js deliberately declares
**no `loadPage` field** — every other module's page loads via `lazy(pkg.loadPage)` inside that now-
filtered loop, but since App.jsx imports `Dashboard.jsx` eagerly instead, a `loadPage` here would just
define a dynamic `import()` call site nothing ever invokes — Vite creates a real, separate chunk for
that syntax regardless of whether it's called, so declaring it would have shipped a genuinely
orphaned, never-fetched `Dashboard-*.js` chunk. Confirmed by inspecting the actual `vite build` output
before and after — no such orphaned chunk exists.

**Same enforcement-gap shape as Chat's/Notes' own conversions, no new mechanism gap this time.** All
10 dashboard AI tools lived unfiltered in `agent_service.py`'s static tool list — closed by moving
them into `module_packages/dashboard/backend/agent_tools.py`. No `owned_brain_paths` gap existed here
the way it did for Chat/Notes — Dashboards data is JSON, not markdown, the same structural category
as Tasks, so `"Dashboards"` joined the UNCONDITIONAL structural skip set (`_ALWAYS_SKIP` in
`routers/brain.py`, the hardcoded set in `agent_service.py`'s `_brain_skip()`) alongside `"Tasks"`,
not the conditional per-user one Chat's `"Chats"`/Notes' `"Notes"` use — `owned_brain_paths=["Dashboards"]`
is still declared too, redundant but honest, matching Tasks' own precedent exactly. Notes' own
workspace-threading fix from the day before already covered every dashboard tool's real need (all 10
were already correctly workspace-threaded inline pre-move) — no further dispatch-mechanism change
needed, just the relocation.

**A real, previously-undocumented design difference found while writing router tests, not a bug**:
unlike pool Notes/Tasks (workspace-visible by default to any member), a pool dashboard's non-admin
access comes only from an explicit `contributors` grant (`dashboards_service._contributor_access()`)
— a plain household/team member sees nothing about a newly-created pool dashboard until one is added,
even though an admin always gets edit on it immediately. First caught as a failing test assertion
(assumed Notes' own pool-default-read behavior applied here too); confirmed by direct read that this
is Dashboards' own real, intentional design, not a bug to "fix" — the test was corrected to match
reality instead.
