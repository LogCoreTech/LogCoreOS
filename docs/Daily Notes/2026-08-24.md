## Mod Store: universal module system, phase 1 (registry infrastructure)

Long design conversation (interviewed extensively, plan at
`/home/logcore/.claude/plans/i-want-you-to-composed-scone.md`) landed on a much bigger scope than
the original "browsing-only Mod Store catalog" from earlier sessions: every module in the app —
including foundational ones like Tasks, Chat, and Dashboards — will eventually convert into a
uniform `module_packages/<id>/` format, each with its own manifest/version/changelog. A locked
module just carries `uninstallable=True` rather than being excluded from the system. Real
infrastructure (`dashboard_blocks/`, `agent_service.py`'s tool-orchestration engine) is explicitly
excluded — no router of their own, imported by every module, never a module themselves.

Today's actual code is the foundation only: the registry mechanism (`module_registry.py`), the
Mod Store service/router (`mod_store_service.py`/`routers/mod_store.py`), and all four
enforcement-gap fixes (Brain browser, AI agent tools, dashboard blocks, export-as-deliberate-no-op)
wired generically off a module's manifest — built and fully tested with **zero real modules
converted yet** (`module_packages/` is empty except `__init__.py`). Journal's actual conversion
(increment 1 in the plan) is still pending — tracked in `docs/TASKS.md`.

### Real bugs caught by writing tests before trusting the design

1. `discover_manifests()` was blindly importing every directory under `module_packages/`,
   including `__pycache__` once Python compiled bytecode for it. Fixed: require an actual
   `manifest.py` file, skip `_`-prefixed dirs.
2. Route ordering: the SPA catch-all was registered via `@app.get` at plain import time, but module
   routers can only register inside `lifespan()` *after* migrations run (a locked module's
   install-state depends on its own upgrade migration). Starlette matches by insertion order, so
   the catch-all had to move into `lifespan()` too, positioned last — otherwise it would have
   shadowed every module route. Verified via a real `TestClient` lifespan run, not just imports.
3. A locked module's registration failure needed to crash boot loudly, not log-and-skip like an
   optional module — the lenient path would leave the app looking healthy while something as
   load-bearing as Tasks was silently missing.

### Design corrections made mid-build (caught by reasoning through edge cases, not just coding)

- Brain-browser/agent-tool module gating is **per-user** (checked against the caller's
  `disabled_modules`), not instance-wide — a module can be installed for the instance but disabled
  for one role/user, and that case must hide its folder too. First draft only handled "never
  installed at all."
- Dashboard block gating threads the module check through **whichever identity `render_block()` is
  actually resolving as at that pass** (viewer at pass 1, owner at pass 2's
  `share_underlying_data` exception) — not a flat "check the owner" shortcut. Verified with a test
  where the viewer has the module off but the owner has it on (resolves as owner) and one where
  both have it off (stays locked).
- `features_service.ALL_MODULE_IDS` → `all_module_ids()` touched 4 files, not the 2 originally
  assumed — `routers/auth.py` had a second validator (`WorkspaceModulesRequest`) using the same
  name that a first pass missed.

### Real gap found mid-conversion

`write_journal_entry` wasn't in `_RESEARCH_TOOLS`/`_READ_TOOLS` — core's "new tools are write-gated
by default" rule — but the phase-1 module-tool plumbing had no way for a module to declare which of
its own tools are read-only. Without a fix, `read_journal_entry` would have silently stopped
working in research mode and started requiring approval in approve mode, a real regression from
today's behavior. Fixed: `ModuleManifest` gained `read_only_agent_tools`; both `agent_service.py`
call sites now union it in via `module_registry.read_only_agent_tool_names()`.

### Test infrastructure fix (affects every future module conversion, not just journal)

A module's own tests need the same fixtures as `app/backend/tests/`, but conftest.py fixtures only
inherit down a directory tree, not across sibling ones. Moved the shared fixtures to a new
`app/backend/conftest.py` (the true common ancestor of `tests/` and `module_packages/`), deleted
the old `tests/conftest.py`, and added `testpaths = ["tests", "module_packages"]` to
`pyproject.toml` so a bare `pytest`/`pytest -v` covers both trees. `pytest tests/ -v` still narrows
to core-only when that's what's wanted (an explicit path on the command line overrides testpaths).

## Hotfix: reinstall crash + badge glitch, reported from the real instance

Owner report, after actually deploying and clicking through increment 1 on their real instance (not
this sandbox): uninstalled journal (worked), reinstalled it, got an error, and the whole app appeared
to crash ("said check logs"); separately, the `pending_uninstall` badge ("Uninstalled — restart to
finish") looked "glitched... half hidden."

**Root cause (restart crash)**: `POST /mod-store/restart` called `docker_sdk...containers.get(
"logcore-app").restart()` synchronously, inline in the handler, before returning — but that call
restarts the very container the request is running in, so Docker can kill the process before the
HTTP response finishes reaching the browser. This is the one Mod Store code path that was never
actually exercised for real anywhere this session (no Docker daemon in this sandbox; only ever
verified as a 502 "container not found," never as a genuine successful restart). See
`docs/MEMORY.md`'s 2026-08-24 entry for the full writeup.

**Fix**: the Docker connectivity/container-lookup call stays synchronous (a real config/permission
failure still 502s immediately to the client), but the actual `.restart()` call is now deferred via
FastAPI `BackgroundTasks` (runs only after the response has been sent) plus a 2s delay. New
`tests/test_mod_store_router.py` (9 tests, the router's first-ever direct test coverage — previously
only the service layer and journal's `on_install`/migration hooks were tested, never `install()`/
`uninstall()`/`restart()` themselves) — including a regression test asserting the fake container's
`.restart()` is *not* called by the time `restart()` returns, only once the deferred task runs.

**Badge fix**: `pending_install`/`pending_uninstall` labels were long unbroken strings inside a
`flex-wrap` row with no `whitespace-nowrap` — shortened both ("Restart to activate" / "Restart to
finish," the page-level banner already explains the full context) and pinned to one line.

**Verified**: full backend suite green (847 passed = 838 + 9 new), frontend `vite build` clean.
**Not verified**: the actual production-instance failure was never reproduced here (no real Docker/
socket-proxy in this sandbox) — the fix is based on a close read of the exact race condition, not a
confirmed repro. Asked the owner to grab real server logs if the restart still fails after this
lands, since this diagnosis, while well-evidenced, wasn't confirmed against their actual error text.

## Hotfix round 2: badge layout + restart never resolving, both from continued real-instance testing

Owner kept clicking through the (still pre-fix) real instance and sent more detail: on mobile the
row's badge+version "grey text" was "pushed down and overflow hidden" instead of sitting in the top
corner (their words — a design expectation, not just a bug description); separately, clicking
"Restart Now" flashed a green success message but the "pending restart" banner never went away,
pressing it again returned an error, and only closing/reopening the Settings page showed the correct
post-restart state. Suggested fix themselves: "should make it autorefresh that page."

**Badge/layout fix** — `ModStore.jsx`'s row previously put name + version + badge in one
`flex items-center gap-2 flex-wrap` line; on a narrow viewport the badge could wrap onto its own line
in a way that read as clipped/hidden rather than a normal second line. Restructured: the badge is now
a `shrink-0` sibling in its own `justify-between` row, pinned to the top-right corner and never
wrapping; the name+version block is what shrinks/truncates (`min-w-0`, `truncate`) if space is tight.
Matches exactly what the owner asked for ("should be in the top corner").

**Restart-never-resolving fix** — root cause: the backend's own restart is now deliberately deferred
(~2s delay, then the actual container stop/start/boot, all real time) per the hotfix above, but the
frontend was calling `load()` exactly once, immediately after the request returned — so it always
re-fetched the *same pending state* that existed before the restart even began, made worse (not
better) by the crash-hotfix's own deferral. `doRestart()` now polls (`catalog()`+`active()` every 2s,
60s deadline) until no row is still `pending_install`/`pending_uninstall`, keeping `restarting` (and
therefore the Restart Now button, which is `disabled={restarting}`) true for the *entire* window —
not just the initial request — so a second click can't land mid-restart, which is what turned into
the reported "pressing again returned an error." Fetch failures during the poll (the container really
is down for a few seconds between the old process dying and the new one answering) are expected and
silently retried (`load(true)`), not surfaced as an error — only a real 60s timeout flashes a message.
`load()` now returns the freshly-fetched `{modules, active}` directly rather than only setting state,
since reading React state back inside the same tick that just called its setter would see stale data.

**Verified**: `npx vite build` clean. **Not verified**: no live browser in this sandbox, so the
actual mobile rendering and the full poll-until-resolved cycle against a real container restart were
never watched happen — reasoned through from the exact reported symptoms and the mechanism's own
timing, same honest gap as the round-1 hotfix above. Asked the owner to re-verify on their real
instance once this lands.

## Hotfix round 3: row content clipped mid-transition, fixed on reload

Owner, still testing round 2's (pre-fix) build: "when the tag and text/buttons switch between
install/restart and uninstall... both sides of text and tags are cut short or bottoms of text or
tags are cut off. but it all returns to normal when page is reloaded." Researched first rather than
guessing blind — spawned an Explore agent to check whether this app has hit this bug class before.
Confirmed two real precedents: `ContactRow`'s presence-popover clipping (2026-08-18 entry above) and
`assetDisplay.jsx`'s lightbox, both caused by `.card`'s `backdrop-blur-sm` (creates a new stacking
context / containing block) — `backdrop-filter` is a genuinely fragile mechanism in this app's mobile
PWA context, not a first occurrence. Neither precedent's fix was a remount trick, though — both found
and fixed the specific stacking-context/containing-block mechanism directly.

**Diagnosis**: "correct on reload, broken on the in-place transition" is exactly the signature of a
stale GPU compositing layer — a fresh mount always paints cleanly; an in-place React DOM mutation is
what triggers the bug. `ModStore.jsx`'s row `<div>` (with `.card`'s `backdrop-blur-sm`) never
unmounts across a state transition — same `key={entry.id}` throughout install→pending→active→
pending_uninstall — so React mutates its children in place every time.

**Fix**: keyed the row on `${entry.id}:${state}:${busy}` instead of just `entry.id`, so React fully
unmounts and remounts the row's DOM subtree (and therefore its backdrop-blur compositing layer) on
every visually-relevant transition, forcing a clean paint every time — mechanism-agnostic (fixes the
symptom regardless of whether the true cause is exactly the same stale-layer-bounds issue or a
related compositing quirk), one line, no shared-CSS/design changes elsewhere in the app.

**Verified**: `npx vite build` clean. **Not verified**: still no live browser in this sandbox — same
honest gap as rounds 1 and 2. This is the third real bug this owner has caught by actually clicking
through the shipped UI on their own instance; none of the three were reachable by this session's
pytest/build-only verification.

Owner confirmed all three fixes working on the real instance ("it all works perfectly"), authorized
the commit, and said to move forward. Committed as `794db43` on `feat/mod-store-registry-infra`.

### Two non-obvious things preserved exactly, not carried by the generic module mechanism

- `m016`'s upgrade migration guards on `ha_config.json`'s existence *and* a real, non-blank url+token
  — Home was always opt-in, unlike journal's blanket "the instance existed before" assumption in
  `m015`. An instance that never connected HA starts correctly uninstalled on upgrade.
- `get_home_state` is read-only (no approval needed) but deliberately excluded from the narrower
  research-mode tool set — a real asymmetry predating this conversion. The generic
  `read_only_agent_tools` manifest union (built for journal) would have added it to both sets
  uniformly, silently widening research mode. Left it out of Home's manifest entirely and kept the
  exact hardcoded `_READ_TOOLS = _RESEARCH_TOOLS | {"get_home_state", "ask_user_question"}` line in
  `agent_service.py` untouched — it works identically regardless of which list a tool's schema comes
  from, since these sets only check names.

`features_service._BUSINESS_MEMBER` needed a comment, not a deletion: it's hand-authored (unlike
`_PERSONAL_MEMBER`, derived via comprehension), and `load_features()` defaults any module missing
from a role map to `True` — Home's `"home": False` had to stay explicit there or a fresh
business-profile instance would silently default Smart Home to enabled.
