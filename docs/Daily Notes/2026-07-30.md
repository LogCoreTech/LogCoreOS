## AI usage counter + caps shipped (TOP PRIORITY task)

Owner picked this as the next thing to build. Scoped via Q&A before writing code: skip automation/n8n tracking (confirmed via code research it's architecturally invisible — n8n calls providers directly with its own credential, never through Python); count all 3 real AI call sites, not just `/chat` as the original TASKS.md note said (chat, save-memory, and custom AI-powered suggestions — the last one reachable from the scheduler, the "run now" button, AND nested inside a chat turn via the agent's own `run_suggestion` tool); tokens-only display, no $ estimate; build hard/soft cap enforcement in the same pass, not just visibility. Mid-session the owner added two more requirements: per-user selectable cap period (daily/weekly/monthly, not just monthly) and a live usage-percentage indicator in both Admin and the Chat module itself.

**Architecture**: instrumented at the single choke point — `ai_provider.py`'s `chat_completion()`/`agent_completion()` — rather than at each of the 3 call sites, so token recording can never be missed by a future caller. Storage is daily buckets (`brain/_system/ai_usage.json`, never in a user's portable Brain folder) with daily/weekly/monthly totals derived on read by summing the right date range, mirroring Finance's "derived values computed on read" rule — this means the per-user cap period is freely switchable with no migration. New `services/ai_usage_service.py`, new `routers/ai_usage.py` (`/api/v1/ai-usage/*`, admin-only except `GET /me`), new `pages/AiUsage.jsx` at `/admin/ai-usage` (linked via a button on the AI Provider card), new usage-% badge + "Continue anyway?" confirm card in `Chat.jsx`.

Full design questions were resolved via `AskUserQuestion` before implementation (limit scope = global default + per-user override; limit metric = admin's choice of messages/tokens/both per user; hard-vs-soft mode = per-user, not instance-wide; soft-cap acceptance holds for the rest of the current period).

**Verified**: 20 new backend unit tests (`test_ai_usage_service.py`) plus the full 494-test suite green; a throwaway end-to-end script drove the real FastAPI app through `TestClient` (register → login → set a hard cap → confirm chat #2 is blocked with zero AI calls made → switch to soft → confirm the confirm-required response → accept overage → confirm subsequent calls go through) — this is full HTTP-level verification of the actual wiring, not just the service layer. Frontend `vite build` and `eslint` both clean. No browser-driven visual check was possible in this environment (no Docker access, no browser tool) — the Admin page and Chat badge have not been visually confirmed on a running instance; owner should eyeball both before considering this fully done.

## Settings/Admin merged into one drill-down menu — Admin page retired

Owner wanted the mobile "Main Menu" pattern from a reference app (icon+label rows grouped under
section headers, each row opening its own page) applied to Settings, and the entire separate Admin
page folded into it behind a single "Admin Settings" row. Scoped through a long interview (6 rounds
of `AskUserQuestion`, explicitly requested by the owner mid-session — "keep asking questions, do not
assume") before writing the plan, since the grouping/drill-down decisions were genuinely the owner's
to make, not mine to infer.

**What shipped**: `pages/Settings.jsx` is now a menu (Profile · Appearance · Notifications ·
Shortcuts[mobile] · Account · admin-only Admin Settings), each row opening its own page under
`pages/settings/`. Admin Settings is the same pattern one level deeper (`pages/settings/AdminMenu.jsx`
→ Users & Roles · AI · General · Team · Household · Hosting under `pages/settings/admin/`), reorganized
**by app area** rather than by setting type per the owner's explicit grouping calls — e.g. Team/
Household each bundle their own pool priorities + relevant integrations (Smart Home on Household) +
a new read-only bank-connections summary, instead of one flat "all settings of type X" page. Users &
Roles drills one level further: the list links to a full per-user page (role, feature role, workspace
access, pool-edit grants, module overrides, and — new — that user's own bank-connection management,
moved off the old flat `BankConnectionsCard` list) and to a separate Role Definitions page. `/admin`
and `/admin/ai-usage` are gone with no redirect (owner's explicit call — self-hosted tool, not a public
app with bookmarks to protect).

**Real behavior changes surfaced mid-interview, not just navigation**: (1) Session length is now a
single **instance-wide** admin-set value (`GET/PATCH /auth/admin/settings` gained `session_minutes`)
— the per-user self-service picker and `PATCH /auth/session` are removed entirely; changing it only
affects new logins, never forces existing sessions to re-auth (owner confirmed both explicitly). (2)
Team/Household bank-connections sections: the owner wanted actual pool-level (non-user) bank
connections ("business and joint family accounts, not tied to a user") — recommended and the owner
agreed to ship the **read-only summary** now (`GET /finance/simplefin/pool-summary`, derived from
existing per-user `account_map` data, zero new storage) plus a visible "coming soon" placeholder for
the real connection, logged as its own follow-up in TASKS.md rather than building new SimpleFIN pool
storage/claim/sync logic into this same pass.

**Explicitly deferred, not built**: a Profile page redesign ("character page" style) plus
auto-pinning every user as a cross-linked Contact — genuinely separate feature with Contacts-module
backend implications; owner agreed to scope it as its own follow-up (logged in TASKS.md) rather than
bundle it in.
