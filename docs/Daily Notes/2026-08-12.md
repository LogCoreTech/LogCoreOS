## Fixed the ai_usage_service timezone-bucketing test bug (deferred from 2026-08-10)

Owner confirmed the other three post-release items were fine and asked to fix this one now.

Root cause (full diagnosis history in the 2026-08-10 note): `test_record_tokens_accumulates_personal_and_business`
and `test_record_message_only_bumps_messages` use `USER = "TestUser"` without ever registering it via
`create_user()`, so `auth_service.get_user_timezone` finds no account and falls back to `"UTC"` —
`today_for_user` then buckets by the UTC calendar date, while the assertions independently computed
bare `date.today()` (local/server timezone). The two only diverge for a several-hour window every
day, whenever UTC has already crossed into the next date but local hasn't — real and recurring, not
a calendar-day coincidence.

Fixed by making both tests compute their expected bucket key via `today_for_user(USER)` — the same
function `ai_usage_service._bump_and_escalate` actually uses — instead of bare `date.today()`, so the
test's assumption matches the service's real contract regardless of what timezone the machine running
it is in. No production code changed — `today_for_user`'s per-user-timezone bucketing (UTC fallback
included) is correct as designed; this was purely a test-assertion bug.

Verified: `test_ai_usage_service.py` 21/21 green, full backend suite **596/596** — first fully clean
run this cycle. `black --check .` and `isort --check-only .` both still clean.
