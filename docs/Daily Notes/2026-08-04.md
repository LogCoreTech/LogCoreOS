# 2026-08-04

## Custom Dashboards — built from a fresh interview, supersedes the prior day's spec

Owner asked to plan out the "custom dashboards feature" and be interviewed to get it right. What
started as a review of the existing `docs/TASKS.md` "Record-Scoped Dashboards" spec (record-owned,
1:1 with a Contact/Asset, no independent sharing model) turned into a full redesign once the owner
clarified the realtor client/property example was "only an example... not the actual request. it
needs to be empty to customize." Multiple `AskUserQuestion` rounds converged on: standalone,
unlimited, user-created dashboard objects (like Notes/Assets); a freeform draggable grid of blocks
pulling live data from essentially every module, including ones the original spec never touched
(Smart Home, Automations, AI Chat/Usage); admin-only blocks hidden from the picker/greyed out for
non-admins; and — the one genuinely new mechanic — an owner-only, per-dashboard toggle that lets a
shared viewer see blocked data "as the owner" would see it, opt-in and off by default.

A Plan agent flagged mid-design that this directly contradicts the prior day's owner-approved spec
(not a minor tweak — the core "owned by a record" mechanic is gone). Surfaced explicitly via
`AskUserQuestion` rather than silently picking a side; owner confirmed full supersession.

**What shipped this session** (full build, not just planning): `services/dashboards_service.py`
(CRUD + `resolve_access()` mirroring `finance_service._resolve_book_access()`, floor-of-one delete
protection), `services/dashboard_index.py` (share-routing + reverse "referenced by" lookup, mirrors
`assets_index.py`), `services/dashboard_blocks/` (registry + 12 resolver modules, 27 block types),
`routers/dashboards.py`, migration `m010_seed_home_dashboards` (seeds each user's old fixed widget
set as a "Home" dashboard). The security-critical piece — `share_underlying_data`'s two-pass
render function — is covered by a dedicated test matrix (16 new tests, all green) rather than just
the ordinary CRUD tests. Frontend: full `pages/Dashboard.jsx` rewrite (replaces the hardcoded
widget page), `components/dashboard/` (grid on `react-grid-layout`, block picker, sharing modal
with the new toggle, dashboard switcher, 27 block presentational components).

**Deliberately deferred, not cut** (sequenced last in the build plan, documented in `docs/TASKS.md`
and `docs/AGENTS.md`): dashboard templates, the "referenced by" UI hooks on non-Assets/Contacts view
pages (the backend endpoint/index works, no frontend surface calls it), Module Engagement +
External Data block types (both need new backend infra), and Net Worth/Spending/Completion trend
blocks (need new time-series aggregation endpoints — `finance_reports.py` only computes
single-period snapshots today).

**Known risk flagged, not yet resolved**: the new `react-grid-layout` surface sits in the same
mobile-shell region (`Layout.jsx`) that has a well-documented history of iOS-standalone-PWA-only
layout bugs invisible to Chromium. Drag/resize is disabled below the `sm` breakpoint specifically to
shrink that risk (mobile gets a read-only stacked view), but this has not been confirmed on a real
device.

**Testing**: full backend suite 553 green (16 new `test_dashboards_service.py` tests, 2 pre-existing
unrelated `test_ai_usage_service.py` UTC-day-boundary flakes). Frontend `vite build` + `eslint`
clean. Relaunched via `bash launch.sh` for the owner to check out remotely.

## Follow-up same day: app-wide scroll-containment audit (third round on the recurring iOS bug)

Owner reported "most all pages scroll the background... Settings is the biggest issue," plus the
new Dashboard page needed the same mobile footer-clearance spacer other pages already have. This
is the third round on the scroll-containment bug class already documented across two prior entries
in `docs/MEMORY.md`'s Known Gotchas — see the new 2026-08-04 entry there for the full technical
writeup (methodology, the rate-limit false-positive that briefly looked like a real bug, the fix).

**Summary of what shipped**: `overscroll-behavior: none` on `html`/`body` + `overscroll-y-contain`
on `<main>` (`index.css`, `Layout.jsx`) as a defense-in-depth layer on top of the existing
`position: fixed` body technique — the modern, purpose-built CSS property for this exact failure
mode, never tried in the two prior rounds. Found and fixed a genuinely separate bug while auditing:
`Brain.jsx` and `Notes.jsx`'s editors both had a `<textarea>` set directly as a flex-1 item with no
`min-h-0` wrapper — the exact mistake already identified and fixed in `Journal.jsx` on 2026-08-03,
never back-ported to these two older editors. Also swapped their `100vh` height calcs to `100dvh`
(mobile browser chrome resize safety, matching `.modal-card`'s existing `dvh` usage). Added the
established mobile-footer-clipping spacer to 23 pages that never got it — essentially the entire
Settings tree, plus Assets/Automations/Finance/Goals/Help/Home/Team/Brain's file list — and to the
new Dashboard page specifically. `Notes.jsx`'s own root spacer was deliberately left for a future
pass (too structurally different — negative-margin breakout, conditional sidebar/editor toggle — to
risk a blind copy-paste).

**Verification honesty**: an isolated-backend + synthetic-brain + Playwright crawl of all ~27
authenticated routes at mobile and desktop viewports found zero `html`/`body` overflow anywhere,
confirming (a third time) that this bug class is real but structurally invisible to Chromium — it
only reproduces on a real iOS standalone PWA. This round is NOT yet confirmed on-device; flagged
directly to the owner as the next real-world test, same as both prior rounds.

**Testing**: `npm run build` + `eslint` clean across all touched files. Relaunched via
`bash launch.sh --skip-build` (frontend-only, `dist/` already fresh from the pre-relaunch build).
