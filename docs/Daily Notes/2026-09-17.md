### A bug the verification pass found, not caused

Running the full suite after all 10 pieces landed left exactly one failure: `test_welcome_back_service.py::test_generate_summary_never_reads_another_users_journal`. Root cause: the test hardcoded a journal entry's date as `"2026-09-01"` while computing the "away since" cutoff as `datetime.now() - timedelta(days=8)` — the two only agreed while real "now" stayed in the first half of September, and broke on their own the moment today's date passed 2026-09-09, with no code change. Fixed by deriving the entry date the same relative way the cutoff is. Full writeup: `docs/MEMORY.md`'s Known Gotchas section (same bug class as the scheduler timezone gotchas already there).

## Cut release 0.8.0

Owner asked whether anything else should go into this release; the honest answer was no — the more valuable move was cutting a release, since `VERSION` was still stamped `0.7.1` while `[Unreleased]` had grown to ~50 bullets across two full audit batches, including real security fixes (IP-spoofing rate-limit bypass, stale-admin-session account creation, a sharing privilege-escalation bug, the Home Assistant service-domain passthrough, `/docs` exposure) that anyone still on 0.7.1 was exposed to in the meantime.

Followed the standing release checklist ([[release-checklist-whats-new]]): bumped `VERSION` and `app/frontend/package.json` to `0.8.0`, stamped `CHANGELOG.md` with a `## [0.8.0] — 2026-09-17` heading above the accumulated content (leaving a fresh empty `[Unreleased]` above that), and added the `help.json` `whats_new` entry (7 highlights — this release spans everything since 0.7.1: the UX Polish Batch, Trash/bulk-actions, the AI Settings provider-picker overhaul, ntfy's removal, the welcome-back popup, and both audit security passes, so it's the biggest highlight set since 0.6.0's 13). No new module shipped this release, so no new `help_section` was needed. `package-lock.json`'s own version stamp was left untouched, matching the precedent set by the 0.7.1 bump commit (`e5ea84a`) — it self-corrects on the next `npm install`, not part of the checklist.

Owner then asked to codify the release process (previously only a private assistant memory note) so a GitHub release title/body gets generated automatically next time — added `docs/RELEASING.md`, then corrected it same-day ("i wil make the version tags myself") to explicitly forbid the assistant from creating the `vX.Y.Z` git tag; the `v0.8.0` tag created earlier in this session was deleted before the correction was committed.

Two CI failures surfaced right after: GitHub's `black --check .`/`isort --check-only .` gates failed on 7 and 8 files respectively from the audit batch (formatters were never run locally before those commits). Fixed both at the versions pinned in `requirements-dev.txt` (exact match to CI); `routers/auth/__init__.py`'s hand-placed "--- X.py: ... ---" re-export comments needed manual re-alignment after isort's alphabetical reordering detached them from the blocks they described. Captured the lesson in `docs/MEMORY.md`: any future batch's own verification pass must run `black`/`isort` alongside `pytest`, not discover the gap via a failed CI run afterward.
