# 2026-09-06

## Real bug: bulk-select checkboxes were silently blocking delete clicks

Owner report: "i dont think any of the newly converted delete functions are wired up. no delete button
works." A serious claim given the whole previous session built the Trash/bulk-actions feature — worth
confirming rather than assuming the report was imprecise.

First ruled out stale deployment: the real running instance on port 8000 is a Docker container whose
`/app` and `/frontend/dist` turned out to be byte-identical to this checkout's own files (confirmed via
`/proc/<pid>/root`, matching `docs/MEMORY.md`'s existing 2026-08-22 note that this dev machine's personal
instance bind-mounts this exact repo). So the live instance was genuinely running yesterday's code, not
something stale — the bug had to be real.

Re-read `services/trash_service.py` and a representative delete function (`goals` service's `delete_goal`)
line by line looking for a backend logic bug; found nothing. Reconsidered the shape of the report instead:
the user named Tasks/Notes/Assets/Contacts specifically — the 4 modules that got bulk-select UI, not the
other 5 (Calendar/Goals/Journal/Finance/Dashboards) which only got a small `TrashLink` icon add. That
pointed at the frontend, not the backend.

Found it: `components/SelectCheckbox.jsx` used a `-m-2.5` (-10px) negative margin around a 44×44px tap
target — a real technique for enlarging a hit area without visually growing the checkbox, but every row it
was wired into places it FIRST, ahead of the row's own "···" menu / expand arrow / open-item button, in a
flex row whose `gap` (6–12px across the four files) is smaller than the 20px the margin needs to stay
clear of a neighbor. On desktop, where the checkbox renders unconditionally (not gated by select-mode,
only mobile hides it), its box silently overlapped and intercepted clicks meant for whatever came right
after it on every single row — frequently the exact click needed to reach the single-item Delete action at
all. That's a mechanically certain bug, not a guess: the negative-margin math and every row's real `gap`
value were checked directly against each other.

**Fix**: removed the negative margin — the wrapper now takes its true 44×44px as ordinary flex-layout
space, same as any other row button. No overlap possible. Full writeup in `docs/MEMORY.md`'s Known
Gotchas (new top entry) — worth keeping since this is a real, reusable-pattern risk ("enlarge a tap target
without shifting layout" is exactly the kind of trick likely to get reached for again).

`eslint --max-warnings 0` and `vite build` both clean on the fix. **Not yet re-verified against the live
instance** — the running container needs a fresh frontend build deployed before this fix takes effect
there; asked the owner to confirm after redeploying, and specifically whether Calendar/Goals/Journal/
Finance/Dashboards (the 5 modules this bug can't explain, since they never got checkboxes) were also
broken, since if so that would mean a second, still-unfound bug.

Owner confirmed the checkbox fix worked (deployment is a live bind mount into this exact checkout —
confirmed by watching `dist/index.html`'s mtime update the instant `npm run build` ran, no restart
needed). Committed as `5ccb56b`: soft-delete/trash bin (#5) + bulk actions (#4), the checkbox fix
included — closes out the entire UX Polish Batch. Owner then asked to commit, and separately whether
anything else was left; flagged the still-unreleased version/whats_new gap and the not-yet-click-through-
verified corners (restore, purge, the admin pool tab, Notes/Assets' tree edge cases) without acting on
either unilaterally.

## Second real bug, found immediately after: a `load()` race, not a rendering bug

Owner: "i found another issue... after deleting an item. it didnt disappear. but actually the dif[f]
reload didnt occur so the item was deleted but still rendered." Asked which page first rather than
guessing — narrowed to Tasks/Notes/Assets.

Confirmed via a research pass first: none of Tasks/Notes/Assets/Contacts has any custom list-diffing
logic — each just does a plain full-array `setState` on refetch, and React's own stable-id keying
(`task.id`/`node.path`/`asset.id`/`contact.id`, never array index) already reconciles removals correctly
on its own. So a genuinely-deleted item disappearing from the fresh array is sufficient by construction —
the bug had to be that the fresh array wasn't actually the one that ended up in state.

Real cause: `load()` on all four pages is called from a lot of independent, uncoordinated places — mount,
every delete/save/move/archive handler, bulk-delete, pull-to-refresh, and (Contacts only) a 60s presence
poll — with no request-sequencing guard at all. Two overlapping calls' network responses can resolve out
of order; without a guard, an older call's slower response landing AFTER a newer call's faster one
silently overwrites the correct post-delete list with stale, pre-delete data. `Dashboard.jsx`/`Goals.jsx`
already have a `cancelled`-flag guard, but it only protects one `useEffect`'s own re-runs against itself —
doesn't help here, since the racing calls are different call sites, not two runs of the same effect.

**Fix**: a `loadGeneration` ref per page, incremented at the start of every `load()` call; each call only
applies its `setState`s if no newer call has started since. Applied to Tasks/Notes/Assets/Contacts.

**A second, related bug found in the same function while fixing the first**: `Contacts.jsx`'s `load()`
re-synced the open detail panel via `cleanList.find(c => c.id === prev.id) || prev` — `cleanList` is
already filtered by the archived toggle, so this can't tell "archived out of this filtered view" apart
from "genuinely deleted"; both produce no match, and `|| prev` redisplayed a deleted contact's stale data
forever either way. Fixed by re-fetching the one open contact directly by id (`contactsApi.get`, which
isn't archived-filtered) instead of searching the already-filtered list — still-exists-but-archived
succeeds with fresh data, genuinely-deleted 404s and closes the panel.

Full design writeup in `docs/MEMORY.md`'s Known Gotchas (new entry, right above the checkbox one from
earlier today — these two bugs happened back-to-back in the same debugging session but are otherwise
unrelated). `eslint --max-warnings 0` and `vite build` clean; confirmed the fix landed in the live
instance's bind-mounted `dist/` the same way the checkbox fix did. Not yet re-confirmed by the owner as
of this entry.
