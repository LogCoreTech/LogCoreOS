# 2026-08-18

## Seven-item polish pass: Assets typed custom fields, Contacts UI/privacy, Dashboard block chrome

Owner sent 7 items in one message, all polish/extension work on features shipped
the day before. Full writeup in `docs/MEMORY.md`'s Key Decisions Log,
"2026-08-18" entry. Planned as one batch: three parallel Explore agents read
every relevant file in full (Assets templating, Contacts sections/popover/
career-history, Dashboard block buttons/chrome) before any design decision,
then a single plan covering all 7 items was written and approved before any
code changed.

**1. Blank-asset custom fields get the same typed picker Templates use, plus
"Save as template."** A blank asset's own `custom_field_defs` (same shape a
Template's `fields` use — `{key, label, type, options?}`) now get real
`_validate_value()` type-checking instead of the old freeform-string-only
path; an undefined key still falls back to freeform. New
`POST /assets/{id}/attach-template` (self-service, edit-access) retroactively
attaches a just-created template back onto the asset it came from — a
deliberate, narrow exception to `template_id` otherwise being immutable after
creation. Deviated from the plan's own stated approach here: rather than a
shared frontend component reused unchanged by `TemplateManager.jsx`, the two
editors' key-handling turned out to differ enough (a Template's key is a
stable, technical, admin-typed identifier; a blank asset's field key is
purely internal, auto-slugified from the label) that forcing one shared row
component fought the layout more than it helped — kept the field-type list
and backend validators shared, left the markup separate.

**2. Last-seen popover still hidden behind the contact below it.** The
2026-08-17 direction fix (`right-0` → `left-0`) didn't touch the real cause:
`.card`'s `backdrop-blur-sm` gives every `ContactRow` its own stacking
context, so the popover's `z-50` only ever won comparisons inside its own
row — the next sibling row (painted later, its own un-elevated stacking
context) covered it regardless of which side it opened toward. Fixed by
promoting the *open* row's own stacking context above its siblings
(`relative z-20`, toggled via a new `onPopoverToggle` callback from
`ContactAvatar`) rather than introducing this codebase's first portal-based
popover.

**3. Dashboard block buttons now always align right.** `BlockActionButtons`
had zero alignment of its own — every one of 9 call sites was independently
responsible, and 2 (`CollectionBlock`'s Kanban view, `NoteEmbedBlock`)
didn't. Fixed at the source with `ml-auto` on the shared component instead
of patching each call site (confirmed harmless-redundant, not conflicting,
everywhere the old per-site tricks already worked).

**4. Core Values are pills now, not a comma-split field.** New
`_validate_core_values()` (list, trimmed/deduped/capped) replaces the old
generic string-capping — also accepts a raw comma-separated string on input,
since the AI's `update_contact`/`update_profile` tools bypass the Pydantic
model entirely and call the service layer directly with a raw dict. New
migration `m014_core_values_to_list` converts existing data; its own test
caught a real dedup bug in the first draft (`"Growth, Growth"` producing two
entries) before it shipped.

**5. Career history: a past role can be added directly, with real dates.**
Entirely a frontend change — the backend already accepted any well-formed
entry independently and never enforced "exactly one current entry." Past
entries now display sorted by `start_date` descending, and can be edited
after the fact instead of read-only-plus-delete-only.

**6. Self-contact sections can be hidden from household/team, owner-only.** A
genuinely new mechanism (`hidden_sections`), distinct from the existing fixed
`_PRIVATE_FIELDS` set — six section keys (Values & Principles, Family,
Career, Address, Personal, Priorities), each mapped to its own field set,
enforced with the same owner-short-circuit shape `_strip_private()` already
uses, called right after it. Write-side rides along in the existing
third-party-viewer stripping branch — nobody but the record's own owner can
ever change what's hidden.

**7. Dashboard blocks get per-instance card/header toggles, default on.**
`show_card`/`show_header`, same lifecycle `sort_mode` already established.
**Explicit judgment call, flagged before implementation and approved with the
plan**: unset reads as true *unconditionally*, not "whatever the block's
`shape` already decided" — so this is a real default-appearance change
across every existing dashboard the instant it ships (list-shaped blocks
start showing a card; every header starts showing in view mode too), not a
narrow opt-in. `show_header` only ever governs the view-mode header — edit
mode keeps showing it regardless, since that's the only way to reach a
block's ✎/✕ controls. `agent_service.py`'s `update_dashboard_block` tool
description now mentions both settings explicitly, alongside the pre-existing
size/position note.

## Ten-item real-usage bug report on the pass above, dominated by one Dashboard workspace/loading cluster

Owner tested the seven-item pass live and sent 10 more items in one message.
Full writeup in `docs/MEMORY.md`'s Key Decisions Log, "2026-08-18 (second)"
entry. Items 1-5 are one interconnected Dashboards feature and were handed to
a background Explore agent (~15 min) before any code changed; items 6-10 were
independent enough to fix directly.

**1-2. Dashboards needed a same-workspace-or-both visibility toggle.** The
picker was already correctly workspace-scoped (pure `X-Workspace`-scoped
storage, no client-side merge) — item 1 was a confirmation, not a bug. Item 2
(no cross-workspace mechanism existed at all) got a new `cross_workspace: bool`
field mirroring Contacts' own mechanism: `find_dashboard()`/
`list_visible_dashboards()` gained a second own/pool/shared pass against the
opposite workspace's stores, filtered to `cross_workspace: true`;
`resolve_access()` for a cross-workspace hit uses the record's native
workspace, not the viewer's ambient one, so a stored pool-contributor grant
keeps its original meaning. Toggle lives in `DashboardSettingsModal.jsx`,
edit-gated (stronger than the `contribute` tier the rest of `PATCH
/dashboards/{id}` uses).

**3-4. "Dashboard not found" on every first open; workspace switch didn't
clear/reload.** Same root cause: `Dashboard.jsx`'s boot effect depended on
`[workspace, idParam]` while calling `setSearchParams` inside itself — a
dependency self-mutating its own array guarantees a double-fire. Fixed by
dropping `idParam` from the dependency array (now `[workspace]` only) and
routing deliberate user actions (`selectDashboard`, `onDashboardCreated`)
through `loadCurrent()` directly instead of a URL-change re-trigger — this
also fixes item 4 as a side effect, since a stale id now gets re-validated
against the new workspace's visible-id set on every switch.

**5. Auto-restore the last opened dashboard.** Owner explicitly delegated the
time window ("or make it longer than 1 minute... whichever you think is
best") — went with 30 minutes. `lc_dashboard_last_id_{workspace}` in
`localStorage` (id + timestamp), same pattern as Chat.jsx's own
last-opened-conversation restore, with an added expiry Chat's version doesn't
need.

**Bonus, not in the original report**: found while researching items 1-5 —
pool pseudo-users always store at the `personal` ws_path base regardless of
which workspace they're paired with, but `_team` pool dashboard creation
passed the ambient `workspace` straight through, so a `_team` dashboard
created from the AI chat agent (the only currently-reachable path to
`pool: true` for dashboards) vanished immediately. Fixed in both the router
and the agent tool handler, mirroring the pattern Assets already had.

**6, 8. Two more instances of the mobile input-zoom bug.** Same root cause as
prior fixes elsewhere: text input under 16px triggers iOS Safari's
auto-zoom-on-focus. `TagInput.jsx`'s `text-sm` → `text-base` covers both
reports at once (Contacts core-values pills and Assets blank-custom-field
select-options pills share this one component) — plus two more instances
found by checking for the same pattern (`PriorityList.jsx`,
`TemplateManager.jsx`).

**7. Dashboard block buttons "still" not right-aligned.** A genuinely
different, second bug from the 2026-08-18 `ml-auto` fix above — `TaskRow`
(used by `Top3TasksBlock`) had no `flex-1` of its own, so it sized to content
inside its `<li>` instead of stretching, leaving `ml-auto` nothing to push
against. Fixed by adding `flex-1` directly to `TaskRow`; confirmed a no-op
everywhere else it's used.

**9. Blank-asset custom fields never showed outside edit mode.** A real
regression from item 1 of the pass above: `AssetView.jsx`'s field-def
resolution only ever read `template?.fields` (always empty for a blank
asset) — the edit flow was fully wired, the read view never was. Fixed by
resolving `ownFieldDefs = template?.fields || asset.custom_field_defs || []`
once and deriving everything else from that.

**10. Pin favorite modules to the desktop sidebar, same as mobile's
shortcuts.** No new mechanism needed — reused the existing `shortcuts` list
and `shortcutModules` computation as-is. `Layout.jsx`'s desktop `<aside>`
gained a "Pinned" nav section above the main list. Along the way, found
`pages/settings/Shortcuts.jsx`'s outer wrapper was `md:hidden` — the entire
settings page silently rendered blank on desktop, not just its intended
mobile-only bottom-bar section — removed.
