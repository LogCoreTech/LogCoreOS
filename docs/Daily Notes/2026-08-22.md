**The real incident**: while investigating why the demo VPS was still on
`0.5.0`, found both it and a beta client's managed-hosting instance stuck
rolling back every single update attempt for over a week — same target
commit, timestamps one second apart. Root cause: the 2026-08-14 CORS
hardening commit (`9b6e827`) made `main.py::_startup_checks()` refuse to
start on wildcard `ALLOWED_ORIGINS`, with a documented shell-script self-heal
(`migrate_insecure_cors()` in both `launch.sh` and `update.sh`) that
auto-derives a real origin from `brain/hosting.json`. Both instances hit the
hardening commit before the self-heal function existed — the new container
crashed at startup, health check failed, `update.sh` rolled the *entire
working tree, including update.sh itself* back to the last commit before the
self-heal was ever written. The fix could never reach them: it only existed
in a future they could no longer pull.

**Permanent fix**: moved the check into `main.py` itself, consulting
`hosting_service.effective_domain_url()` — the same live value
`DynamicCORSMiddleware` already trusts at request time — before refusing
anything. A configured real domain makes the static env var moot (the
middleware never reads it in that branch); with nothing configured yet, it
now falls back to a safe localhost-only default instead of refusing to boot,
since bricking a fresh instance before its owner can even reach Admin →
Hosting was a real, avoidable cost of the original design. This self-heals
both currently-stuck instances automatically on their next update once a
release is cut — no manual intervention needed for either. Full mechanism
recorded in `docs/MEMORY.md` Known Gotchas, since the underlying pattern (a
shell-level self-heal for a Python-level hard-fail is fragile because the
shell script only updates *after* success) is worth remembering for any
future startup gate shaped like this one.

Manually fixed the demo VPS's `ALLOWED_ORIGINS` directly (read-only
investigation first, then the fix, then confirmed the container came back
healthy) since it was already in scope for today's other demo-mode work.
Left the Loves client instance for the code fix itself to self-heal, per
owner's explicit call — didn't touch that one directly.

## Post-release: 0.6.1 shipped, two more real bugs surfaced on the demo + Loves instances

Owner cut the 0.6.1 release and the CORS self-heal worked — both instances
finally updated. But that surfaced two more issues, both real, both
independently root-caused with a live VPS + a from-scratch isolated repro,
not guessed at:

**1. AI chat 500s on both VPS instances — not a release bug, and not a wiped
key either (corrected after an initial wrong diagnosis).** SSH'd into the
demo VPS (read-only first): `docker compose logs app` showed
`anthropic.AuthenticationError: 401 - API key is invalid`. First checked
`docker/.env`'s `ANTHROPIC_API_KEY` and found it blank — wrongly concluded
that was the cause. `ai_provider.py` actually resolves the key from
`brain/ai_settings.json` first (`{**env-based base, **_load_ai_settings()}`,
Brain value wins) — that's where Admin → AI Settings actually writes it, and
it's a Brain file, bind-mounted from the host, entirely outside the git
checkout `update.sh` touches. Checked it directly: a real, correctly-shaped
key is on file (108 chars, valid `sk-ant-` prefix) — not blank, not touched
by the update, structurally impossible for a git-based update to have
cleared since it isn't part of the repo at all. The actual cause is that
Anthropic is rejecting that specific key as invalid — revoked/rotated/dead
on the Anthropic console side, unrelated to LogCoreOS or this release. Owner
should check console.anthropic.com and re-enter a fresh key via Admin → AI
Settings if needed. Loves is very likely the identical story (a real key on
file, no longer valid) but not checked directly — client instance, outside
today's established scope for direct changes.

**2. The "floating high" chat box — real, reproduced cold, not caching.**
Owner was certain a hard refresh didn't fix it, and traffic logs on the demo
VPS confirmed a genuinely fresh frontend build (new hashed asset filenames,
container recreated). Built a from-scratch isolated backend + fresh
Playwright browser context serving the exact same production `dist/`
(matched by hashed filename against what's actually on the demo VPS) to
reproduce without touching either live instance further. Root-caused to
`Chat.jsx`'s auto-scroll (`bottomRef.current.scrollIntoView({behavior:
'smooth'})`, two call sites) never setting `block: 'nearest'` — the default
alignment walks *every* scrollable ancestor, and the sidebar's own module
list (tall enough to overflow on its own, worse with the 2026-08-18 Pinned
section) made the outer app-shell wrapper a legitimate-but-unintended scroll
target, so every auto-scroll nudged the *whole shell* up and clipped it via
its own `overflow: hidden`. Explains why it didn't show on the owner's
personal instance: same code, just a taller browser window there, so the
sidebar never actually overflowed. Full mechanism in `docs/MEMORY.md`.

Fixed by adding `block: 'nearest', inline: 'nearest'` to both
`scrollIntoView` calls. Owner then asked the obvious follow-up — if the
sidebar can overflow, shouldn't it scroll on its own? Correct: the fix above
stops chat from hijacking the outer shell's scroll, but the sidebar's own
`<nav>` still had no scroll region of its own (`flex-1` with no `min-h-0`),
so on a short window Settings/Help/Sign out could end up genuinely
unreachable. Fixed by adding `min-h-0 overflow-y-auto` to that `<nav>` —
same pattern `<main>` already uses elsewhere in `Layout.jsx` — so the module
list scrolls internally while the header/Pinned section/footer stay fixed.

### Verification

Both fixes verified against a from-scratch isolated backend (throwaway
brain fixture, never the real local Brain) + Playwright, screenshotted
before/after: outer shell `scrollTop` nonzero pre-fix, `0` post-fix across
both changes; sidebar's `<nav>` confirmed independently scrollable
(`scrollHeight` > `clientHeight`) with Settings/Help reachable and the
header staying pinned at `top: 0` throughout. Full backend suite unaffected
(774 green — this is a frontend-only change).

## Post-release, part 2: "Failed to load that chat" — not corruption, a workspace-routing bug

Owner asked directly: does a declined API key corrupt the chat archive when a
send fails? Investigated properly rather than assuming — it doesn't, and the
real cause is unrelated to the API key entirely.

`routers/brain.py` (`GET/PUT /brain/files/{path}`) never accepted a
`workspace` parameter — every request resolved against the personal folder
only, regardless of the `X-Workspace` header the frontend already sends on
every call. `Chat.jsx`'s `openSession()` loads a saved conversation through
this exact endpoint. Any conversation held in the business workspace writes
its archive to `Business/Chats/{filename}.md`; reopening it always looked at
`Chats/{filename}.md` instead. Confirmed directly on the demo VPS: the file
from the actual failed chat existed on disk the whole time, at
`brain/USERS/anthony bailey/Business/Chats/2026-08-22_12-48-34.md` — not
missing, not corrupted, just never where the endpoint was looking.

Fixing it surfaced a second, more serious bug: `ws_path(name, "business")`
is `brain/USERS/{name}/Business/` — a literal subfolder of the personal
base, not a sibling. Simply switching the endpoint to the correct
workspace-scoped path wasn't enough on its own: a personal-workspace listing
recursively walked straight into `Business/` and surfaced its files as if
they were personal, and a personal-workspace request for the literal path
`Business/<file>.md` resolved successfully — a real cross-workspace
read/write bypass, caught by writing the test for the listing leak and
noticing the same reasoning applied to path resolution. Fixed by adding
`"Business"` to the router's existing folder-exclusion set (previously just
`Tasks`, for an unrelated reason) — one change closes both the leak and the
bypass, since both the listing and the path-resolution logic already
consult that same set.

While in the file, also fixed the stale "admin-only writes" description of
`brain.py` in `docs/MAP.md` (already flagged in `docs/TASKS.md`'s backlog;
closed that item out here rather than leaving it for later).

### Verification

7 new tests in `tests/test_brain.py` (zero coverage on this router before
today): business-workspace read/write succeeds and is invisible from
personal, personal listing never includes a business file, and a
personal-workspace request for `Business/<file>.md` is rejected with 403.
Full backend suite green (781 — 774 prior + 7 new).

## Post-release, part 3: the chat box was STILL floating high — a different bug, and a red herring in how it was being tested

0.6.2 shipped the desktop sidebar-scroll fix and the `scrollIntoView`
`block: 'nearest'` fix. Owner confirmed the API-key and business-workspace
issues were resolved, but the chat composer was still floating high — on
mobile, specifically, and only on the demo/Loves VPS instances, never on
the owner's own personal instance. That last part turned out to be the key
clue, and a wrong one at first.

**The real bug**: entirely separate from anything fixed in 0.6.2. Mobile
viewport only — desktop was never affected. `Layout.jsx`'s `<main>` already
reserves 72px of bottom padding to clear the fixed mobile nav bar (which is
only 53px tall). `Chat.jsx` *also* renders its own dedicated 80px spacer for
the identical stated purpose, stacking on top — ~152px reserved to clear a
53px bar. Found the same exact spacer (same comment wording) copy-pasted
across `Journal.jsx`, `Tasks.jsx`, `Calendar.jsx`, `Contacts.jsx`,
`Household.jsx`, and `Brain.jsx` too — genuinely redundant everywhere, but
only reported as a bug on Chat, since a composer is expected to hug the
bottom in a way a scrolling list's trailing whitespace isn't. Owner
explicitly scoped this fix to Chat only ("only that chat box part... was
the problem") — the same redundancy on the other six pages is left alone,
not assumed-fixed.

**The red herring**: while investigating why the owner's personal instance
never showed this, checked its container's actual mount table
(`/proc/<pid>/mountinfo`) and found `/frontend/dist` and `/data/brain`
bind-mounted straight from this exact repo checkout. Every local
`npm run build` this whole session — for the CORS fix, the desktop sidebar
fix, this fix — silently redeployed live to the personal instance with zero
restart or update step. It was never a fair comparison point for whether a
*shipped release* fixed something; it only ever reflected whichever local
rebuild had most recently run. The two VPS instances, needing an actual
release + `update.sh` cycle, kept showing the bug long after local testing
said it was resolved — which is exactly why the owner's confusion
("personal is fine, why isn't the VPS") was reasonable, not a sign of a
device-specific bug. Documented as its own gotcha since this could burn a
future debugging session the same way.

Version bumped to 0.6.3.

## GitHub security alerts triage: 28 total, verified which were real

Owner asked for the 18 CodeQL code-scanning + 10 Dependabot alerts on the

**Confirmed false positives / non-issues (test-backed):**

  payloads (encoded, doubled-slash, backslash) all correctly fell

  a sanitizer.
- ReDoS in `contacts_service.py`'s email regex — timing stayed linear

- Dependabot's `python-dotenv` `set_key()` alert — grepped the whole
  repo, that function is never called (`config.py` only uses
  `pydantic-settings`'s read-only `env_file` loading).
- `black`/`pytest` Dependabot alerts — dev-tool only, never imported
  outside tests/CI, no runtime/production exposure either way.

1. **SSRF (Critical)** — `simplefin_service.py`'s `decode_setup_token()`

   only `http(s)`/`mailto`/relative in-app paths render as real links;
   verified the scheme-check logic against 8 known-safe/known-malicious
   inputs in isolation.
3. **9 exception-exposure alerts** — HA/n8n connection tests, n8n
   workflow sync, the n8n-secrets-restart handler, and the GitHub
   release check all returned `str(exc)` directly in JSON responses.
   Genericized all 9; full detail still goes to the logger. Deliberately
   left the 10th alert in this category (finance CSV-import validation
   errors) untouched — those are safe, deliberate messages about the
   user's own uploaded file, not leaked system internals, and would
   have made the feature worse to genericize.
4. **CI workflow permissions** — added `permissions: contents: read` to
   `ci.yml` (2 alerts); neither job writes to the repo today.
5. **Dependency bumps** — `python-multipart` 0.0.18→0.0.32 (7 alerts,
   also fixed a stale dev-venv drift down at 0.0.9), `python-dotenv`

## Closing out #7: encrypting the Infisical secrets cache/token at rest

The one item left "accepted, not fixed" from the alert triage above. Owner
asked to actually do it. Planned properly first (plan mode) since the real
shape turned out bigger than "add encryption" — a genuine chicken-and-egg
key-management problem, not a drop-in patch.

**The core constraint**: `load_infisical_secrets()` runs before
`config.Settings()` exists, specifically because Infisical can be the
*source* of `SECRET_KEY` itself for managed-hosting instances. That rules
out deriving the cache-encryption key from `SECRET_KEY` (circular — the
cache's own fallback path exists for exactly the moment `SECRET_KEY` might
not be resolvable yet) and rules out auto-generating the key inside
`brain/_system/` next to the ciphertext (that whole directory is one
`backup.sh` tarball — key-and-ciphertext traveling together defeats the
point). Landed on a new `INFISICAL_CACHE_KEY` env var living only in
`docker/.env`, same tier as `SECRET_KEY`/`N8N_ENCRYPTION_KEY` already.

**Scope, per owner's explicit choices going in**: both `infisical_cache.json`
*and* `infisical_config.json` (the token itself — CodeQL only flagged the
cache, but the token is arguably more sensitive and was the identical
exposure); and graceful degrade (warn once, stay plaintext) rather than a
hard failure if the key is ever missing — mirroring the CORS-incident
lesson that a security hardening pass should never be what bricks an
instance's startup.

**Implementation**: `Fernet` from `cryptography` (already installed
transitively via `python-jose[cryptography]`, zero new dependency).
`infisical_loader.py` gained `_cipher()`/`_read_encrypted_json()`/
`_write_encrypted_json()` and a new public `read_cache()`. No explicit
migration script needed — decrypt-or-fall-back-to-plaintext means an old
file just reads correctly with no key configured, and self-heals (rewrites
itself encrypted) the moment a key **is** available, on its very next read.
`launch.sh` generates a fresh key only for new installs (mirrors
`N8N_ENCRYPTION_KEY`'s existing pattern exactly); `update.sh` gained
`migrate_infisical_cache_key()` (mirrors `migrate_insecure_cors()`) to
provision one for existing instances that don't have it yet — a
convenience, not a requirement, since graceful degrade means an instance
without the migrated key just keeps working in plaintext.

**A real gap found while exploring**: `n8n_service.py`'s
`sync_business_workflows()` and `routers/automations.py`'s
`/n8n/sync-secrets` handler both bypassed `infisical_loader` entirely,
reading `infisical_cache.json` straight off disk via `file_service.read_json()`
— which would have silently broken (read back `{}`, no error) the moment
the cache was actually encrypted. Both switched to the new `read_cache()`.
Neither had any existing test coverage at all (confirmed by grep before
writing anything) — added one for the `n8n_service.py` side and verified it
actually catches the regression by temporarily breaking the real fix,
confirming the test fails, then restoring it.

### Verification

New `tests/test_infisical_loader.py` (9 tests, green field — no prior test
file existed for this module): encrypted round-trip for both files, plain
JSON on disk confirmed when no key is set, legacy-plaintext-file self-heals
to encrypted on next read once a key exists, an invalid key value falls
back to plaintext instead of crashing, and the `n8n_service.py` integration
point actually resolves real credentials through the encrypted cache
(regression-tested by breaking it on purpose first). Full backend suite
green: 792 passed (781 prior + 9 new + 2 from the earlier session's other
fixes already counted). `black --check`/`isort --check-only` clean.

## Owner asked: do any recent fixes need surfacing in README/website security messaging

Expected a "yes, mention X as a new feature" answer. Found something more
important instead: the website's `/security` page (`logcoretech.com/security`,
in the separate Website repo) makes an absolute claim — "No stored-XSS
content path exists... no HTML sanitizer needed because none is ever
parsed" — that this session's own Chat.jsx XSS fix had just quietly
invalidated. Traced why: the July 19 audit's "verified sound" reasoning
for that claim was specifically "the frontend has no markdown-to-HTML
renderer... because it never needs one" (`docs/Security-Audit-2026-07-19.md`
line 160, with one already-fixed exception noted, A3, the automation-inbox
link). That premise held until `Chat.jsx` shipped its own hand-rolled
markdown renderer on 2026-08-10 — a second content-to-HTML path the audit
never anticipated — and nobody re-checked the invariant against it. It sat
quietly wrong for six weeks until CodeQL's automated scan caught the exact
same bug class in it that A3 had already covered elsewhere. This turned
"should we advertise a bug fix" into "we have a live, factually inaccurate
claim on a public trust page, found by our own recent work."

**Decision**: correct both `SECURITY.md` (this repo) and the website's
`/security` page — a factual correction, not a marketing addition.
Deliberately left out of both: the exception-message sanitization, CI
workflow permissions, and dependency bumps (routine hygiene, not
named-finding material for a public audience) and the Infisical
encryption-at-rest fix (managed-hosting-only; self-hosted instances, the
actual audience for these pages, never create those files at all — stayed
out per the same "public repo = dev/self-hosted work only" reasoning
already applied elsewhere this session). `README.md` needed no change — its
Security section only points elsewhere and makes no claims of its own.

Added a standing design-notes rule to `SECURITY.md` ("any new feature that
renders a URL as a clickable link must validate its scheme first") and a
`docs/MEMORY.md` gotcha generalizing the actual lesson: an audit's
"verified sound because X never happens" claim needs re-checking against
every future feature that could make X happen, not just left for the next
full audit or scanner pass to eventually catch it.
