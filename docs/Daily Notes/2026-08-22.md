# 2026-08-22

## 0.6.1 release prep, and a real deadlock found on two live instances

Continuation of the website/marketing session's spillover into product work: a
few quick wins (failing test, demo-mode plumbing) turned up a genuine
production incident affecting both real deployed instances.

**Quick wins, all shipped:**
- Fixed `test_finance_transfers.py::test_transfer_leg_never_false_matches_a_recurring_bill`
  — hardcoded `next_due` date had aged past its own assertion window; now
  relative to `date.today()`.
- `docker/.env.example` documents a Haiku model as the recommended `AI_MODEL`
  for a public demo instance (cost control) — this one's genuinely just a
  config value, no code change needed.
- New `DEMO_MODE` instance flag (off by default): shows a standing "this is a
  demo, data resets nightly" banner (with Privacy/Terms links) and gates a
  new nightly reset script (`app/backend/demo_reset.py` + `docker/demo_reset.sh`)
  that wipes non-admin accounts. The script refuses to run at all unless the
  flag is explicitly set, specifically so it can't be copy-pasted onto a
  personal/managed instance by mistake and silently delete real family/team
  data. Caught my own bug before it shipped: `docker-compose.yml` uses an
  explicit env-var allowlist per service, and `DEMO_MODE` wasn't in it —
  without that the whole flag would never have reached the container.
- Login/registration now links to Privacy Policy and Terms of Service.
- FastAPI's reported version (`/docs`, OpenAPI schema) was hardcoded to
  `0.1.0` — now reads the same `installed_version.json` `update.sh`/`launch.sh`
  already maintain.

**The real incident**: while investigating why the demo VPS was still on
`0.5.0`, found both it and a beta client's managed-hosting instance stuck
rolling back every single update attempt for over a week — same target
commit, timestamps one second apart. Root cause: the 2026-08-14 CORS
hardening commit (`9b6e827`) made `main.py::_startup_checks()` refuse to
start on wildcard `ALLOWED_ORIGINS`, with a documented shell-script self-heal
(`migrate_insecure_cors()` in both `launch.sh` and `update.sh`) that
auto-derives a real origin from `brain/hosting.json`. Both instances hit the
hardening commit before the self-heal function existed — the new container
crashed at startup, health check failed, `update.sh` rolled the *entire
working tree, including update.sh itself* back to the last commit before the
self-heal was ever written. The fix could never reach them: it only existed
in a future they could no longer pull.

**Permanent fix**: moved the check into `main.py` itself, consulting
`hosting_service.effective_domain_url()` — the same live value
`DynamicCORSMiddleware` already trusts at request time — before refusing
anything. A configured real domain makes the static env var moot (the
middleware never reads it in that branch); with nothing configured yet, it
now falls back to a safe localhost-only default instead of refusing to boot,
since bricking a fresh instance before its owner can even reach Admin →
Hosting was a real, avoidable cost of the original design. This self-heals
both currently-stuck instances automatically on their next update once a
release is cut — no manual intervention needed for either. Full mechanism
recorded in `docs/MEMORY.md` Known Gotchas, since the underlying pattern (a
shell-level self-heal for a Python-level hard-fail is fragile because the
shell script only updates *after* success) is worth remembering for any
future startup gate shaped like this one.

Manually fixed the demo VPS's `ALLOWED_ORIGINS` directly (read-only
investigation first, then the fix, then confirmed the container came back
healthy) since it was already in scope for today's other demo-mode work.
Left the Loves client instance for the code fix itself to self-heal, per
owner's explicit call — didn't touch that one directly.
