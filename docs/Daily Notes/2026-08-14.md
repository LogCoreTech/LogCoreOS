# 2026-08-14

## ESLint 8→9 + Vite 5.4→8 migration (plan-mode, owner-approved)

Owner asked how hard the two dev-tooling major-version bumps left in TASKS.md's Security section
(deferred since 2026-07-20 as "no runtime/security exposure" / "low real-world risk") would be. Initial
estimate before hands-on research: "an hour or two." Entered plan mode at owner's explicit request
before touching anything.

**Research changed the estimate substantially.** `app/frontend/package.json`'s `"lint": "eslint src/
--max-warnings 0"` has no `--ext` flag — under ESLint 8's eslintrc config, a bare directory target only
walks `.js` files by default. This repo has 6 `.js` files and **92 `.jsx` files** — CI's lint step had
been silently skipping virtually the entire React component tree since the project began. Flat config
(mandatory in ESLint 9+) matches files via explicit glob patterns in the config itself, not a CLI
extension flag, so migrating correctly and naturally starts linting `.jsx` for the first time —
surfaced 1489 previously-invisible problems in one shot (confirmed via `npx eslint src/ --ext .js,.jsx`
before writing any code): 1417 were `react/prop-types` (this codebase has never used PropTypes on any
of its ~90 components — confirmed, once actually checked, to be an established convention rather than
an oversight), and 72 were real, individually-addressable issues.

Presented this as a genuine scope fork via AskUserQuestion rather than deciding unilaterally: owner chose
to turn `react/prop-types` off in the new config (matches the codebase's actual convention, keeps the
task scoped to tooling rather than a ~90-file PropTypes-writing project). Wrote the full plan
(`/home/logcore/.claude/plans/iridescent-fluttering-flame.md`) with concrete target versions (confirmed
live via `npm view` — real npm registry access works in this environment), the exact real 72-issue
breakdown by rule, and a step-by-step approach; owner approved as-is.

**Mid-execution, owner added a directly-related request**: make sure `launch.sh` gets existing/new
self-hosted instances onto the new deps correctly too, not just this dev environment. Investigated
before assuming anything was needed: `build_frontend()` already runs `npm ci` (exact-lockfile install),
so that part already "just works" once `package.json`/`package-lock.json` are committed — no launch.sh
change needed there. But `check_prerequisites()` only checked that `node`/`npm` *exist*, never their
*version* — an existing self-hosted instance with an old Node would have hit a confusing, late-stage
failure deep inside `npm run build` (Vite 8's own internal version check) instead of a clear one at the
top of the script. Added `node_version_ok()` (checks Vite 8's actual floor, `^20.19.0 || >=22.12.0` —
unit-tested the boundary logic standalone, including the real semver gap where Node 21.x satisfies
neither range) wired into `check_prerequisites()`, plus a matching `"engines"` field in `package.json`
as a secondary signal. Deliberately did *not* touch `install_deps()`'s NodeSource `setup_20.x` pin
(auto-install path) — that always installs a current 20.x, which already clears the floor; bumping the
auto-installed major is a separate, bigger judgment call than what was actually asked.

**Execution matched the plan closely** (64 real issues found post-migration vs. 72 predicted — the gap
is exactly the 8 `no-console` + 3 `no-empty` the corrected config rules resolved with zero file edits,
per plan; 3 new "unused eslint-disable directive" warnings appeared from the react-hooks plugin's 4→7
major changing what it flags, removed as stale). Also discovered and dropped one intentionally *not*
adopted: `eslint-plugin-react-hooks` v7's own "recommended" set jumped from 2 rules to 17 (14 new
React-Compiler-oriented strict rules like `purity`/`immutability`/`set-state-in-render` — this codebase
uses none of that), so `eslint.config.js` explicitly keeps just the original two
(`rules-of-hooks`/`exhaustive-deps`) rather than silently adopting 14 new strictness dimensions as a
side effect of a version bump — same reasoning as the prop-types decision, applied without re-asking
since it's the same category of call the owner had just made.

**Fixed the 61 mechanical issues directly** (29 unescaped-quote errors across 13 files, 8 unused-vars —
one of which cascaded into a second, `openContextMenu` in `Notes.jsx`, orphaned once its only caller
`handleAction` was removed as dead code). **For the 24 `react-hooks/exhaustive-deps` warnings, looked at
each individually rather than pattern-matching on the message text** — this caught a real trap: two
"useCallback has an *unnecessary* dependency: workspace" warnings looked mechanically safe to "fix" by
deleting the dep, but `workspace` wasn't unused by accident — it was kept specifically so `load` gets a
new reference (re-triggering a downstream effect) when the workspace switches; removing it would have
silently broken "switch workspace → reload data." Ended up: 4 fixed directly (added `setSearchParams` —
confirmed genuinely stable per React Router's own contract — to 4 identical deep-link-cleanup effects;
1 `isImage` primitive-boolean add; the `AssetTreePicker` `useMemo` restructured per the linter's own
suggestion), the remaining ~19 suppressed with an inline reason each (mount-once fetches where `load`
isn't memoized, identity-scoped user-effects that would otherwise refetch on every unrelated profile
field change, an autosave effect that sets its own tracked value). Also learned mid-way that
`eslint-disable-next-line` must sit immediately before the line the *linter actually reports* — for a
multi-line `useEffect`, that's the closing `}, [deps])` line, not the opening `useEffect(() => {` line;
caught via a stale "unused directive" warning on the first attempt (`UserDetail.jsx`), fixed the
placement pattern before repeating it another dozen times.

**Verified thoroughly, not just "tests pass":**
- `npm run lint` — genuinely 0 output, exit 0, the *first* time this command has ever actually checked
  the `.jsx` tree.
- `npm run build`/`dev`/`preview` — all clean under Vite 8 (which now ships Rolldown, a Rust bundler,
  under the hood — visible in the build output's new terminology/timing diagnostics, but the output
  shape is identical and nothing broke).
- `npm audit` after both bumps: `brace-expansion` (transitive, dev-only) fixed automatically via `npm
  audit fix`; one real finding remains (`react-router-dom`, moderate, needs a 6→7+ major) — logged as a
  new, separate TASKS.md item rather than folded into this pass, since a runtime routing library major
  bump is a materially different kind of risk than a dev-tooling bump.
- Live browser smoke test in a fresh isolated instance (same pattern used all session): logged in,
  navigated 5 different pages including one edit modal (`TaskModal.jsx`, a file directly touched by the
  exhaustive-deps fixes) — first attempt at clicking a task row to open it timed out, investigated before
  assuming a regression, found the actual edit trigger is a separate "✎" button (title text has no click
  handler) — re-verified against the real element and got a fully-rendered, correctly-styled modal.
  Zero console errors beyond the same benign background-poll 401s seen in every other isolated-instance
  check this session.
