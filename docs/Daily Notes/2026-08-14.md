### Item 3 — Finance: cross-book, cross-workspace Transfer type

The biggest single piece of this release. Confirmed first that transactions have exactly one `account_id`,
no stored `type`/`kind` (derived transiently from `amount_cents`'s sign), and no linking field between
transactions existed anywhere — and that balances already self-correct for a same-currency transfer pair
with zero special-case code (`account_balances()` sums each account's own transactions independently), so
the double-counting problem is confined entirely to the report layer, never balances/net-worth.

**Schema**: added `transfer_pair_id` (uuid, null unless this row is one leg of a transfer) plus
denormalized peer info (`transfer_peer_book_id/name`, `transfer_peer_account_id/name`,
`transfer_peer_workspace`) to the transaction shape — mirrors this codebase's existing denormalization
convention elsewhere (dashboards' `_template_label`, by-asset transaction lookups carrying `book_id`/
`book_name`) so the frontend never needs a pair-id-only lookup. The Plan-validation pass caught a real
blocking bug before any code was written: `add_transaction()` builds its stored row from an explicit
named-field allowlist, not `**kwargs` passthrough — the new fields had to be added to that allowlist
explicitly or they'd be silently dropped. Partway through building the frontend edit modal, realized the
peer's *workspace* was also needed (not just book/account) for the cross-workspace PATCH/DELETE calls to
work — added `transfer_peer_workspace` to the schema, router, and a test assertion after the fact.

**Guardrails**: same currency required (no FX conversion, matching `net_worth()`'s existing per-currency
grouping precedent); edit access required on both books (a contribute-level collaborator can't move money
between two whole books); cross-workspace allowed per the owner's explicit choice, so the new
`finance_transfers.py` router does **not** rely on the ambient `X-Workspace` header at all — request body
carries explicit `from_workspace`/`to_workspace`, each validated against the caller's entitlement and
resolved via `find_book()` independently. Deliberately skips `finance_planning_service
.on_transactions_added()` for both legs (documented in code as deliberate, not an oversight) —
`match_bill()`'s matching is category-blind and could otherwise false-match a transfer leg to an unrelated
recurring bill.

**API**: new `finance_transfers.py` (matches the existing per-feature router-file split — `finance_banking
.py`/`finance_planning.py`/etc. already do this rather than growing `finance.py`), importing `_find_or_404`/
`_require_edit` directly from `finance.py` per that same sibling-router precedent. `POST /finance/transfers`
creates both legs (best-effort deletes leg 1 if leg 2 fails); `PATCH`/`DELETE /finance/transfers/
{transfer_pair_id}` take both book_ids explicitly rather than needing a new cross-book index. Closed a gap
in the *existing* single-tx endpoints: `PATCH`/`DELETE /finance/books/{id}/transactions/{tid}` had zero
awareness of `transfer_pair_id` before this — added a 409 guard so a transfer's two legs can't be edited/
deleted independently and silently desync.

**Reports**: one-line `transfer_pair_id` exclusion filter added to `monthly_report()`, `pnl()`, and
`budget_status()`'s spent-sum loop.

**Frontend**: `TransactionModal.jsx` gained a third "Transfer" kind alongside Expense/Income — swaps the
category/payee/asset/deductible/tax fields for a To Book + To Account picker spanning both workspaces
(reused the `listBooksForWorkspace(workspace)` + `extraHeaders` override mechanism built earlier this
session for SimpleFIN pool connections), with client-side currency-match validation before submit. New
`TransferEditModal.jsx` shows both legs together for edit/delete. `TransactionsView` rows for a transfer
leg show a ⇄ badge + the peer book/account name instead of a category.

New `tests/test_finance_transfers.py` (12 tests): cross-workspace leg creation with correct peer fields
both directions, same-book degenerate case, same-account rejection, currency-mismatch rejection,
workspace-entitlement rejection, contribute-only-access rejection, report exclusion (sums + category
breakdown), budget_status exclusion, no false-positive bill matching, PATCH moving both legs, DELETE
removing both legs, old single-tx endpoints rejecting direct edits to a transfer leg (409).

**The most significant debugging detour of this session** happened during live verification, not in the
code itself. A cross-workspace transfer's `transfer_peer_workspace` kept coming back `'personal'` on both
legs instead of the expected `'business'`/`'personal'` split. Spent real effort ruling out an application
bug before concluding it wasn't one: raw JSON inspection, filesystem inspection (`find ... -iname
books.json`), and Playwright network-request interception all pointed at the same root cause — the test
user's real persisted `/auth/me` `workspaces` field was `["personal"]` only, even though `/auth/register`'s
*response* showed `["personal","business"]` (a response shape that doesn't reflect what's actually saved).
That meant (a) `TransactionModal.jsx`'s `otherWorkspace` computation was correctly returning `null` — there
was genuinely no second workspace to offer — and (b) the test script's raw API call with an
`X-Workspace: business` header override was being correctly coerced down to `'personal'` by this same
session's earlier entitlement-coercion security fix (`get_current_user()` now checks the header against
the caller's real `workspaces` grant, not just that it's a valid string). Both behaviors were working
exactly as designed. Fixed by properly granting business-workspace access at both the instance level
(`PATCH /auth/admin/settings` → `enabled_workspaces`) and the per-user level (`PATCH
/auth/admin/users/{id}/workspaces`) before retesting — after which every result was correct (`peer_ws`
correct on each leg, balances 750/750, report exclusion 0/0, UI showing "Client Ops (Business)"). Also hit
and worked around several Playwright-specific issues along the way that were test-script bugs, not app
bugs: a mobile-only "← Back" button assumed visible at desktop width, an ASCII `+` vs. full-width `＋`
character mismatch in a `has-text()` selector (root-caused via a raw `innerText()` dump), and
`selectOption({label: /regex/})` not being valid Playwright (it requires a literal string — fixed by
looking up the real `<option>`'s `value` attribute directly).

### Item 4 — Tasks: remove category headers, flatten sort by score, add a sort-mode control

`Tasks.jsx` grouped tasks into `{cat, tasks}` buckets with an `<h2>` header per group — that header+wrapper
was "the unnecessary gap" the owner flagged. Within-group sort was by priority *label* only, never the
real scoring formula or due date, and comparisons only ever happened within a category — never across
categories, so a High-priority task in a low-ranked category could never outrank a Medium-priority task in
a higher-ranked one, which was the owner's second, related complaint. The real formula
(`priority_service.py`'s `score_task()`) already had a flat, cross-category, sorted backend endpoint
(`GET /tasks/scored`), but it's scoped to pending/non-goal/**own-user-only** tasks — Tasks.jsx also shows
household/team assigned pool tasks and All/Done/Overdue filter tabs that endpoint doesn't cover. Decided
to port `score_task()` to a small pure JS function (`scoreTask()` in `lib/constants.js`) rather than
extending the backend endpoint — this codebase already tolerates multiple independent copies of this exact
formula (a **third** copy already exists in `brain/skills/life-priorities/score_tasks.sh` for an agent
skill), so a JS port is squarely inside established practice, not a new risk category; named it 1:1 with
the Python function and cross-referenced it in comments so drift is at least grep-able, while the Python
side stays locked down by its own 14 existing tests.

A sort-mode control was added mid-research as a separate owner message: "add a button or drop down on top
on tasks page to change filter order. either by date/time or priority or another one you think of." Built
as three modes — Priority (default, via `scoreTask()`), Date/Time, Alphabetical — persisted to
`localStorage` (`lc_tasks_sort`, matching this codebase's exact existing convention for browser-only UI
prefs like `lc_ws`/`lc_sidebar`). Removed `grouped`/`uncategorized`/category-`<h2>` rendering entirely in
favor of one flat sorted list. Confirmed `Goals.jsx` is a fully independent, copy-pasted grouping
implementation sharing no component/hook with Tasks.jsx — deliberately not touched.

**Files:** `app/frontend/src/pages/Tasks.jsx`, `app/frontend/src/lib/constants.js`.

### Item 6 — Mobile: keyboard open/close leaves touch targets offset from what's displayed

Reported live: "after keyboard opens then closes again i have to click like 3 inches above whatever i want
to click to hit it. like that app isnt reverting the action part back but the displayed part moves back."
Confirmed zero keyboard-aware code existed anywhere in the app — no `visualViewport` listener, no
`interactive-widget` meta directive, no manual scroll/focus compensation in any modal or form — and that
this app's scroll architecture deliberately takes `<body>` out of normal document flow (`position: fixed`,
`overflow: hidden`) as a hard-won fix for the *unrelated* iOS PWA bugs documented earlier in this file
(phantom-toolbar-on-launch, touch-drag rubber-banding). Root cause matches a documented WebKit/PWA bug
class: absent `interactive-widget=resizes-content`, the keyboard pans the *visual* viewport instead of
resizing actual page layout, and that pan offset doesn't always reset cleanly on dismiss in standalone PWA
mode — exactly matching the symptom (content re-renders at the "right" position, touch coordinates stay
mapped to the stale panned offset).

Shipped the same two-layered defense pattern this exact gotcha class has used before (see MEMORY.md's iOS
PWA saga): (1) primary — `interactive-widget=resizes-content` added to `index.html`'s viewport meta tag,
so the keyboard resizes layout (affecting `100dvh`) instead of just panning; (2) defensive — a
`visualViewport` `resize` listener in `Layout.jsx` that forces `window.scrollTo(0, 0)` once the viewport
height returns to matching the full layout height (keyboard closed), a no-op when nothing was desynced.
Stated explicitly, matching this app's own established precedent for this bug family: **cannot be verified
in this environment** (no real iOS device, and Playwright/Chromium can't simulate the actual WebKit
keyboard-resize quirk) — shipped both layers regardless, flagged for on-device confirmation.

**Files:** `app/frontend/index.html`, `app/frontend/src/components/Layout.jsx`.
