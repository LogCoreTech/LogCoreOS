# 2026-08-30

## App-wide search + universal tags — 4 owner-reported follow-ups from actually using it

The owner tried yesterday's 8-increment search/tags rollout and came back with a short, concrete
list — three real UI bugs/gaps and one substantial feature request, all fixed/built in one sitting.

### 1. Notes' tag row was pinned instead of scrolling with the note

**Bug**: the tag input sat in its own `shrink-0` row above the note's own scrollable `<textarea>` —
always visible on screen regardless of how far you scrolled through a long note, instead of reading
as part of the note's own content. Owner: "i want it to stay fixed on top of the note and scroll
with it not stay fixed on that spot of the screen."

**Fix, `module_packages/notes/frontend/Notes.jsx`**: the textarea itself is no longer the scrolling
element — it now auto-grows to its own content height (a `useEffect` on `[editContent, note?.path]`
setting `el.style.height = 'auto'` then `scrollHeight + 'px'` via a new `textareaRef`), and the
OUTER wrapper (still a plain, `flex-1 min-h-0`-bounded div — the exact safe shape MEMORY.md's
Journal fixed-layout gotcha already established, just `overflow-y-auto` now instead of
`overflow-hidden`) is the real scroll boundary, containing the tag row and the textarea as two
ordinary stacked children instead of one pinned + one internally-scrolling. Verified live: a
seeded 80-line note's tag input visibly scrolled out of view when the container was scrolled down,
with no page-level scroll leak (the exact regression the gotcha warns about) — checked directly via
`document.body.scrollHeight` staying sane.

### 2. Contacts' tag field was still the old plain comma-separated text input

**Gap**: Contacts already had a `tags` field before yesterday's rollout (used in a client-side
filter), so wiring its OUTPUT into the shared vocabulary (Increment 3) read as "already done" — but
the INPUT itself, `ContactModal.jsx`'s plain `<input placeholder="Tags (comma-separated)">`, was
never actually replaced with the same `TagInput` pill picker every other module now uses. Owner
caught the gap directly: "tags on contacts are still the comma separated and not the new feature."

**Fix**: `ContactModal.jsx` gained a real `tags` array state (was folded into the giant `form`
object as a joined string before), a `tagSuggestions` fetch effect (pool-vs-personal resolved from
`isPoolContact` when editing, or the existing `keepPersonal` checkbox state when creating — matches
`ContactCreate.pool`'s own default-true behavior found during yesterday's Increment 3 verification),
and the plain input swapped for `<TagInput value={tags} onChange={setTags} suggestions={tagSuggestions} />`
— the exact same component `coreValues` already uses two fields below it in this same form. Verified
live: typed a new tag, got a real pill with a ✕ remove button, not comma-separated text.

### 3. App-wide search wasn't mentioned anywhere in the Help page

Owner: "probably should mention the new search feature to help page." Added two lines to the
existing `getting-started` section in `app/backend/content/help.json` (the one hand-authored
section not owned by any single module, matching where cross-cutting features like this belong) —
one `howto` line about the header search icon / Ctrl+Cmd+K, one `tips` line about tag-filtering
being shared across every module. Verified live: `GET /help` content includes both new lines.

### 4. Goals page rebuilt as a real hierarchy, matching Assets' own tree UI

The biggest of the four — a real UI redesign, not a bug fix. Owner: "i want the goals on goals page
to work similar to assets with the condense and expand buttons. where it shows them in their own
heirachy. with linked tasks also visible with it."

Researched `module_packages/assets/frontend/Assets.jsx`'s own tree first rather than guessing at the
pattern: a recursive `AssetRow` component, a `childrenMap` built via `useMemo` (groups by
`parent_id`, falling back to a `_root` bucket when a match's own parent didn't pass the current
filters — so a filtered-in child is never silently hidden just because its parent got filtered out),
an `expanded` `Set` state + a `toggle(id)` function, and a per-row ▸/▾ chevron that's only
interactive when the row actually has children.

**`Goals.jsx` rewritten to the identical shape** — `GET /goals` already returns every goal at any
depth flat with a real `parent_id`, so no backend change was needed, only a client-side grouping
pass exactly like Assets' own. New recursive `GoalRow` (module-level, not nested inside `Goals()` —
the MEMORY.md rule that components defined inside components remount every render) renders the
existing category badge/title/overdue tag/due-date/tag-pills/progress-% row, now indented by depth
with a chevron, collapsed by default (matching Assets' own `useState(new Set())` starting empty) —
the old flat list previously showed every goal, parent and child alike, as separate same-level
cards with just a small "Subgoal" badge; that badge is gone now since indentation itself is the
signal, the same way `AssetRow` never needed one either.

**Linked tasks visible in the hierarchy** — the genuinely new piece, since `GET /goals`'s own list
response doesn't carry each goal's linked tasks (only the single-goal detail endpoint does). Rather
than a new backend endpoint, `Goals.jsx` fetches the caller's own full task list once per tab/workspace
(`tasksApi.list()` for ME, or the pool's own task client for the pool tab — reusing `GoalModal.jsx`'s
existing `poolTaskApi(workspace)` helper, newly exported from there instead of duplicated) and groups
it by `goal_id` client-side into a `tasksByGoal` map — the exact same "fetch everything, group
locally" shape Assets' own tree already uses for parent/child grouping, just one level removed. A new
`TaskLeafRow` renders each linked task as a simple ✅/⬜ + title row nested one level deeper than its
goal, with a small "recurring" tag when applicable; clicking one opens the PARENT goal's own detail
modal (which already has full linked-task actions — unlink, the "counts toward this goal's progress"
toggle) rather than building a second place to edit a task from, keeping this a preview, not a new
edit surface.

**Verified live**: created a parent goal, a subgoal, and a task linked to the parent via the real
API; confirmed the subgoal and linked task were both hidden until the parent row's chevron was
clicked, then both appeared correctly nested and indented one level under the parent, task above
subgoal, progress percentages showing on both goal levels.

## Same-day follow-up: each top-level goal/asset gets its own card

Owner, right after seeing the new Goals hierarchy: "can you make the each of the top level goals
have its own card? so everything isnt all together. also change assets too that way." Both
`Goals.jsx` and `Assets.jsx` previously wrapped their ENTIRE tree — every root and all its nested
children — in one single `.card` div, so multiple unrelated top-level goals/assets rendered as one
visually undifferentiated block. Fixed in both files identically: the outer wrapper changed from
one `.card` containing a `.map()` of root rows to a plain `space-y-2` container whose `.map()`
produces one `.card` PER root, each containing that root's own row (which still recursively renders
its own subtree/linked tasks inside that same card via the normal expand mechanism — only the
TOP-level separation changed, nesting inside a root is unaffected). Verified live: created a second
top-level goal and a second top-level asset, confirmed each rendered in its own visually distinct
card instead of blending into the one before it. `eslint`/`vite build` clean.
