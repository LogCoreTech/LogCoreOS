## VAPID_SUBJECT auto-derived from the configured domain, and a real Web Push encryption bug found + fixed

Owner asked how to set `VAPID_SUBJECT` (the last open item from the 2026-08-15 push-notification
work — `docker/.env` still had no real value, so `POST /push/test` was 502ing against the
placeholder `logcore@localhost`). Corrected a misunderstanding along the way — VAPID has nothing to
do with user Apple ID/Google logins; it's a single, server-wide contact address stamped into every
push request, unrelated to any individual user's own push *subscription* (already per-user). Owner
then asked if it could be automatic rather than a per-user setting (a request based on the same
misunderstanding, redirected) — and it genuinely can: `services/push_service.py::_build_vapid_jwt`
now falls back to `hosting_service.effective_domain_url()` (the domain already configured via
Admin → Hosting, stored as a full `https://` URL — a valid VAPID subject as-is, RFC 8292 requires
`mailto:`/`https:`) whenever `settings.vapid_subject` is still the unconfigured placeholder, instead
of requiring an env-var edit + restart. Falls back to the old placeholder-only behavior when no
domain is configured at all (e.g. localhost-only dev instances). New tests:
`test_placeholder_subject_uses_configured_domain_automatically` /
`..._stays_placeholder_with_no_domain_configured`.

**Real bug found while diagnosing why "Send Test" still didn't produce a notification on the
owner's iPhone even after that fix and a real rebuild** (confirmed via the app's own logs it was no
longer 502ing — `send_push()` only ever returns success on a real 2xx from the push relay, not a
fake one). Walked the whole chain and ruled out everything else first: the stored subscription
(`brain/USERS/{name}/push_subscription.json`, freshly rewritten by a real disable/re-enable cycle,
pointed at `web.push.apple.com` with both `endpoint` and `keys` present), the frontend
subscribe/unsubscribe flow (`Notifications.jsx` — correctly calls the browser's own `unsubscribe()`
before re-subscribing, generating a genuinely fresh subscription each time, not reusing a stale
one), the service worker's `push` handler (`public/sw.js` — correctly parses the payload and calls
`showNotification()`), and iOS's own per-app notification settings (owner confirmed Allow
Notifications + all three display-style toggles were already on). That left the payload encryption
itself — `_encrypt_payload()` in `push_service.py`, a from-scratch RFC 8291 implementation (no
`pywebpush` dependency) — as the only untested link in the whole chain, and it had a real,
consequential bug: RFC 8291 §3.3's first key-derivation step requires **two separate,
sequentially-keyed** HMAC-SHA-256 calls (`PRK_key = HMAC(auth_secret, ecdh_secret)`, then
`IKM = HMAC(PRK_key, key_info || 0x01)` — note the required trailing HKDF counter byte on the
second call). The code instead collapsed both into **one** HMAC call, keyed by `auth_secret`
throughout, over the concatenated message, with no counter byte. The push service itself never
decrypts anything — it just relays opaque encrypted bytes — so it always returned a real 2xx
regardless; only the *receiving device*, deriving its own CEK/nonce correctly per spec from its own
private key, would ever notice the mismatch, fail AES-GCM tag verification, and silently discard
the notification with no visible error anywhere. This means Web Push has never actually been
deliverable on any device on this instance, for any user, independent of the VAPID subject issue —
the two bugs were stacked, not sequential (fixing VAPID_SUBJECT alone was necessary but not
sufficient; this was the real blocker for actual delivery).

**Fix verified two ways**, not just asserted: (1) a new test,
`test_encrypt_payload_is_decryptable_by_a_spec_compliant_receiver`, implements the RFC 8291
receiver side completely independently (a simulated client keypair, its own from-scratch correct
HKDF derivation — not calling back into `_encrypt_payload`'s own helpers, so it can't share a mutual
bug with the code under test) and asserts a real AES-GCM decrypt-and-verify round-trip succeeds. (2)
Confirmed the test actually catches the original bug, not just passes trivially: temporarily
reverted `_encrypt_payload` to the original one-HMAC-call version, re-ran the new test alone — it
failed with `cryptography.exceptions.InvalidTag`, the exact silent-decrypt-failure signature that
explains the real-world symptom — then restored the fix and confirmed all 8 tests in the file pass
again. Full backend suite: 1163 passed (up from 1160, +3 net — the 2 VAPID-fallback tests plus this
one). `black`/`isort` clean on both touched files.

**Confirmed working**: owner rebuilt, redeployed, and reported real notifications arriving on their
iPhone.

## Multi-device push: storage rebuilt from one subscription per account to a real per-device list

Immediately after confirming push worked, owner asked the obvious next questions: "did you make
sure it works on different known devices? does it also work on multiple devices on once? all these
need figured out now." Honest answer on the first: no physical devices exist in this environment to
test against, though the encryption fix above is receiver-spec-generic (not iOS-specific), so
there's good reason to expect it works the same on Android/desktop — a reasoned expectation, not a
verified one. The second question wasn't a maybe — checking the code found it flatly didn't work:
`push_subscription.json` was one fixed file per user, `save_subscription()` did a plain overwrite.
Enabling push on a second device would have silently stolen notifications from the first, no
warning, no error, just a device going quietly dark.

**Rebuilt storage as a list**: `get_subscriptions(user)` returns every device, keyed by `endpoint`
(re-subscribing the same device replaces just its own entry). Reads the old single-object format
transparently — no migration needed, the first save after this ships rewrites the file as a list
(matters for real: the owner's own existing subscription file was in that exact old format).
`send_push()` fans out to every device independently, one try/except per device so one
expired/unreachable device can't block the others.

**Real bug caught by the test I wrote to prove this worked, before it ever shipped**: the first
version wrote `any(_send_to_one(...) for sub in subs)` — `any()` short-circuits on the first `True`,
so only the FIRST device would ever actually get pushed to whenever it succeeded, silently skipping
every device after it. `test_send_push_delivers_to_every_device_independently` asserted both
endpoints were called and caught that only one was. Fixed by evaluating results into a list first,
then `any()` over that.

**Per-device removal, not just per-device delivery** — the other half of "figured out now."
Subscriptions gained `label` (client-guessed, e.g. "iPhone · Safari" — `Notifications.jsx`'s new
`_deviceLabel()`, a minimal `navigator.userAgent` sniff) and `created_at`. New `list_devices()`/
`delete_device()` expose a safe opaque id (`sha256(endpoint)[:16]`, never the real endpoint — a
live, sender-authenticated URL) so `GET /push/devices` / `DELETE /push/devices/{id}` can remove a
device that ISN'T the one making the request — the actual point, since removing an old phone you no
longer have has to work from whatever device you're currently on. `Notifications.jsx` gained a real
device list under the existing Enable/Disable/Test controls, each row with its own Remove button.
`DELETE /push/subscribe` (still "disable on this device") now requires the caller's own endpoint in
the body instead of wiping the whole account.

**Verified**: 19 tests in `test_push_service.py` (up from 8) — multi-device coexistence, same-endpoint
replace-not-duplicate, per-endpoint delete, the legacy-format read path, safe device-list metadata
(confirmed no endpoint/keys leak), fan-out delivery, one device's failure not blocking another's,
and per-device-only 410 pruning. Full backend suite: 1174 passed (up from 1163, +11 net).
`black`/`isort`/`eslint --max-warnings 0`/`vite build` all clean. `docs/API.md`'s Push Notifications
section rewritten for the new endpoints; `help.json` updated. Not yet live-verified with a genuine
second physical device — still only the owner's one iPhone confirmed; the fan-out path is covered
by tests but a real second-device click-through remains open, logged in `docs/TASKS.md`.

## Owner-requested security review of the notification changes — found and fixed a real SSRF

Owner: "when you are done i want you to go through and do security checks on these recent changes
on notifications." Walked auth/authz (all four new/changed endpoints correctly scope to
`current_user`, no path takes an arbitrary user id — `device_id` is only ever matched within the
caller's own subscription list), input validation, and XSS (labels render via plain JSX text
interpolation, never `dangerouslySetInnerHTML` — React auto-escapes) before finding the real issue.

**The finding**: `POST /push/subscribe`'s `endpoint` field had zero validation of what host it
actually points to, and `send_push()` does a genuine server-initiated HTTP POST to that exact URL
(carrying a signed VAPID auth header and an encrypted body, 10s timeout) every time ANY notification
fires — not just an explicit `/push/test` click, but every scheduled digest/overdue-alert too, and
those aren't behind any rate limit at all. This is a real Server-Side Request Forgery path: an
authenticated account (any role, not just admin) could point `endpoint` at an internal-only address
— the Docker socket-proxy, n8n's internal port, cloud instance metadata at `169.254.169.254` — and
get the server to make outbound requests to it on a recurring basis. **Pre-existing, not introduced
today, but meaningfully amplified by the multi-device rebuild earlier in this same session**: before
today, one account could only ever hold ONE stored subscription (each new subscribe silently
overwrote the last), capping this at one attacker-controlled URL per account. Removing that
accidental cap as part of shipping real multi-device support also removed the only thing bounding
this — an account could now register unlimited fake "devices," each a live SSRF trigger, fired
automatically by routine notification traffic with no extra action needed.

**Fixed same sitting, since this was found while implementing the exact code that made it worse**:
`push_service._validate_push_endpoint()` requires `https://`, resolves the hostname via
`socket.getaddrinfo()`, and rejects if any resolved address is private/loopback/link-local/
reserved/multicast/unspecified (Python's `ipaddress` stdlib classification, not a hand-rolled CIDR
check). Deliberately validates by "resolved IP must be public" rather than an allowlist of known
push-provider hostnames — providers multiply and change domains over time, and a stale allowlist
would just break real browsers going forward, while the IP-based check needs no maintenance.
Explicitly does **not** defend against DNS rebinding (the gap between this check and the real send
later) — documented as a deliberate scope call, not an oversight: legitimate push-provider domains
are stable, high-reputation domains with no realistic path to resolving privately, and full
IP-pinning on every single send wasn't judged worth the complexity for this app's actual threat
model. Paired with `_MAX_DEVICES_PER_USER = 10` as a second, independent bound on the amplification
factor regardless of whether the validation is ever somehow bypassed.

**Verified**: 8 new tests, including a `_fake_dns` autouse pytest fixture (real DNS lookups in unit
tests would make the whole file flaky/network-dependent) stubbing a fixed public IP by default, with
individual tests overriding it locally to exercise each reject path (private, loopback, cloud
metadata, non-https, unresolvable) plus the accept path and the device-cap boundary (including that
re-subscribing an already-registered device isn't blocked by the cap even at the limit). 31 tests
total in the file now. `docs/API.md` updated for the new cap/validation behavior and the `PATCH`
endpoint. Full backend suite: 1186 passed.
