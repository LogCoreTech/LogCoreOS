## Force-pushed yesterday's history rewrite, fixed two more real gaps it surfaced, added a leak-check Stop hook

Owner asked to push and self-fix any sync issue. `--force-with-lease` (implicit form) rejected with
"stale info" even against a freshly-fetched, verified-correct `origin/master` — root cause: the
implicit lease compares against `refs/remotes/origin/<branch>`, which is only meaningfully tied to a
NAMED remote, but this repo's own documented workflow pushes straight to the SSH URL rather than the
`origin` alias (HTTPS, for the updater's own unauthenticated cron fetches — see `docs/AGENTS.md`'s git
workflow section), so the lease had nothing reliable to compare against. Fixed with the explicit form
(`--force-with-lease=master:<verified-hash>`, confirmed via a direct `git ls-remote` first) — pushed
cleanly. `master` on `origin` now carries the redacted history from yesterday's rewrite.

**Real gap found right after**: the release tags (`v0.4.4`–`v0.7.0`) still pointed at the OLD,
unredacted commits even though they'd been correctly rewritten locally — a routine `git fetch` in
between had silently re-synced them back to origin's old versions (tags aren't fast-forward-protected
the way branches are, so a fetch just force-updates them to match whatever's on the remote). Re-ran the
same redaction pass (idempotent — no-op on `master`, correctly re-fixed every tag), cleared
`refs/original/*` again, `git gc --prune=now` again, verified clean across every ref, then force-pushed
all 14 tags individually.

**Owner asked directly whether the tags actually pointed to the right commits — a fair challenge, not
just reassurance-seeking, since the updater relies on exact tag targets.** Verified three independent
ways rather than just asserting it: (1) read `VERSION` at all 16 tags, confirmed every one matches its
own tag name exactly — this is precisely what would catch a `--prune-empty`-collapsed/misassigned tag;
(2) grepped both filter-branch runs' full logs for any skip/prune/empty message — zero, meaning
`--prune-empty` never actually fired on any of the 476 commits processed (it only fires when a
commit's tree becomes byte-identical to its parent's, and only 2 files in the whole repo were ever
touched); (3) `git fsck --full` came back completely clean. Cross-checking against the live demo host's
own tag surfaced one unrelated finding (its local `v0.7.0` pointed to a commit not in the canonical
history at all) — owner explained: they'd manually moved that tag locally because a later commit landed
after the original tag point, unrelated to anything from the rewrite.

**Confirmed a new release wouldn't self-heal the two live hosts on its own** — read `docker/update.sh`
directly rather than guessing: it lands updates via `git merge --ff-only "$new_commit"` (deliberate
safety design — refuses any non-fast-forward, explicitly logs "divergent local history" and aborts
rather than silently discarding local state). Since the demo host's and the beta client's local history
shared no commit hashes with the rewritten lineage past the leak point, any future release tag would
hit exactly that refusal and the host would just sit stuck on `ff-failed` forever, not corrupt or
auto-recover. Owner asked whether the updater itself should be changed to auto-resolve this (e.g., auto
fetch+reset on divergence) — pushed back: the ff-only refusal is the correct behavior for the general
case (protects against corruption, tampering, or any other unexpected divergence, not just this one
rare deliberate rewrite), and weakening it for a one-time event isn't worth trading away that safety
property for every future run. The actual fix is the manual one-time resync, not a permanent behavior
change to the updater.

**Manually resynced all three affected hosts** (this dev machine was already correct — the rewrite
happened directly on this checkout, never diverged): the demo VPS and the beta client's managed
instance both got `git fetch origin master --force && git reset --hard origin/master` plus a tag
re-fetch; the demo host's stray local `v0.7.0` was deleted and re-fetched clean. Deliberately did NOT
force a container rebuild on either — the actual application code is byte-identical to what's already
running (only git hashes and 2 markdown files changed), so a rebuild+restart would just be disruptive
downtime for zero functional gain. Verified clean on both afterward (no leaked strings in tracked repo
content; the client's own `brain/USERS/Daniel Love/` folder match found during the scan is their own
real account data on their own server, expected and unrelated).

**New `docs/hooks/leak_check.sh`, wired as a Stop hook**: scans uncommitted changes (tracked-file diffs
+ brand-new untracked files — `git diff HEAD` alone misses the latter entirely) and the tip commit's own
diff if it's new since the hook last ran, for real (non-private-range) IPv4 addresses and a few common
secret patterns (private key blocks, AWS access key IDs, hardcoded-looking key/secret/token/password
assignments). Advisory only, surfaced via the same `additionalContext` mechanism `commit_reminder.sh`
already uses — never blocks anything, just gives Claude a reminder to review before the next
commit/push. Enforces `docs/MEMORY.md` Security Rule 11 (no customer/tenant details in this public
repo), added directly because of this exact incident. Two real bugs caught testing it before relying on
it: `git status --porcelain`'s human-readable output quotes filenames containing spaces (like every
Daily Note), so naive parsing silently produced a mangled path that `[ -f ]` couldn't find — switched
to `git status --porcelain -z` (NUL-delimited, no quoting ambiguity) and fixed the offset math; a
grep pipeline for the secret-pattern check had `-q` (quiet, no output) piped into a second grep, which
is always empty — split into two real greps. Verified end-to-end with a synthetic leak (a fake IP +
fake AWS key), confirmed detection fires, confirmed a clean repo state produces no output, confirmed it
doesn't false-positive against its own pattern-matching code. Registered in `.claude/settings.json`
alongside the existing Stop hooks; documented in `docs/MAP.md`.

## Self-service fix for the `ff-failed` update state — Admin -> Updates gets a "Fix Automatically" button

Owner: "there is a good chance of this happening again" (any future ff-only refusal, not just today's
specific rewrite) — asked for a proper in-product fix rather than only a written notice for existing
users. Built directly against the real update pipeline rather than inventing a parallel one:

**`docker/update.sh`**: `do_update()` gained an optional `force_resync` param. When true, the landing
step is `git reset --hard "$new_commit"` instead of the normal `git merge --ff-only` — everything else
(backup, build, restart, health check, automatic rollback) is the exact same code path a normal update
already runs, not a duplicate. New `pending_resync` flag file (parallel to the existing
`pending_update`), checked in both `watch_mode()` and `--cron` mode; a resync flag takes priority over
a plain update flag if both are somehow present. The `ff-failed` log message also now prints the exact
manual recovery command inline, and mentions the new button.

**Backend**: `POST /update/resync` (mirrors `/apply` exactly — same 409-if-running/pending guards, same
"just write a flag file" shape; the backend still never touches git directly). `GET /update/status`
gained `resync_pending`. New `tests/test_update_service.py` (6 tests) — first-ever coverage for this
file; scoped to what this change touches, not a full retroactive backfill of the pre-existing
untested endpoints.

**Frontend**: the existing `ff-failed` warning box (added earlier today) gained a "Fix Automatically →"
button — only rendered when `last_update.result === 'ff-failed'` and nothing's currently running, so
there's no path to it outside that exact state. Opens `ResyncModal`: plain-language explanation, the
manual fix command in a copy-able code block, and a confirm-gated "Fix Automatically" button that calls
the new endpoint. Nothing happens without that explicit click.

**Then asked whether any OTHER failure state (`tag-failed`/`fetch-failed`/`signature-failed`/
`rollback`/`success-stamp-failed`) would benefit from the same button — checked each rather than
assuming: none would. `tag-failed`/`fetch-failed` have no resolved target to reset to at all;
`rollback` means the new code itself is broken, and resetting to the same target would just fail the
same way again; `success-stamp-failed` is a file-permissions issue git can't touch; and critically,
`signature-failed` is a deliberate security gate for hardened/managed instances — offering an easy
bypass there would be a real regression, not a convenience. Scoped to `ff-failed` only, deliberately.

**Then asked for a file-level diff preview ("so they can see what files are getting changed") for more
confidence before clicking.** Checked feasibility first rather than assuming: the backend container has
**zero git access** — `.dockerignore` excludes `.git` from the build, and the Docker build context is
scoped to `app/backend/` alone, so the running app can't reach the repo's history at all. The only
thing with real git access is `update.sh` on the host, reachable only through the same async
flag-file/polling channel (up to a ~60s round trip) — building a live in-app diff would mean the admin
waits up to a minute to see a file list. Presented the tradeoff via `AskUserQuestion` rather than
picking silently; owner chose the simpler path: a "See exactly what will change →" link in the modal
pointing straight at GitHub's own compare view between the installed and target version tags
(`github.com/LogCoreTech/LogCoreOS/compare/v<installed>...v<latest>`) — instant, zero new
backend/host mechanism, and arguably more trustworthy than a locally-computed summary since it's the
same canonical public source anyone can already check.
