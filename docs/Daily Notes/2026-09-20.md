## Closing a process gap: two flagged follow-ups that never reached TASKS.md

Owner asked "was there anything not done per TASKS.md, I feel like I'm forgetting something." A scan of the active backlog found nothing owed from before this week's Homes work, but surfaced a real gap: two things had been flagged directly to the owner in conversation and written into `docs/MEMORY.md`/the Homes plan file, but never actually logged into `TASKS.md` — the one place that's supposed to make sure a flagged-but-deferred item doesn't just quietly disappear. Owner chose to build both immediately rather than only log them.

**1. The 6 other `type="number"` inputs** flagged when the original Homes comma-bug was fixed (2026-09-18) but never touched: `RecurrencePicker.jsx` (recur-every interval, day-of-month), `module_packages/goals/frontend/MetricPicker.jsx` (a metric config's numeric target), `pages/settings/Notifications.jsx` (digest hour/day-threshold settings), `components/assetDisplay.jsx` (a custom Asset template's own numeric field type), `module_packages/goals/frontend/GoalModal.jsx` (a manual-metric goal's "log a new value" field), and `module_packages/contacts/frontend/ContactModal.jsx` (height/weight). All switched to `type="text" inputMode="decimal"|"numeric"`. Two required more than a type swap: `RecurrencePicker.jsx`'s two fields already had a safe `parseInt(...) || fallback` in their `onChange`, so those needed no logic change at all; `MetricPicker.jsx`/`Notifications.jsx`/`GoalModal.jsx` did NOT have that safety net — `type="number"` had been doing the "reject non-numeric text" job implicitly, so removing it required adding an explicit `Number.isNaN()` guard in each `onChange` (previously invisible because the browser never let a bad value reach the handler at all). `GoalModal.jsx`'s manual-log field had a second, quieter bug on top: an unparseable value became `NaN`, which isn't valid JSON — `JSON.stringify(NaN)` silently serializes to `null`, so a bad value wouldn't error, it would just vanish into a null write. Fixed the same call site. `ContactModal.jsx`'s height/weight needed the least — the backend's `height_cm`/`weight_kg` fields are already `float | None` on the Pydantic model, which coerces a numeric string and cleanly 422s on garbage, so removing the risky input type was the whole fix there.

**2. Homes' own deferred `SearchProviderSpec`** — noted in the original 2026-09-18 plan as "a real, cheap potential fast-follow, not an oversight": a home is now findable by name/address via the app-wide search bar itself, the reverse direction of Homes' own tag-based aggregation. New `_search_homes` in `homes/manifest.py`, folding personal + household/team pool visibility the same way `list_homes()` already does. The one real design subtlety, caught before writing the test rather than after: every result's `tags` field must be hardcoded `[]`, never the home's own `tag` — otherwise a home would self-referentially show up as one of its own "tagged items" in `GET /homes/{id}/items`, since that endpoint's `search_service.search()` call fans out across every active provider, including this brand new one. Verified directly with a dedicated test (`test_never_matches_its_own_tag_or_any_tag_search`) rather than just reasoning it through. Also had to add a `?homeId=` deep-link handler to `Homes.jsx` (mirroring `Calendar.jsx`'s own `?event=` pattern) — without it, a home would show up in search results and be clickable, but clicking wouldn't actually select that home on the page, since `recordParam: 'homeId'` had been declared in the frontend manifest back on launch day but nothing ever read it.

12 new backend tests across the two follow-ups; full suite still green. black/isort/eslint/build all clean. Also updated `docs/RELEASING.md` per a separate owner ask: added a step requiring each changed module's own `manifest.py` `version` field to be bumped at release time (separate from the app-wide `VERSION` bump), since `services/mod_store_service.py`'s catalog endpoint surfaces that field directly in Admin → Mod Store and it would otherwise silently go stale.

## A real, unrelated crash: "Add transaction" in Finance

Owner reported clicking Add Transaction in Finance crashed with "cannot access uninitialized variable," and asked whether it might be connected to the `type="number"` fix above — checked first, confirmed no: `TransactionModal.jsx` had zero diff in this session (`git status` clean) and its Amount field was already `type="text" inputMode="decimal"`, never `type="number"` to begin with.

The real cause, found by reading the file directly: a genuine, pre-existing temporal-dead-zone bug, unrelated to anything shipped this week. `snapshot = () => JSON.stringify({..., toBookId, toAccountId})` (built 2026-09-04 for the "warn before discarding unsaved changes" feature) was defined near the top of the component and immediately invoked via React's lazy-`useState`-initializer convention (`useState(snapshot)` calls the function once, synchronously, during the first render) — but `toBookId`/`toAccountId` themselves weren't declared until ~50 lines further down in the same function body. `const`/`let` stay in the temporal dead zone until their own declaration line actually executes, so every call to `snapshot()` during that first render threw `ReferenceError: Cannot access 'toBookId' before initialization`, unconditionally, on every single mount — meaning every "Add transaction" (and "Edit transaction," same modal) click since whenever this state was originally added. Fixed by moving the 3 `useState` declarations up above `snapshot`'s own definition — no logic change, just reordering. Full writeup + the general "how to apply" for any lazy initializer that closes over later-declared state: `docs/MEMORY.md`'s new Known Gotchas entry. eslint/build clean, live via the frontend build (no backend involved).
