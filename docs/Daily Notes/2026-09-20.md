**1. Two required more than a type swap: `RecurrencePicker.jsx`'s two fields already had a safe `parseInt(...) || fallback` in their `onChange`, so those needed no logic change at all; `MetricPicker.jsx`/`Notifications.jsx`/`GoalModal.jsx` did NOT have that safety net — `type="number"` had been doing the "reject non-numeric text" job implicitly, so removing it required adding an explicit `Number.isNaN()` guard in each `onChange` (previously invisible because the browser never let a bad value reach the handler at all). `GoalModal.jsx`'s manual-log field had a second, quieter bug on top: an unparseable value became `NaN`, which isn't valid JSON — `JSON.stringify(NaN)` silently serializes to `null`, so a bad value wouldn't error, it would just vanish into a null write. Fixed the same call site. `ContactModal.jsx`'s height/weight needed the least — the backend's `height_cm`/`weight_kg` fields are already `float | None` on the Pydantic model, which coerces a numeric string and cleanly 422s on garbage, so removing the risky input type was the whole fix there.

Also had to add a `?homeId=` deep-link handler to `Homes.jsx` (mirroring `Calendar.jsx`'s own `?event=` pattern) — without it, a home would show up in search results and be clickable, but clicking wouldn't actually select that home on the page, since `recordParam: 'homeId'` had been declared in the frontend manifest back on launch day but nothing ever read it.

## A real, unrelated crash: "Add transaction" in Finance

Owner reported clicking Add Transaction in Finance crashed with "cannot access uninitialized variable," and asked whether it might be connected to the `type="number"` fix above — checked first, confirmed no: `TransactionModal.jsx` had zero diff in this session (`git status` clean) and its Amount field was already `type="text" inputMode="decimal"`, never `type="number"` to begin with.

The real cause, found by reading the file directly: a genuine, pre-existing temporal-dead-zone bug, unrelated to anything shipped this week. `snapshot = () => JSON.stringify({..., toBookId, toAccountId})` (built 2026-09-04 for the "warn before discarding unsaved changes" feature) was defined near the top of the component and immediately invoked via React's lazy-`useState`-initializer convention (`useState(snapshot)` calls the function once, synchronously, during the first render) — but `toBookId`/`toAccountId` themselves weren't declared until ~50 lines further down in the same function body. `const`/`let` stay in the temporal dead zone until their own declaration line actually executes, so every call to `snapshot()` during that first render threw `ReferenceError: Cannot access 'toBookId' before initialization`, unconditionally, on every single mount — meaning every "Add transaction" (and "Edit transaction," same modal) click since whenever this state was originally added. Fixed by moving the 3 `useState` declarations up above `snapshot`'s own definition — no logic change, just reordering. Full writeup + the general "how to apply" for any lazy initializer that closes over later-declared state: `docs/MEMORY.md`'s new Known Gotchas entry. eslint/build clean, live via the frontend build (no backend involved).

## App-level 2FA (TOTP) — the last open item from the July security audit

Owner: "I suppose we can begin the 2fa pass." Researched via 3 parallel Explore passes (backend auth flow, frontend login/settings UI, admin-policy/audit-log precedent) plus direct verification of every load-bearing file before trusting it, then a full plan-mode pass (`/home/logcore/.claude/plans/whimsical-brewing-wolf.md`).

**The one finding that shaped the whole design**: `login_attempt()` succeeding used to immediately mint a full session in the same call, with zero intermediate state — the `must_change_password` flag (confirmed client-side-only enforcement) was explicitly rejected as a template for the real 2FA gate, since a second factor has to intercept *before* session-minting, not nag after it. Fixed in both `/login` and `/token` (they shared the identical vulnerable shape): a `totp_enabled` user now gets `{"totp_required": true, "pending_token": ...}` instead of a session — a short-lived (5 min) JWT carrying `purpose: "2fa_pending"` + `mode: cookie|bearer` claims (one `/2fa/verify-login` endpoint serves both callers), stateless, no revocation list. Wrong-code attempts reuse `auth_service`'s existing account-lockout trio — wrong passwords and wrong TOTP codes now share ONE lockout counter, not two.

New `services/totp_service.py`: `pyotp` for secret gen/verify, `qrcode[pil]` for the QR (reuses the already-present Pillow dep — zero new imaging dependency), Fernet field-level encryption of the stored secret mirroring `infisical_loader.py`'s own `_cipher()` pattern exactly (new `TOTP_ENCRYPTION_KEY` env var, graceful plaintext fallback if unset), bcrypt-hashed one-time recovery codes (same `hash_password`/`verify_password` real passwords use). New `routers/auth/totp.py` sibling (7 endpoints) wired into the existing `routers/auth/__init__.py` package-split convention.

Owner resolved the admin-policy design question directly: *"have it opt in per user user settings per account and then have a toggle setting in admin to make it mandatory for every user or admins only or optional"* — shipped as `require_2fa: "off"|"admin"|"all"` on Admin → General, with a self-lockout guard (an admin can't require 2FA for others before enrolling themselves — mirrors the existing last-admin-lockout guard shape but checks 2FA enrollment, not admin scarcity). Admin can also reset a user's 2FA from their User Detail page. Same answer also surfaced two related-but-separate asks — admin/self password-recovery tooling, and self-service email/name editing — deliberately sequenced as an immediate follow-up pass, not built this round (owner: *"Finish 2FA first, then the other two right after"*); logged under TASKS.md → Now.

Frontend: new `pages/settings/Security.jsx` (enroll/manage, own route, matches the existing one-page-per-concern settings split), `Login.jsx` gained a 3rd `mode` value (`'totp'`) for the post-password verification step (6-digit code or a recovery code), `Admin → General`/`UserDetail`/`AuditLog` each gained their corresponding pieces.

35 new backend tests (enrollment, login flow, shared lockout, admin-policy self-lockout, admin reset, the `must_setup_2fa` nag flag) — full backend suite 1624 passed, 0 failures. black/isort clean. Frontend eslint clean, `npm run build` clean. Not live-verified in a real browser (no browser automation available in this environment, flagged per this project's own standard) — manual walkthrough checklist is in the plan file for whenever the owner tests by hand.

**Follow-up same day**: owner asked "can 2fa be disabled if its not mandatory enabled?" — yes for an opt-in user, but checking the actual code to answer honestly surfaced a real gap: `disable_totp()` never checked the admin policy at all, so a user under a *mandatory* policy could still self-disable with zero server-side block (the policy only ever drove the client-side "please enroll" nag, never enforced staying enrolled). **Live deploy**: owner asked to "relaunch app to install dependencies." Rebuilt the `app` image (`docker compose build app` — `pyotp-2.9.0`/`qrcode-7.4.2` installed cleanly) and recreated the container; confirmed healthy and all 7 new `/2fa/*` routes registered via direct `app.routes` inspection inside the running container. Generated a real `TOTP_ENCRYPTION_KEY` and set it in `docker/.env` before recreating — deliberately done now, before this instance has any 2FA enrollments, since setting it later would be free but rotating it after even one enrollment permanently breaks that user's stored secret. **That surfaced a real pre-existing bug**: the key wasn't taking effect inside the container at all — `docker-compose.yml`'s `app` service only passes through env vars explicitly listed in its own `environment:` block, and neither the new `TOTP_ENCRYPTION_KEY` nor the existing `INFISICAL_CACHE_KEY` (present since 2026-08-22) was ever listed there, so `INFISICAL_CACHE_KEY` had silently never reached any container despite being fully implemented and documented. Harmless on this self-hosted instance (no `INFISICAL_TOKEN`, so the Infisical cache files never exist), but would silently defeat that encryption on any managed-hosting instance using this same compose file. Fixed by adding both keys to the `environment:` block; confirmed via `totp_service._cipher()` returning a real Fernet instance inside the running container after the fix. Full writeup + the general "how to apply" for any future optional `os.environ`-read secret: `docs/MEMORY.md`'s new entry.
