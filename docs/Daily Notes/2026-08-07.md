## Nav button can target a specific dashboard, not just land on the current default

Owner: "i want the nav button block to be able to select to go to a certain dashboard not just the
module itself." `dashboard` was already a pickable module in the "Navigate To…" target dropdown (a
real `ALL_MODULES` entry), but had no "specific record" option — so picking it could only ever mean
"wherever `/` currently resolves to," i.e. your current default dashboard, which changes over time
and isn't the same thing as "go to *this* dashboard."

**Fixed with the same generic mechanism every other module's record-linking already uses, not a new
one.** `Dashboard.jsx` already reads `?id=<dashboardId>` — that's the existing mechanism the
dashboard switcher itself uses — so this only needed three small, mechanical additions:

- `deepLinks.js`: `dashboard: 'id'` added to `RECORD_PARAM`, so `deepLinkUrl('dashboard', someId)`
  now correctly produces `/?id=<someId>` instead of falling back to the bare `/`.
- New `DashboardPicker.jsx` — a plain `<select>` over `dashboardsApi.list()`, the exact same shape as
  `finance/FinanceBookPicker.jsx` — registered in `ModuleAndRecordPicker.jsx`'s existing generic
  `RECORD_PICKERS` map (`dashboard: DashboardPicker`). Since that map is already keyed generically by
  module id and the "specific record" rendering path doesn't special-case any one module, this was
  the only wiring needed — the whole-page/section/record three-way choice built the day before
  already had a slot for exactly this shape.
- `_actions.py`'s `_resolve_record_title()` gained a `dashboard` branch using
  `dashboards_service.find_dashboard()` — the same access-checked lookup pattern every other
  module's branch already uses there — so the button's default label shows the *target* dashboard's
  real name instead of a generic "Go to Dashboard."

**Verification caught one wrong assumption in my own test, not a bug**: I initially expected the
button's default label to read "Go to My Target Dashboard," but it actually showed just "My Target
Dashboard" — which is correct, not broken. `NavButtonBlock`'s label logic (`data.label || data.title
|| \`Go to ${moduleLabel}\``) gives a resolved title priority over the generic fallback, exactly
matching how every other record-linked nav button already behaves (a task target shows the task's
own title, not "Go to Tasks"). Fixed the test's expectation once I traced through why, rather than
assuming the app was wrong.

**Verified via isolated Playwright** (backend + synthetic brain, same methodology as every round this
week): created two dashboards, added a nav_button on one targeting the other by id, confirmed the
`href` resolves to `/?id=<target>`, confirmed the default label shows the target's real name, and
confirmed clicking it genuinely navigates to and renders the target dashboard (not just a plausible
URL — the page actually shows the target's own name after the click). Full backend suite green
(`test_dashboards_service.py`, 18 passed), `npm run build` and eslint clean (0 new warnings beyond
this file's existing pattern).

## Dashboard Templates + grouped navigation

Owner: "the navigation to other dashboards is too inconvenient and we still need to add dashboard
templates like in assets... templates should not be mandatory as they are with assets. just a easy
way to make the same dashboard. would still like the way that changing the template updates all the
dashboards though... group them where the template is the 'folder'... unless you have a better idea
which you should ask me about it."

**Three design forks, asked before writing any code, not assumed.** Read Asset Templates' full
implementation first (the explicit mirror target) to ground the questions in what's actually
buildable, then used `AskUserQuestion` with a "Recommended" option on each — all three picked:

1. **Shared subject** — a dashboard made from a template picks one contact or asset as its "subject";
   block configs can reference "this dashboard's own contact/asset" instead of a fixed id.
2. **Block set stays synced, layout goes independent** — editing a template's blocks (add/remove/
   retype) updates every dashboard made from it automatically; each dashboard's own position/size,
   once a block exists there, is that dashboard's alone to arrange.
3. **Mirror Asset Templates exactly** — two-tier: admin-managed global templates + everyone's own
   shareable personal ones.

**The mechanism that makes (2) true without a parallel "resolve live" code path.** Assets resolve
their template at *read* time and never store structure on the instance. A dashboard's `blocks` array
is read by too many existing places (`render.py`, `dashboard_index.py`, the router) to introduce a
second, parallel shape — so instead, `dashboards_service._sync_templated_dashboard()` reconciles a
templated dashboard's stored `blocks` against its template's current blocks **on every read**
(self-healing, the same shape `resolve_default_dashboard_id` already uses in this file), persisting
only if something actually changed. The reconciliation itself (`_sync_blocks_from_template`) is one
pure function, keyed by a stable per-slot id: an existing slot keeps its own stored `layout` and takes
fresh `type`/`config` from the template; a new slot gets an auto-stacked layout; a slot the template
no longer has just disappears. That's the entire live-sync mechanism — no resolver, no index, no
router endpoint needed to change. The generic `PATCH /dashboards/{id}` additionally enforces
layout-only edits for a templated dashboard server-side (`_apply_layout_only`), so the guarantee holds
even against a client that ignores the UI entirely.

**`"$subject"` — a sentinel resolved once, centrally, not a mechanism every resolver learns about.**
A template's block config can use the literal string `"$subject"` on a `contact_id`/`asset_id` field;
`render.py::render_block()` substitutes it with the dashboard's own `subject_id` in exactly one place
(`_resolve_subject_config`) before any resolver ever runs — so none of the ~10 existing record-linked
resolvers needed a single line touched. A `"$subject"` that survives unsubstituted (no subject picked
yet) locks the block with `locked_reason: "no_subject"` instead of a confusing generic not-found.
`BlockPicker.jsx` only offers the "$subject" checkbox on a field whose `kind` matches the template's
own declared subject type, so a mismatched field can't even be authored through the UI.

**Two-tier templates, personal sharing included** — new `services/dashboard_templates_service.py`
mirrors `assets_service.py`'s template section closely enough that reading one explains the other
(`visible_templates`, `create_template`/`update_template`/`delete_template`,
`share_template`/`respond_to_template_share`, `template_reference_count`/delete guard). Found
`file_service.py::dashboard_templates_path(user_name)` already existed, unused, seeded speculatively
when Dashboards first shipped — reused it as the personal store; added
`global_dashboard_templates_path()` as its sibling.

**Grouped navigation, the actual UX ask.** `list_visible_dashboards()` denormalizes
`_template_label`/`_template_icon` onto every returned item (`_attach_template_labels`, same
rationale as `assets_service.attach_templates` — works even for a shared dashboard whose template the
viewer doesn't own). `DashboardSwitcher.jsx` groups by that label into collapsible sections (default
expanded, "Other" bucket for ungrouped) whenever there's no active search — searching flattens back to
a plain list, since browsing structure and finding one item are different tasks. `DashboardPicker.jsx`
(the nav_button target picker) got the same grouping via native `<optgroup>` — still "a dropdown for
quick and easy selection" per the owner's own words, just organized.

**New UI**: `CreateDashboardModal.jsx` (blank or from-a-template, with a Contact/Asset subject picker
when the template requires one) replaces the old direct blank-create calls; `DashboardTemplateManager.jsx`
mirrors `TemplateManager.jsx`'s list/edit/share structure but the per-template form manages a block
list (via `BlockPicker.jsx` reused in a new `templateMode`) instead of field definitions — no
grid/layout editor needed there at all, since template blocks have no stored layout to begin with.
`DashboardSettingsModal.jsx` gained "Change subject" and "Detach from template" (the escape hatch that
freezes a dashboard's current blocks/layout in place as an ordinary freeform dashboard, for the rare
case a specific instance needs to diverge beyond what the template allows).

**Scope stated up front**: a templated dashboard's block *set* is entirely template-derived for v1 —
no per-instance one-off extra blocks (detach if you need that). `nav_button`'s target (a module+record
composite, not a plain contact/asset field) doesn't get `$subject` support this round.

**A pre-existing bug found and fixed alongside this, not part of the ask**: `Layout.jsx`'s
notification-bell `respond()` had no case for `dashboard_share` (dashboard *instance* sharing, shipped
when Dashboards first launched) — it fell through to `assetsApi.respondShare(n.id, accept)`, a
completely different call shape than `dashboardsApi.respondShare` actually needs
(`owner, dashboardId, accept`, not a bare notification id). Fixed together with adding the equivalent
new `dashboard_template_share` case, since both are the same category of gap.

**Verified**: 13 new backend tests (`test_dashboards_service.py`) covering template CRUD + the
referenced-template delete guard, sync-on-read add/remove/retype propagation, per-instance layout
surviving a template change, the layout-only PATCH enforcement against a tampered payload, `$subject`
substitution resolving two different dashboards to two different contacts, the `no_subject` lock, and
detach-stops-sync — full suite **566 green**. `npm run build`/`eslint` clean. Isolated Playwright
(separate backend + synthetic brain): created a global "Client Overview" template (contact subject, a
`$subject`-linked block + a fixed one), made two dashboards from it for two different contacts,
confirmed each rendered its own contact's data, confirmed adding a block to the template propagated to
both instances without touching either directly, confirmed a per-instance layout customization
survived that same template edit while the sibling instance's copy of the same slot stayed untouched,
confirmed a tampered-PATCH retype attempt was rejected, and confirmed via screenshot that the grouped
switcher (two template groups + an "Other" bucket holding every pre-existing dashboard from earlier
rounds this week), the templated dashboard's settings panel (Uses template / Change subject / Detach),
and the template editor all render exactly as designed. 22/23 automated checks passed; the one failure
was my own test script clicking the wrong template's "Edit" button (confirmed via screenshot — the app
was right, the test was wrong).
