## Third follow-up same day: weight entered in lbs stored (and displayed) as if it were kg

Owner reported entering 155 (lbs) and seeing 342 on the view page — 155 × 2.20462 ≈ 342, the exact
signature of a value being stored as raw kg and then converted to lbs for display without ever
being converted from lbs to kg on the way in.

**Root cause**: `weight_kg` is a canonical-kg field by contract — both the backend's `format_weight()`
and `ContactDetail.jsx`'s local `formatWeight()` always multiply by 2.20462 to render lbs. Height
already gets this right: `ContactModal.jsx` keeps separate `heightFt`/`heightIn` entry state that's
converted to canonical `height_cm` via `commitHeightFtIn()` on every change. Weight had no
equivalent — its input was bound directly to `form.weight_kg` with no unit conversion at all, so
typing "155" while "lbs" was selected wrote `weight_kg: 155` straight through.

**Fixed** by mirroring the height pattern: new `weightDisplay` state holds the number in whichever
unit is currently selected (derived from `weight_kg`/`weight_unit` on load), `commitWeight()`
converts it to canonical kg on every keystroke, and `changeWeightUnit()` re-converts the displayed
number when the lbs/kg toggle itself changes (so flipping units doesn't reinterpret the same digits
under a different scale). Input `max` also now varies by unit (500 kg / 1102 lbs — was hardcoded to
500 regardless of unit, which silently capped a lbs entry far too low).

**Data note**: this only fixes entry going forward — anyone who already saved a weight has a
corrupted `weight_kg` value sitting in storage (e.g. `155` where the real value is `~70.3`).
Re-entering the weight once through the fixed editor corrects it; no backend data migration was
run, since there's no way to distinguish an already-correct small kg value from an already-wrong
former-lbs value after the fact.

**Testing**: `eslint` clean on `ContactModal.jsx` (0 new errors), `vite build` clean, relaunched via
`bash launch.sh --skip-build` and confirmed healthy.

## Fourth follow-up same day: weight round-trip drift (155 -> 154) — needed 1 decimal, not whole numbers

*and* the way back out to display compounds: 155 lbs → round(70.31 kg) = 70 kg stored → round(70 ×

## Seventh follow-up same day: Journal page still scrolled — textarea-in-flexbox quirk

Owner confirmed the redesign looked right but the page still scrolled ("it needs locked"). Root
cause: a `<textarea>` set directly as a flex item (`flex-1 min-h-0`, same treatment given to a
plain `<div>` in `Chat.jsx`'s message pane) doesn't reliably honor `min-height: 0` shrinking the
way an ordinary block element does — form controls get special-cased automatic-minimum-size
handling in the flex sizing algorithm, and in practice that let the textarea force its container
(and therefore the whole page, since `<main>` is the outermost scrollable ancestor and `html`/`body`
are already `overflow: hidden`) taller than the viewport. This is a well-documented flexbox +
form-control interaction, not specific to this app.

**Fixed** by not making the textarea itself the flex item: wrapped it in a `<div className="flex-1
min-h-0 overflow-hidden">` (an ordinary div, which shrinks correctly) and set the textarea to `w-full
h-full` so it just fills whatever box its wrapper resolves to, plus `overscroll-contain` on the
textarea itself so exhausting its own internal scroll doesn't chain into scrolling `main`. General
lesson for any future page using this fixed-layout pattern (`flex flex-col flex-1 min-h-0`, per
`Chat.jsx`'s shape): plain divs are safe as the flex-1 scrolling item; form controls (`textarea`,
`input`) are not — wrap them.

**Testing**: `eslint` clean, `vite build` clean, relaunched via `bash launch.sh --skip-build` and
confirmed healthy. No automated browser available in this environment to visually re-verify scroll
behavior directly — flagging that this is reasoned from the known CSS spec behavior and a live
report, not confirmed against a running browser session; ask the owner to double check as their
next real-world test.

## Ninth follow-up same day: app-wide — root cause found in Layout.jsx's shared CSS, not Journal

Owner pushed back on the eighth follow-up's "probably stale cache" conclusion with a sharper
observation: this happens on *every* module, and it's not just nested-scroll bleed — the app's own
mobile top header (which lives outside `<main>` in `Layout.jsx` and structurally should never move
no matter what scrolls inside `main`) moves too. Only the `position: fixed` bottom nav stays
anchored. Asked one clarifying question (`AskUserQuestion`) given how high-blast-radius and
historically fragile this exact code area is — confirmed: installed iPhone PWA (home-screen icon),
not a browser tab, not Android, not desktop.

That answer matches the exact bug class already in `docs/MEMORY.md` (the footer-gap saga, five
attempts, confirmed-on-device 2026-07-29) — but a different symptom of it. Root cause: iOS Safari
(including standalone PWA mode) has a long-documented quirk where `overflow: hidden` on `html`/
`body` doesn't reliably stop a touch-drag from scrolling the whole document, separate from the
already-fixed phantom-toolbar bug. Since the previous Playwright test already proved `main`'s own
containment logic is correct (zero overflow, both mobile and desktop, even with forced long
content), this app-wide symptom sits one level up, in the shared `html`/`body` rules — consistent
with the owner's own diagnosis, not something further work on individual pages could have fixed.

**Fix**: `body` in `index.css` gets `position: fixed` back (removing it from the scrolling flow
