## Goals rebuilt as a real, independent module — `module_packages/goals/`, the 14th package overall but NOT part of the Mod Store rollout above

Proceeded directly into Goals immediately after the rollout's own migration-verification pass, per
the owner's direction. Unlike every module converted today and every day before it, there was no
`routers/goals.py`/`services/goals_service.py` to move — "Goals" had never been a real backend
module at all, just Task records with `type=="goal"`, filtered client-side, riding on Tasks' own
`require_module("tasks")` gate (`App.jsx`'s `/goals` route used `moduleId="tasks"`; no
`require_module("goals")` existed anywhere). The owner asked for it to become a real module with a
meaningfully bigger feature set than Tasks' old goal-flavor ever had, so this was scoped through an
extensive multi-round plan-mode interview before any code was written (plan file:
`/home/logcore/.claude/plans/i-want-you-to-composed-scone.md`), then built in one sitting. Some
details evolved during actual implementation, noted below where they diverge from the plan.

**New module: `module_packages/goals/`, NOT locked** (`uninstallable=False`, an ordinary optional
module like Assets/Contacts/Finance) — `manifest.py` declares `owned_brain_paths=["Goals"]`, 7
`owned_agent_tools` (2 read-only: `list_goals`/`get_goal`), `owned_block_types=["goals_progress"]`,
and one guarded upgrade migration, `m031_migrate_goals` (the next available id after Finance's own
`m030`). `backend/service.py` (431 lines) is the core logic, and deliberately stays FULLY inside
this package — unlike `task_service.py`/`assets_service.py`/etc., which stayed core across every
prior conversion specifically because of real external consumers, nothing outside this package needs
Goals data directly. Goals does not get the per-user share-handshake pattern Assets/Finance/
Contacts/Notes use (no `shared_with`/`contributors` on an individual goal — only pool visibility),
which means `services/user_deletion_service.py` needed **zero** Goals-specific handling: a user's
personal goals are deleted with the rest of their Brain folder, the same as their Tasks already are.
`backend/router.py` (272 lines), `backend/dashboard_block.py` (the `goals_progress` block, personal-
only), `backend/agent_tools.py` (158 lines, 7 tools: `list_goals`/`get_goal`/`create_goal`/
`update_goal`/`delete_goal`/`link_task_to_goal`/`unlink_task_from_goal`).

**Data model** (`Goals/goals.json` per store — personal, `_household`, `_team`): `id`, `title`,
`notes`, `category`, `parent_id` (a self-pointer, unbounded depth, cycle-guarded — directly mirrors
`assets_service.py`'s own `parent_id`/`collect_subtree_ids` pattern), `due_date` (fully **optional**
now — the old `goal_requires_due_date` validator was dropped along with `type=="goal"` itself),
`status` (pending/done, the manual fallback when no metric/children drive the number), `metric`
(nullable, see below), `created_by`/`created_at`/`updated_at`.

**Task changes (stays core) — a real removal, not just an addition.** Task gained a new
`goal_id: str | None` field (`routers/_task_models.py` + `task_service.py` — mirrors the existing
`asset_id` field exactly). `type=="goal"` was removed entirely from Task's `Literal` type — a goal is
no longer a kind of Task at all. This forced real cleanup: `task_service.cleanup_done_goals()` (the
old "Clear completed" mechanism) was deleted outright, since Goals now owns that concept over real
Goal records; `priority_service.py`'s `_pending_non_goal()` helper simplified to a plain `_pending()`
(the goal-exclusion filter was dead code once `type=="goal"` became impossible); `recurring_service.py`'s
`t.get("type") in ("recurring", "goal")` simplified to just `"recurring"`;
`module_packages/tasks/backend/dashboard_block.py`'s old `resolve_goals_progress`/`goals_progress`
`BlockSpec` (and its dead `and t.get("type") != "goal"` filter inside `resolve_due_today`) were
removed entirely — that block moved wholesale into Goals' own package, rebuilt to show real computed
progress instead of a bare task list; `module_packages/tasks/backend/router.py`'s old
`POST /tasks/goals/cleanup` endpoint was removed; `module_packages/tasks/backend/agent_tools.py`'s
`type` enum on `add_task`/`create_tasks` lost `"goal"` (and gained `goal_id` as a new optional input,
including on `create_tasks`' per-item schema, so the AI's "break this goal into tasks" flow can set
`goal_id` directly when creating the breakdown tasks — the AI-links-them-automatically behavior the
owner asked for during scoping).

**Migration (`goals:m031_migrate_goals`) does more than mark-installed.** Same guarded idiom as every
optional module's own (checks `_system/features.json` existence to distinguish upgrade from fresh
install), but it also converts every existing `type=="goal"` Task into a real Goal record (preserving
id/title/category/due_date/notes/status/created_at) and removes it from `tasks.json` — across every
real user (both workspaces) AND both pool pseudo-users (`_household`, `_team`). Tested directly with
a real pre-existing `type=="goal"` task written to disk exactly as an old instance's `tasks.json`
would have it, confirming both the personal AND pool conversion paths work. A fresh install correctly
starts with goals NOT installed, same as every other optional module.

**Milestone: `features_service.py`'s `_CORE_MODULE_IDS` — which was `["goals"]` after Finance's own
conversion, the last hardcoded-core id in the whole app — is now `[]`, completely empty.** Every
module in the entire app is now either a converted `module_packages/` entry or permanent
cross-cutting infrastructure the Mod Store plan's own closing note never intended to convert. Frontend
mirror: `lib/constants.js`'s `CORE_MODULES` array is also now `[]` (was `[{id:'goals',...}]`); the
core halves of `lib/deepLinks.js`'s `_CORE_MODULE_ROUTES`/`_CORE_RECORD_PARAM` are both now literally
`{}` too. This is the natural next step of the exact milestone that got its own bolded callout in
MAP.md/MEMORY.md/PROJECT.md/TASKS.md when Finance converted earlier today.

**Generic metric-provider mechanism — genuinely new infrastructure, not just a Goals feature.** A
Goal can pull its completion percentage from live data in ANOTHER module. Built as a fully generic,
extensible registry, mirroring exactly how `owned_agent_tools`/`owned_block_types` already let a
module declare capabilities generically: `module_registry.py` gained a new dataclass
`MetricProviderSpec` (`key`, `label`, `config_schema` — a list of `{key,label,kind,...}` field
descriptors in the SAME shape `blockRegistry.js`'s `CONFIG_FIELD_SCHEMAS` already uses on the
frontend, so the existing kind-based picker dispatch mechanism could mostly be reused; `resolve`, a
`(config, user, workspace) -> {"current","target","pct"}` callable that must never raise, degrading
to 0% instead) and a new `ModuleManifest.owned_metric_providers` field. A new discovery function
`module_registry.metric_providers()` unions every ACTIVE module's own registered providers, keyed by
`f"{module_id}:{provider.key}"` (namespaced like migration names) — mirrors
`admin_agent_tool_names()`/`read_only_agent_tool_names()`'s own discovery shape exactly. Goals itself
contains ZERO module-specific metric logic anywhere — it just calls this and lists whatever comes
back.

v1 ships THREE concrete providers: (1) built-in, no registry entry at all, native to Goals — % of
linked subgoals + linked tasks marked done (free, the tree/link data already exists); (2) "manual" —
also native to Goals, a `target_value` the user sets plus a LOGGED HISTORY of dated `{date, value}`
entries (not a single overwritten value — a deliberate choice during scoping, "weight, other health
metrics" need a trend, not just a snapshot); (3) two real registry-discovered providers, each
declared on ITS OWN owning module's manifest — `finance:budget_pct`
(`module_packages/finance/manifest.py`, reusing `finance_planning_service.budget_status()`'s
existing `spent*100/limit` computation directly, the one real "current vs target → %" precedent
already in the codebase before this) and `contacts:number_field`
(`module_packages/contacts/manifest.py`, reading a number-type custom field's value off a Contact
record, defaulting to the caller's own self-contact — this is what "metrics in my profile" meant
during scoping: weight, other health numbers, or any admin-defined number-type custom field). Fast-
follow providers (mechanism ships now, NOT built in this pass, deliberately deferred to be added one
at a time later exactly like the 13-module rollout itself was sequenced): Assets, Journal, Calendar,
Home Assistant, Automations.

**New frontend picker: `components/dashboard/ContactNumberFieldPicker.jsx` — a real, honest
deviation from the plan, not glossed over.** Contacts' custom field DEFINITIONS are global/
instance-wide (not per-record the way Assets' template fields are), so this needed no
`assetId`/`templateId`-style dependency the way the existing `AssetSelectFieldPicker.jsx` needs —
genuinely simpler. The original plan assumed one shared component would serve both this and a
hypothetical future Assets number-field picker; in practice, since Contacts' fields are global and
Assets' are per-template, they turned out to need different data-fetching shapes, so this shipped
Contacts-only for now, not the shared component the plan assumed.

**Progress computation (`goals_service.compute_progress`, computed live on every call, same
"no persisted percent" precedent as Finance's own `budget_status()`).** If a goal has its own metric
configured, that metric ALWAYS wins for the displayed/driving percent (subgoals/tasks still list
underneath for organization but don't override an explicit metric — confirmed owner choice during
scoping, not a default invented here). If no metric but has subgoals/linked tasks, percent is a
WEIGHTED AVERAGE of each child's own percent (a subgoal that's itself 60% metric-complete
contributes 0.6, not just "not done" — a deliberate choice over a simple done/not-done count, made
during scoping specifically so the "ME" life-goal progress bars are genuinely informative). No metric
and no children = plain manual pending/done toggle, same as the old Task-based Goals always worked.

**Delete (`goals_service.delete_goal`) is a real choice surfaced to the caller, not a fixed rule.**
`cascade` (bool) — false (default) re-parents subgoals up to the deleted goal's own parent (root-level
if it had none); true deletes the whole subtree. `delete_linked_tasks` (bool) — false (default) just
clears `goal_id` on affected tasks (they stay as ordinary tasks, matching the existing app-wide
precedent that nothing else cascade-deletes a Task when the thing it's linked to goes away); true
deletes them too. Both independent, owner-requested during scoping ("make it optional on the delete
popup... also make it optional to delete only that goal and or its subsets too").

**Pool goals (household/team) are served from Goals' OWN router** (`/api/v1/goals`), not from
household's/team's own routers — the same "a single owning module serves personal + pool" shape
Finance/Contacts/Assets/Notes already use, NOT the older per-pool-router shape Tasks/Calendar/Events
predate that split by. This ties pool-goal availability correctly to Goals' OWN install state. Every
non-list endpoint takes an explicit `pool: bool` flag (default False) rather than trying to infer
"which store does this id belong to" from the id alone — mirrors the EXISTING precedent on
`POST /notes/file`'s own `pool: true` flag. Visible to all pool members by default (matches
Tasks/Notes' pattern, NOT Dashboards' contributors-gated pattern — an explicit owner choice during
scoping). Permissions reuse the EXISTING `pool_edit` grant mechanism exactly as-is
(`PATCH /auth/admin/users/{id}/pool-edit`) — no new permission model.

**A real subtlety, found and fixed during implementation, not anticipated in the plan**: a pool
pseudo-user's (`_household`/`_team`) own storage ALWAYS lives at `workspace="personal"` internally,
regardless of which real workspace (personal/business) the calling user is currently in —
`ws_path()` only branches on `"business"` for a REAL username (`brain/USERS/{name}/Business/`);
`_household`/`_team` have no such subfolder, their entire existence already encodes
personal-vs-business. Confirmed by direct read of `module_packages/team/backend/router.py`, which
calls `task_service.list_tasks(_TEAM)` with NO workspace argument anywhere (defaults to
`"personal"`). Goals' router's `_store_for()` helper returns a `(store_user, store_workspace)` PAIR,
not just a store_user, specifically to get this right — an earlier draft during implementation got
this wrong (passed the caller's own ambient workspace straight through for pool stores) and was
caught and fixed before merging, including in the household/team dashboard block resolvers (team's
own `resolve_team_goals` initially read `"_team"` goals under `workspace="business"`, the wrong
store entirely — fixed to `"personal"`).

**Household/team pool dashboard blocks**: `household_goals`/`team_goals` — added to
household's/team's OWN `dashboard_block.py` files and `owned_block_types` (NOT to Goals' own
package), gated `module="household"`/`module="team"` (not `"goals"`) — mirrors
`household_tasks`/`team_tasks`' own already-established precedent exactly (gate on POOL membership,
not on the underlying data-owning module).

**Additional signals, all owner-confirmed in-scope during a later scoping round, each with a real,
distinct trigger.** Completion celebration fires via `suggestions_service.py`'s EXISTING
`notify_user()` (no new delivery mechanism) the moment a goal's computed % crosses from <100 to >=100
— detected once daily by a new scheduler job `job_goal_progress_snapshot` (runs at
`overdue_check_hour:15`, before `goal_drift` at `:30`) that compares today's snapshot against the
most recent prior one for every goal, not a real-time write-hook — deliberately, since a
metric-driven goal's percent can change from an entirely different module's own write (a Finance
transaction posted elsewhere) with no Goals-specific write happening at all to hook a real-time
check onto. This closes the `docs/TASKS.md` backlog item ("a distinct celebration moment when a goal
hits 100%") that now has a real trigger to hang off of — removed from TASKS.md. "On pace" indicator
(`goals_service.on_pace`) is only computed when a goal has BOTH a metric `target_value` AND a
`due_date` — straight-line interpolation from `created_at` to `due_date` vs. actual current value,
`"on_pace"`/`"behind_pace"`. `goal_drift` (`services/suggestions_service.py`) was REWORKED — the OLD
version only checked staleness-by-creation-date (confirmed via earlier research this same session
that it never read any real progress signal at all — the field it half-relied on,
`last_completed_date`, was never written for goal-type tasks in the first place). Now compares
CURRENT computed % against a snapshot from N days ago (default 14, via a new lightweight daily
rolling snapshot log, `Goals/goal_progress_history.json`, capped at 30 entries — distinct from the
manual metric's own user-logged history) — alerts only on genuinely stalled PROGRESS, not just
elapsed time. New suggestion `goal_due_urgency` — a SEPARATE signal from `goal_drift`, watching the
approaching DEADLINE regardless of whether progress has stalled (mirrors the existing overdue-alert
pattern for tasks) — "are you stuck?" vs "are you running out of time?" are different questions, so
both ship as independent suggestion types with independent configs, not one extended from the other.
`scheduler.py` gained 2 new cron jobs (`goal_progress_snapshot@:15`, `goal_due_urgency@:35`) alongside
the reworked `goal_drift@:30` (same hour as before, unchanged position) — 19 `scheduler.add_job()`
calls total now.
