## Contacts converted into `module_packages/contacts/` — the 12th converted module, second of the three largest remaining, converted the same day as Assets

Proceeded directly into Contacts per the tracked rollout order after Assets' own conversion. Same
upfront research pass every increment gets (full file inventory on both sides, every cross-module
consumer of `contacts_service.py`/`contacts_index.py`, and existing test coverage) before writing any
code. Unlike Assets, no endpoints moved out of `routers/contacts.py` — its own automation endpoints
(`/automation/lookup`, `/automation/contacts`, `/automation/interactions`, `/automation/deals`) were
already correctly gated only by the shared n8n token (`_require_automation_token`), the same accepted
pattern Assets' own automation endpoints already use.

**`contacts_service.py`/`contacts_index.py` both stay core — MORE dependents than any prior "stays
core" service, including Dashboards' and Assets' own.** On top of the usual
`user_deletion_service.py`/`main.py`'s `_warm_share_index()` consumers, TWO already-converted sibling
module packages import `contacts_service` directly — `module_packages/dashboard/backend/router.py`
(Dashboard Hero's `subject_type == "contact"` resolver) AND `module_packages/chat/backend/router.py`
(a lazy import for the AI system-prompt's own profile context) — plus `agent_service.py`'s own core
`get_profile`/`update_profile` tools, deliberately left in place rather than moved into Contacts' new
`agent_tools.py`, since Profile is a generic concept independent of Contacts' own module state.

**`custom_fields`/`ContactPicker.jsx` — the same "spans more than one module, owned by none" shape
`dashboard_blocks/_actions.py`'s `nav_button`/`status_button` already established, applied for the
first time to a genuine split.** `services/dashboard_blocks/_contacts.py` had 4 block types; 3
(`linked_deals`/`contacts_list`/`linked_assets`) are exclusively Contacts' own and moved into
`module_packages/contacts/backend/dashboard_block.py`, each gaining a `module="contacts"` gate for the
first time. But `custom_fields` genuinely reads from EITHER `contacts_service` OR `assets_service`
depending on which config field is set — extracted into a NEW core file,
`services/dashboard_blocks/_custom_fields.py`, and stays ungated. The frontend mirrors this exactly:
`components/contacts/ContactPicker.jsx` stays core, confirmed by import-grep to have 7 external
importers beyond its own module's `ContactModal.jsx` — including two already-converted Dashboards
components depending on it directly — leaving it as the only file remaining in
`components/contacts/`.

**Two admin-gated-but-not-`require_module` endpoints found during this conversion's own research, each
judged independently.** (1) `PUT /contacts/fields` had `require_admin` but no
`require_module("contacts")`, unlike its own `GET` sibling — a real, narrow gap: an admin whose own
account has Contacts disabled could still edit Contacts' own field schema. **Fixed.** (2) `GET
/contacts/available-for-linking` is **deliberately left as-is** — same reasoning as `GET`/`PATCH
/contacts/me`: self-contact linking is account-creation infrastructure that must keep working
regardless of Contacts' module state.

**`_guest_map()`'s nuance: the first converted-and-optional module with its own guest-specific default
override.** `guest["contacts"] = False` (guests never get Contacts by default — PII data, same
reasoning as Finance) was deliberately left untouched — an unconditional post-copy override that keeps
working correctly whether `"contacts"` is a core id or a converted/installed module id.

## Finance converted into `module_packages/finance/` — the 13th and FINAL module in the entire Mod Store rollout, converted the same day as Assets and Contacts

Proceeded directly into Finance per the tracked rollout order after Contacts' own conversion. Same
upfront research pass every increment gets (full file inventory on both sides, every cross-module
consumer of Finance's own services, and existing test coverage) before writing any code. The largest
and most structurally complex module in the app — and the last one in the plan.

**Six-router assembly — a genuinely new pattern, since every other module had exactly one router
file.** `routers/finance.py` (722 lines)/`finance_banking.py` (432)/`finance_planning.py` (310)/
`finance_invoicing.py` (323)/`finance_sharing.py` (191)/`finance_transfers.py` (218) — 2,196 lines /
78 endpoints, all previously mounted separately in `main.py` under one `/api/v1/finance` prefix with
6 different tags — moved into `module_packages/finance/backend/` as `router.py`/`router_banking.py`/
`router_planning.py`/`router_invoicing.py`/`router_sharing.py`/`router_transfers.py`.
`ModuleManifest.get_router()` only supports returning ONE router — so `manifest.py`'s `_get_router()`
composes all six into a single parent `APIRouter()` via six `include_router()` calls, each keeping
its own original tag rather than adding a new umbrella "finance" tag, so the OpenAPI grouping stays
byte-identical to before this conversion. Confirmed by a dedicated test: exactly 78 routes, exactly
the original 6 tags, nothing more.

**`finance_service.py`/`finance_invoice_service.py`/`finance_index.py` all stay core — the strongest
"stays core" case of any conversion yet.** Contacts' own `GET /contacts/{id}/finance` endpoint makes
deep, real, multiple-function calls into both — that endpoint already had its own defensive
`if "finance" in disabled_modules` check from BEFORE this conversion, meaning Contacts' own
conversion had already anticipated Finance staying core. On top of that: `user_deletion_service.py`
imports both directly; `dashboard_blocks/_actions.py` imports `finance_service` for its `nav_button`
resolver; `main.py`'s `_warm_share_index()` unconditionally rebuilds `finance_index` at every boot.

**A genuinely new kind of "stays core" reasoning: a scheduler dependency, treated exactly like a
sibling-module dependency.** `finance_planning_service.py` and `simplefin_service.py` ALSO stay
core — neither has a sibling-module or core-router dependent, but both are imported directly by
`scheduler.py`'s own job functions (`job_finance_nightly`, `job_simplefin_sync`), registered
unconditionally at boot. Mirrors `n8n_service.py`'s own precedent from Automations' conversion
(2026-08-25) — confirmed by direct read of that entry before deciding. The `month_end()` wrinkle:
`finance_planning_service.py` needed a helper that used to live in `finance_reports.py` (which DOES
move) — relocated INTO `finance_planning_service.py` (core) instead, with the moved `reports.py`
importing it back from there, so a scheduler-critical core file never depends on
`module_packages/finance/` even in principle.

**The 13-endpoint SimpleFIN admin-gate fix — the same narrow-inconsistency shape as Contacts' own
`PUT /contacts/fields` finding.** 13 admin-lifecycle SimpleFIN endpoints in `finance_banking.py` were
gated by `require_admin` ALONE, never `require_module("finance")` — an admin whose own account has
Finance disabled could still manage every user's bank connections. **Fixed** by adding
`require_module("finance")` alongside `require_admin` on all 13. Every other `finance_banking.py`
endpoint was already correctly gated. Separately: all 9 Finance AI tools lived unfiltered in
`agent_service.py`'s static `_USER_TOOLS` list — the SIXTH confirmed instance of the same
enforcement gap every prior conversion found (Chat/Notes/Dashboards/Assets/Contacts/now Finance).

**Two tests needed their example module id swapped from `"finance"` to `"goals"`** — the second time
this exact predicted failure mode has hit. `test_features.py`'s two tests used `"finance"`
specifically because it used to be a safe, permanently-core id — the first test's own docstring
already documented this happening to `"team"` when Household/Team converted, and predicted a real
converted-but-optional id would hit it again. Finance converting hit exactly that. Fixed by swapping
both to `"goals"` — now the only genuinely-permanent core id left.

**Milestone: `features_service.py`'s `_CORE_MODULE_IDS` is now just `["goals"]`.** The only
hardcoded-core module id left in the entire app — `goals` was never itself a real backend module, it
rides Tasks' own permission gate. Every OTHER module is now either a converted `module_packages/`
entry or permanent cross-cutting infrastructure the plan's own closing note never intended to
convert (`dashboard_blocks/`, `agent_service.py`'s orchestration engine, `module_registry.py`
itself). Frontend mirror: `CORE_MODULES` is now also just `{goals}`; `deepLinks.js`'s
`_CORE_MODULE_ROUTES` is `{goals: '/goals'}` and `_CORE_RECORD_PARAM` is literally `{}`.
