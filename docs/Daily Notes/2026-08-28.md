# 2026-08-28

## Contacts converted into `module_packages/contacts/` — the 12th converted module, second of the three largest remaining, converted the same day as Assets

Proceeded directly into Contacts per the tracked rollout order after Assets' own conversion. Same
upfront research pass every increment gets (full file inventory on both sides, every cross-module
consumer of `contacts_service.py`/`contacts_index.py`, and existing test coverage) before writing any
code. Unlike Assets, no endpoints moved out of `routers/contacts.py` — its own automation endpoints
(`/automation/lookup`, `/automation/contacts`, `/automation/interactions`, `/automation/deals`) were
already correctly gated only by the shared n8n token (`_require_automation_token`), the same accepted
pattern Assets' own automation endpoints already use.

**`contacts_service.py`/`contacts_index.py` both stay core — MORE dependents than any prior "stays
core" service, including Dashboards' and Assets' own.** On top of the usual
`user_deletion_service.py`/`main.py`'s `_warm_share_index()` consumers, TWO already-converted sibling
module packages import `contacts_service` directly — `module_packages/dashboard/backend/router.py`
(Dashboard Hero's `subject_type == "contact"` resolver) AND `module_packages/chat/backend/router.py`
(a lazy import for the AI system-prompt's own profile context) — plus `agent_service.py`'s own core
`get_profile`/`update_profile` tools, deliberately left in place rather than moved into Contacts' new
`agent_tools.py`, since Profile is a generic concept independent of Contacts' own module state.

**`custom_fields`/`ContactPicker.jsx` — the same "spans more than one module, owned by none" shape
`dashboard_blocks/_actions.py`'s `nav_button`/`status_button` already established, applied for the
first time to a genuine split.** `services/dashboard_blocks/_contacts.py` had 4 block types; 3
(`linked_deals`/`contacts_list`/`linked_assets`) are exclusively Contacts' own and moved into
`module_packages/contacts/backend/dashboard_block.py`, each gaining a `module="contacts"` gate for the
first time. But `custom_fields` genuinely reads from EITHER `contacts_service` OR `assets_service`
depending on which config field is set — extracted into a NEW core file,
`services/dashboard_blocks/_custom_fields.py`, and stays ungated. The frontend mirrors this exactly:
`components/contacts/ContactPicker.jsx` stays core, confirmed by import-grep to have 7 external
importers beyond its own module's `ContactModal.jsx` — including two already-converted Dashboards
components depending on it directly — leaving it as the only file remaining in
`components/contacts/`.

**Two admin-gated-but-not-`require_module` endpoints found during this conversion's own research, each
judged independently.** (1) `PUT /contacts/fields` had `require_admin` but no
`require_module("contacts")`, unlike its own `GET` sibling — a real, narrow gap: an admin whose own
account has Contacts disabled could still edit Contacts' own field schema. **Fixed.** (2) `GET
/contacts/available-for-linking` is **deliberately left as-is** — same reasoning as `GET`/`PATCH
/contacts/me`: self-contact linking is account-creation infrastructure that must keep working
regardless of Contacts' module state.

**`_guest_map()`'s nuance: the first converted-and-optional module with its own guest-specific default
override.** `guest["contacts"] = False` (guests never get Contacts by default — PII data, same
reasoning as Finance) was deliberately left untouched — an unconditional post-copy override that keeps
working correctly whether `"contacts"` is a core id or a converted/installed module id.
