## Chat UI polish — 5 items, owner's "make it sleeker" ask

Following up on the 2026-08-09 AI Chat/Agent expansion, owner asked for ideas to make the chat UI
sleeker; picked all 5 proposed:

1. **Dependency-free markdown rendering** for assistant replies — no npm registry access in this
   environment, so hand-rolled a line-by-line block parser (`Markdown`/`renderInline` in `Chat.jsx`):
   bold/italic/inline code/fenced code/headings/bullet+numbered lists/links. Real React elements only,
   never `dangerouslySetInnerHTML`. Applied to both the live thread and the saved-chat drawer.
2. **Distinct visual identities per pending-action card** instead of one orange treatment for
   everything: `ApprovalCard`/`ProposalCard` stay orange (both are "review before you commit"),
   `AskUserQuestionCard` is now blue/cool (a question has no side effects), `DashboardBlockPreview` is
   neutral charcoal (informational only, not a decision point).
3. **Auto-growing `<textarea>`** replaces the old single-line `<input>` — Enter sends, Shift+Enter
   inserts a newline, caps at 160px.
4. **Consolidated composer** — the old loose row of icons (🧠 workspace toggle, ⏳/📚 memory links) is
   now one "Memory" pill opening a popup with descriptions + an iOS-style toggle; the mode selector,
   usage badge, Memory pill, and input now live inside one bordered box (Claude-Code-style). This is
   sub-items (2)+(4) of the pre-existing `docs/TASKS.md` "Chat UX redesign" bundle — the *visual* half
   only; chat-session-persistence-across-navigation and archive-format-persistence (items 1+3 of that
   same bundle) stayed out of scope on purpose.
5. **Fade-in on new messages/cards** + a shimmer-text "Thinking…" state replacing the generic
   bouncing-dots spinner. Both respect `prefers-reduced-motion`.

Verified in an isolated instance (never the real family data), light + dark theme both checked, 17/17
mocked-response Playwright checks passing. Frontend build + lint clean.

**Found while checking test status before the release, not a paperwork item**: the full backend suite
is 594/596 green. The 2 failures (`test_ai_usage_service.py::test_record_tokens_accumulates_personal_and_business`,
`::test_record_message_only_bumps_messages`) were previously logged (2026-08-09) as a harmless
"date-boundary flake that resolves once the calendar rolls over" — that diagnosis was **incomplete**.
Root-caused this time: `ai_usage_service._bump_and_escalate` buckets "today" via
`auth_service.today_for_user()`, which resolves the user's *stored* timezone and **falls back to UTC**
when absent; the test fixture user has no `timezone` set, so it buckets by UTC. The assertions use
Python's bare `date.today()` (local/CDT in this environment). The two diverge for several hours every
single day, whenever UTC has already crossed into the next calendar date but local hasn't (confirmed:
failed again tonight, ~10pm CDT, same mechanism) — not a calendar-day coincidence, a real and recurring
several-hour daily window. Real-world implication, not just a test artifact: **any account whose
`timezone` field is missing or invalid buckets AI usage by UTC day instead of any locale-sensible day**,
which could make a daily usage cap reset at the wrong local time for that account. Logged in
`docs/TASKS.md` with the corrected diagnosis, replacing the earlier incomplete one. Not fixed this
session — owner's call whether to fix before or after cutting 0.5.0; low severity (only affects
accounts without a timezone, and only during the UTC/local crossover window), not a release blocker.
