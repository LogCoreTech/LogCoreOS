## Round twelve: found the real root cause of the keyboard double-jump/periodic-scroll bug — it was never Chat-specific (attempts 1-8 are logged in `docs/Daily Notes/2026-08-15.md`)

Continuing the same investigation from yesterday. Attempt 8 (removing all keyboard-avoidance JS from
`Chat.jsx` entirely, landing back at zero JS) still showed both symptoms on a real device after a proper
rebuild+relaunch: "i relaunched and reloaded the pwa and it still does the double jump and periodic auto
scroll down." That's decisive — eight straight attempts scoped to Chat's own composer, and removing all of
them changed nothing. The bug was never actually about Chat's composer position at all.

**Asked a scoping question instead of shipping a ninth Chat-only guess**: does the same jump/scroll happen
on other pages, or only Chat? Owner's answer is what actually cracked this: **"happens everywhere that has
scroll enabled. only notes and journal dont have issue cause they have scroll locked."**

That single comparison identifies the real cause precisely: `<main>` (`Layout.jsx`, shared by every page,
`overflow-y-scroll`) is an actual scrollable container. WebKit's native "keep the focused field visible"
correction acts on whichever scrollable ancestor a focused field sits inside — and with `index.html`'s
`interactive-widget=resizes-content` reflowing the whole layout at the same moment the keyboard opens, that
native correction visibly runs in separate passes (the double jump) and can re-trigger more than once (the
periodic scroll). Notes and Journal's editors fill the screen without ever needing `<main>` to scroll, so
WebKit never had anything to correct there — nothing special in their own code, they just never gave the
browser a reason to act.

**Attempt 9: lock `<main>`'s own scroll while a text field inside it is focused — in `Layout.jsx`, app-wide,
not `Chat.jsx`.** New `mainRef` on `<main>`; a `focusin`/`focusout` listener pair on `document` toggles
`mainRef.current.style.overflowY` between `'hidden'` (a field is focused) and `''` (released). `focusout`
checks `e.relatedTarget` so tapping directly from one field into the next stays locked instead of flickering
unlocked for a frame in between — same pattern the pre-existing touch-desync effect just above it already
uses for its own field-to-field case. This gives WebKit's own correction nothing to act on, rather than
computing or moving anything ourselves — deliberately not a ninth position/scroll calculation after eight
straight ones each introduced a new problem of their own.

**Scoped to `(pointer: coarse)` (touch) devices only.** There's no on-screen keyboard to correct for on
desktop, and locking `<main>`'s scroll on every field focus there would break the ordinary desktop habit of
mouse-wheel-scrolling a long form while a field still has focus — caught before shipping, not after.

### Verification

`npm run lint` and `npm run build` both clean. The focus/blur logic itself checked mechanically — a
standalone Playwright script against a minimal HTML page running the exact same listener code (not the live
app, which needs a real backend): confirmed it locks on field focus, stays locked when focus moves directly
from one field to another, and releases when focus moves to a non-field element. As with every round on this
bug: the real on-device keyboard/scroll interaction can't be verified from here — reported to the owner as
unverified, awaiting real-device confirmation.

**Files:** `app/frontend/src/components/Layout.jsx` (new `mainRef`, new focus-scoped scroll-lock effect,

## Round thirteen: attempt 9's `overflow: hidden` did nothing on the real device — switched to actively snapping scroll position back (attempt 9b)

Owner rebuilt, force-closed and reopened the PWA (confirmed explicitly, ruling out the earlier stale-cache
confusion), and reported: "nothing changed," — the double-jump/periodic-scroll bug was completely unaffected
by attempt 9.

**Honest read on why, before jumping to a tenth guess**: `overflow: hidden` is a well-documented unreliable
way to stop scrolling on iOS Safari specifically. It works for an ordinary user touch-drag or mouse-wheel
scroll, but WebKit's own internal "scroll the focused field into view" correction — the exact mechanism
behind this bug — is a lower-level UA behavior that doesn't reliably respect it. Explained this plainly and
asked the owner how to spend a tenth attempt given nine straight rounds with no way to verify any of them
directly from this environment: try the more robust fix, deprioritize as a cosmetic issue, or something
else. Owner: **"Try the position:fixed lock (recommended)"** — picking up on my own framing of `position:
fixed` as the standard, more-robust iOS scroll-lock technique (the usual fix for exactly this
`overflow:hidden`-doesn't-work quirk).

**Caught a real problem with my own suggestion before writing it.** `position: fixed` freezes an element at
a captured size and position — but `<main>`'s *size* is precisely what `interactive-widget=resizes-content`
needs to keep changing as the keyboard opens, to keep the composer/whatever's at the bottom actually visible
above it. Freezing `<main>` at its pre-keyboard size would stop that resize from happening at all — trading
this cosmetic double-jump bug for the original, worse "composer permanently hidden behind the keyboard" bug
this whole saga started from. Told the owner directly rather than shipping the flawed version.

**Attempt 9b: keep the same underlying idea (a lock more robust than `overflow: hidden`) but scope it to
just the scroll *position*, not the element's size.** On focus of a field, `Layout.jsx` now captures
`main.scrollTop` and attaches a `scroll` listener that snaps it back to that captured value the instant
anything changes it — including WebKit's own internal correction, not just a user-driven scroll attempt.
`<main>` keeps resizing normally for the keyboard; only its scroll offset is held in place. Same
`(pointer: coarse)`-only scoping as attempt 9.

### Verification

`npm run lint` and `npm run build` both clean. Standalone Playwright checks against the exact snap-back
logic (not the live app): confirmed a scroll change forced while a field is "focused" gets actively reset
back to the captured value (not just passively blocked), and confirmed the lock correctly releases once
focus moves to a non-field element, leaving further scroll unaffected. (First run of this check showed a
stale/flaky result before the headless browser had fully settled; two clean reruns after that were
consistent.) As always: the real on-device WebKit keyboard-correction behavior — the actual thing this is
trying to defeat — can't be verified from here.

**Files:** `app/frontend/src/components/Layout.jsx` (`overflow: hidden` toggle replaced with an active
scroll-position snap-back). Docs: `docs/MEMORY.md` (attempt 9 marked as a real-device no-op, new attempt 9b
entry), `docs/TASKS.md`, `CHANGELOG.md`, this file. Uncommitted, same standing rule as every prior round.

## Round fourteen: attempt 9b also had zero effect — the real problem was never scroll position, it's `<main>`'s own height reflow (attempt 10)

Owner: "nothing changed again.." — the second structurally different scroll-lock in a row (passive
`overflow: hidden`, then active `scrollTop` snap-back) with no measurable effect at all. Ten real-device
round trips deep with no way to verify anything directly from this environment, asked plainly how to spend
an eleventh: use Safari Web Inspector for real diagnostic access (recommended), deprioritize as a cosmetic
issue, or keep guessing blind with lower confidence flagged. Owner: **"Keep guessing blind."**

**Two zero-effect results in a row is itself the useful signal, not just a dead end.** If neither locking
`<main>`'s `overflow` nor actively fighting its `scrollTop` touched the bug at all, the visible motion is
very likely not a `scrollTop` change in the first place — both attempts were defending a variable that was
never actually moving.

**Traced the real chain instead.** `index.css`'s `html`/`body` rules (a pre-existing fix for a *different*
iOS standalone-PWA quirk — the phantom-toolbar bug) confirm `html`'s height resolves against the layout
viewport, cascading through `body` (`height: 100%`) → `#root` (`height: 100%`) → `Layout.jsx`'s flex column
→ `<main>` (`flex-1 min-h-0`). `index.html`'s `interactive-widget=resizes-content` shrinks that layout
viewport progressively across the keyboard's own multi-frame opening animation (typically ~250-300ms), not
in one instant step. Ordinary CSS layout reflow isn't interpolated by the browser the way `transform`/
`opacity`/explicitly-transitioned properties are, so each intermediate frame of that resize renders as a
discrete, visible jump rather than a smooth shrink. Separately: browsers auto-clamp a scrollable container's
`scrollTop` whenever its height shrinks below the current scroll position — which would fire on *every one*
of those reflow frames, independent of any WebKit keyboard-focus-correction behavior at all. That gives a
clean, complete mechanistic account of both symptoms — the double jump *and* the periodic auto-scroll-down —
from pure CSS reflow timing, no scroll hijacking involved anywhere. It also explains why both prior attempts
did nothing: `overflow: hidden` never stops the container's *height* from changing, and 9b's snap-back was
reactively fighting the browser's own per-frame scroll-clamp rather than addressing the underlying reflow.

**Attempt 10: removed both scroll-lock attempts entirely (the JS effect and the now-unused `mainRef`) and
added `transition-[height] duration-300 ease-out` directly to `<main>`'s className** — a pure CSS change,
smoothing the reflow itself rather than fighting scroll position or overflow. `duration-300` roughly matches
iOS's typical keyboard-animation timing. Same Tailwind arbitrary-property + duration pattern already used
elsewhere in this codebase (`Chat.jsx`'s earlier `transition-transform duration-150`), so no new technique
being introduced, just applied to a different property.

### Verification

`npm run lint` and `npm run build` both clean. Confirmed directly in the built CSS output (`node` script
reading the compiled stylesheet) that `.transition-\[height\]{transition-property:height;...}` and
`.duration-300{transition-duration:.3s}` both compiled correctly. As always: whether this actually smooths
the real keyboard-open reflow on iOS can't be verified from here — reported to the owner as unverified.

**Files:** `app/frontend/src/components/Layout.jsx` (removed the `mainRef`/scroll-lock effect entirely,
added `transition-[height] duration-300 ease-out` to `<main>`). Docs: `docs/MEMORY.md` (attempt 9b marked as
a second real-device no-op, new attempt 10 entry), `docs/TASKS.md`, `CHANGELOG.md`, this file. Uncommitted,
same standing rule as every prior round.

documented assumption that only happens once the keyboard is fully closed. That assumption describes the
*older* pan-based keyboard behavior, where `window.innerHeight` stays constant while only the visual viewport

purpose is keeping the layout viewport in sync with the visual viewport *continuously*, not just at rest. If
they track each other throughout the keyboard's entire opening animation, the near-equal condition could be
true on every single resize tick during that ~250-300ms window, not just the final one — meaning this
correction could have been firing a forced `scrollTo(0,0)` many times per keyboard-open instead of once, the
whole time this investigation was looking at completely different code downstream.

**Attempt 11: debounced it.** `onViewportResize` now clears and resets a 150ms timer on every resize tick and
only runs the height-check-and-correct once resize events have genuinely stopped, instead of on every
qualifying tick. Same intent as the original fix (correct the touch offset once the keyboard transition is
truly done), just no longer capable of firing repeatedly mid-animation.

## Round seventeen: real production crash in AI Chat — found and fixed, unrelated to the keyboard saga

Owner reported, after relaunching for the keyboard-debug-console round: asked Chat to resize/move a
dashboard block, got a full error page — `"undefined is not an object (evaluating 'e.split')"`. Retried and
it worked. Then hit Accept on the approval card and got a *different* error page —
`"cannot access uninitialized variable"` — and **that error now fires every time Chat is opened**, since
Chat auto-reopens the last conversation on load. A real, actively-blocking crash, not a cosmetic issue —
prioritized ahead of the keyboard investigation immediately.

**Found the cause fast, and it's a genuine bug, not a device quirk.** `"Cannot access uninitialized
variable"` is Safari's exact, verbatim wording for a temporal-dead-zone `ReferenceError`. Grepped
`DashboardBlockPreview` (`Chat.jsx`) — the dashboard move/resize preview feature added earlier this session
— and found it immediately: in the `update_dashboard_block` branch,
```js
const layout = step.input.layout
  ? { lg: { ...b.layout.lg, ...(layout.x != null ? { x: layout.x } : {}), ... } }
  : b.layout
```
references `layout` — the variable currently being declared — *inside its own initializer expression*.
That's a real TDZ violation, and it fires unconditionally and deterministically the instant
`step.input.layout` is truthy, i.e. every single time the agent actually proposes a position/size change
(exactly what "resize and move my dashboard blocks around" triggers). Because the crash happens on *render*,
not on click, the broken message was permanently saved in the conversation's archive — so every future
reopen re-renders the same crashing card. Fixed by renaming the ternary's source to `override`, so `layout`
is never referenced before its own declaration finishes. Verified the corrected logic directly in Node
(constructing the same override/merge shape) — no `ReferenceError`, correct merged output.

**The first error (`e.split`) couldn't be pinned to a specific cause** — `chat.py`'s `final_answer` always
has a non-empty string fallback in every pause branch checked (question/plan/write-approval all have `||
"..."` fallbacks), so `res.response` reaching the frontend as literally `undefined` isn't explained by
anything found in the backend code read directly. Hardened `Markdown` anyway rather than leaving it fragile:
`text.split('\n')` → `(text || '').split('\n')` — a turn that's a pure tool call with no accompanying prose
is a legitimate case that should render blank, not crash the whole page, regardless of what produces it.

### Verification

`npm run lint` and `npm run build` both clean. Confirmed the fixed `DashboardBlockPreview` layout-merge logic
directly in Node with a realistic override shape (`{x, y, w}` over an existing block layout) — correct merged
`lg`/`sm` output, no exception. The already-saved, currently-crashing chat should self-repair the next time
it's opened post-deploy, since the underlying saved data was always valid — it was the *rendering* code that
was broken, not the archive.

**Files:** `app/frontend/src/pages/Chat.jsx` (`DashboardBlockPreview`'s TDZ bug fixed; `Markdown` hardened
against undefined text). Docs: `docs/MEMORY.md` (new Core Design Decision #16), `CHANGELOG.md`, this file.
Uncommitted, same standing rule as every prior round.
