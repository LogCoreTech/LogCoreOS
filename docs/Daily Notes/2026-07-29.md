## Mobile footer nav — recurrence of the [0.4.1] "floating above the bottom" bug, fixed properly this time

Owner reported the mobile footer nav was still sitting above the true bottom of the screen — the built-in `env(safe-area-inset-bottom)` padding inside the nav is correct (keeps buttons clear of the home indicator), but the whole nav bar was floating that same distance above the true edge, exposing a strip of body background below it. This is the identical symptom already "fixed" twice on 2026-07-20 (`h-[100dvh]` → `h-full` + explicit `#root` height, see CHANGELOG [0.4.1] and the prior revert/re-fix commits) — both fixes addressed the layout's height-resolution chain and verified clean in Chromium with a simulated safe-area inset at the time, but evidently didn't hold on a real device.

**Root cause, confirmed via a Chromium repro** (`/tmp/.../scratchpad/footer-repro.html` + `shoot.js`, not committed — scratch only): built two versions of the layout, both with the flex column's height artificially forced 34px short of the true viewport (simulating whatever WebKit is actually doing on-device, since Chromium won't reproduce it directly). The nav-as-last-flex-child version reproduced the exact floating-gap bug (screenshotted: green nav with a red gap below it); a `position: fixed; bottom: 0` version stayed flush to the true bottom regardless of the same forced shortfall, because `fixed` positioning anchors to the viewport directly and doesn't care what any ancestor's height resolves to.

**Fix applied:** `Layout.jsx`'s mobile footer nav changed from a flex-column child to `fixed bottom-0 left-0 right-0` (matching the module drawer just below it in the same file, which already used `fixed` and was never reported with this bug — a clue in hindsight). `<main>` now reserves `pb-[calc(4.5rem+env(safe-area-inset-bottom))]` on mobile so scrolled content isn't hidden behind the now-floating nav. Full writeup + the general rule ("bottom-pinned mobile bars must be `fixed`, not a height-chain flex child") added to `docs/MEMORY.md` Known Gotchas.

**Update: the `fixed` fix above was NOT enough.** Owner relaunched (server-side rebuild verified byte-for-byte present in the new `dist/`), then deleted and reinstalled the PWA from scratch (ruling out any client-side/service-worker cache explanation) — same bug, still floating. That forced a second look: the footer `<nav>`, even as `position: fixed`, was still nested two levels deep inside `Layout.jsx`'s two `overflow-hidden` flex containers. That's a well-documented real Safari/WebKit bug — a `fixed` descendant gets clipped to the nearest `overflow: hidden` ancestor's box instead of the true viewport, even with no `transform`/`filter` on that ancestor (which is what *should* be required to change the containing block, per spec; Chromium implements the spec correctly, which is exactly why none of this ever reproduced in Chromium testing across three attempts now). Supporting clue found in the same file: the module drawer, also `fixed`, sits only *one* `overflow-hidden` level deep and was never reported broken.

**Real fix:** `Layout.jsx`'s `return` is now a Fragment; the footer nav (and the module drawer) render as top-level siblings outside *every* `overflow-hidden` container in the layout, not just off the normal flex flow. Rebuilt and verified the new markup is present in `dist/` again. This still needs an actual on-device check from the owner — Chromium cannot validate this specific bug at all, so "looks right in Chromium" carries much less weight than it did on the last two attempts.

**Update: attempt 3 (Fragment restructuring) still wasn't enough either.** Owner reported the footer itself now looks right, but there's still a gap beneath it — and gave a genuinely new diagnostic clue: the gap's color tracks light/dark mode (grey in dark, white in light) but does **not** track the custom background gradient/photo setting. That's `body`'s plain Tailwind background classes (`bg-white dark:bg-charcoal-900`) showing through, not its `--bg-image` layer — meaning `body`'s background-image isn't reaching wherever this gap is, while its background-color does.

Two things fixed as a result:
1. `body` had `background-attachment: fixed` — a well-known unreliable property on iOS Safari, and pure dead weight here since `body` never scrolls (`overflow: hidden`). Removed; this should make the chosen gradient/photo paint consistently instead of falling back to plain color in some regions.
2. More importantly: the last remaining `overflow: hidden` ancestor of the (now correctly-nested-outside-Layout's-own-containers) footer nav is `body` itself — sized with `height: 100%`, the exact same percentage-chain mechanism already suspected as unreliable on iOS back in attempt 1. If Safari really does clip `fixed` descendants to the nearest `overflow: hidden` ancestor's box (attempt 3's theory), and that box (`body`) doesn't actually reach the true device height, the gap reappears no matter what's done inside `Layout.jsx`. `body` now uses `position: fixed; inset: 0` instead of `height: 100%` — the most bulletproof way to make an element exactly equal the true viewport on all four edges, immune to the whole class of percentage/dvh resolution ambiguity this bug has hit repeatedly. Verified via Playwright that `getComputedStyle(document.body)` now reports `position: fixed`, zero inset, and height exactly equal to `window.innerHeight` — this is as far as remote verification can go; Chromium has never reproduced any version of this bug, so on-device is still the only real test.

Full history + general rule written up in `docs/MEMORY.md` (now covers 4 attempts).

**Update: attempt 4 (`body` → `position: fixed; inset: 0`) still wasn't enough.** Owner explicitly tested with a colorful gradient background in dark mode (the decisive version of the earlier color clue) and confirmed: the gradient still doesn't reach that spot. Rather than guess a fifth CSS fix, asked the one question none of the prior four attempts had checked: does this happen in a regular Safari browser tab too, or only the installed home-screen PWA? **Owner confirmed: regular browser tab renders the footer correctly; only the standalone PWA is broken.** Since `Layout.jsx` and `index.css` render identically in both modes, this proved every prior theory wrong in one shot — the bug was never in the app's own layout code.

Searched and found the actual root cause: a documented WebKit bug (Apple Developer Forums thread 744327, corroborated by field-tested iOS-PWA writeups) where **standalone PWAs specifically** render as if an invisible browser toolbar is still present and pushes the whole page upward — shorting the true bottom edge by roughly the top safe-area amount. Regular Safari tabs never show this because they have a *real* toolbar occupying that role instead. This matches the symptom exactly and explains why every fix aimed at "make the footer/body properly reach the viewport edge" kept looking correct in Chromium (which doesn't have this bug) and failing on-device (which does).

**Real fix:** `index.css` — `html` now carries `min-height: calc(100% + env(safe-area-inset-top))` alongside its `height: 100%`, deliberately reserving more height than the true viewport so the phantom upward shift has somewhere to go instead of shorting real content. `body` reverted from attempt 4's `position: fixed; inset: 0` back to the plain `height: 100%` chain, matching the externally-documented working pattern rather than continuing home-grown theorizing. Rebuilt and confirmed the new CSS is in `dist/`. `docs/MEMORY.md` rewritten once more to record the full 5-attempt arc and the actual root cause, since this is the kind of thing worth not re-discovering from scratch next time.

**CONFIRMED FIXED** — owner relaunched and verified on the installed PWA: footer sits flush against the true bottom, no gap. Five attempts, but the last one addressed the actual (externally-documented, standalone-PWA-specific) bug rather than another plausible-sounding theory about our own layout code. `docs/MEMORY.md` gotcha entry updated to reflect on-device confirmation, not just "should work."
