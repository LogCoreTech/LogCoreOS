## Now — active build work

- [ ] **Record-Scoped Dashboards (Client/Property Boards) — owner approved, building now on the owner's PC (2026-08-03)** — sourced from a beta tester (a realtor) asking for customizable fields (already exists on Contacts) plus a single visible place to see and update status/flow for a specific client or house, pulling in data from every other module. Design converged over a full conversation pass; full spec below is meant to be directly buildable, not just a one-liner.

  **Core concept — two dashboard mechanics share one module, not one unified schema:**
  1. **Workspace Dashboards** (already backlogged separately, unbuilt, unchanged by this item) — one per workspace (personal/business), a fixed catalog of live-aggregate widgets (Top 3 Tasks, Streaks, Due Today, Smart Home, Team Tasks, Goals) each querying "current user + workspace." Do not fold this into the design below — confirmed during design discussion that unifying them would conflate two different mechanics (live aggregate queries vs. a curated per-record object set).
  2. **Record Dashboards** (new, this item) — one instance per Contact or Asset ("client" or "house"), built from a **Dashboard Template** made of an ordered list of typed **sections**, populated primarily by objects auto-derived from links that already exist elsewhere in the app, with manual pin/add as an override, not the primary mechanism (auto-by-default matters for a realtor with 40 active files — pure manual curation per dashboard doesn't scale).

  **Data model:**
  - **Dashboard Template** — mirrors the existing Assets Template pattern almost exactly: global admin-curated store at `brain/_system/dashboard_templates.json` (personal per-user templates can follow later, same as Assets did). Shape: `{id, key, name, icon, owner, record_type: "contact"|"asset", sections: [{id, type, label, order, config?}], shared_with?, restrict_roles?}`. `record_type` constrains which record kind a template applies to (a "Property Board" template only attaches to Assets; a "Client Board" only to Contacts). `key` is immutable and deletion is key-based, matching the existing Asset Template rule so a re-seeded default can't resurrect a deleted one.
  - **Critical mechanic — live reference, never a snapshot**: a dashboard instance stores only `template_id`. The section list/order is resolved live from the current template on every read, exactly like an Asset instance embeds `_template` resolved at read time rather than a frozen copy. This is what makes "edit the template, every instance using it updates immediately, no migration step" work for free — it's not a new guarantee to build, it's reusing one this codebase already has.
  - **Dashboard Instance** — one per `(record_type, record_id)` pair, 1:1 with a Contact or Asset for v1 (multi-dashboard-per-record is a v2 decision if ever wanted). Storage: workspace-scoped, `ws_path/Dashboard/instances.json`, entries shaped `{id, template_id, record_type, record_id, created_at, section_overrides: {section_id: {pinned_object_ids: [...], hidden_default_ids: [...]}}}`. `section_overrides` is the *only* per-instance data — section list/order/type is 100% template-owned; an instance can never reorder or hide a whole section, only add specific pinned objects the auto-resolver missed, or suppress a specific auto-derived object it doesn't want surfaced (this is the "set in stone via the template" requirement). Pool records (`_household`/`_team`-owned Contacts/Assets) get pool-scoped instance stores the same way pool Assets/Contacts already work — no new pool concept needed.

  **Section types (v1 catalog, backend-registered resolver `(record_type, record_id) -> [objects]` + a frontend renderer each) — built to need zero new linking fields where possible:**
  - **Finance Activity** — Asset-scoped reuses `finance_service.list_transactions_for_asset()` / `GET /finance/assets/{id}/transactions`; Contact-scoped reuses the existing `GET /contacts/{id}/finance` rollup. Both endpoints already exist — this section just renders their existing response.
  - **Linked Deals** — Contact-scoped only, the contact's existing deals/kanban data as a compact stage strip.
  - **Linked Assets / Linked Contact** — cross-pointer rendering: an Asset section shows its linked Contact via the existing `contact` template field type; a Contact section shows assets via the existing `GET /assets/by-contact/{id}` reverse lookup.
  - **Documents/Attachments** — Asset's existing attachment list, reused as-is.
  - **Custom Fields** — renders the record's own template/custom fields inline for quick reference without leaving the dashboard.
  - **Linked Tasks** — Asset-scoped via existing `asset_id` on tasks; Contact-scoped linked tasks don't exist as a field yet, so this section is Asset-only until that's added.
  - **Notes** — deferred to manual-pin-only: Notes don't carry a `contact_id`/`asset_id` link yet (already tracked separately under the Contacts-overhaul bundle, item 5). Gains auto-derive for free once that field ships.
  - **Calendar/Showings** — deferred to manual-pin-only: Calendar events don't link to a Contact or Asset at all today. **This is a genuinely new gap surfaced by this design discussion, not previously backlogged** — closing it is what unlocks auto-derive for this section.
  - **Status/Pipeline** — Contact-scoped shows the existing deal pipeline stage; an Asset-side customizable status/pipeline could follow later if the existing Deal pipeline alone doesn't satisfy the "flow" part of the ask — not required for v1.

  **Access control**: no new sharing/permission model. A dashboard instance's visibility is 100% inherited from its underlying Contact/Asset's already-resolved access level (read/contribute/edit) — deliberately avoids adding a fifth near-duplicate access-resolution implementation (four already flagged as tech debt: Assets/Finance/Contacts/Notes).

  **Navigation**: the Dashboard module gets a searchable picker (reuse the `AssetTreePicker` pattern, not a button row — a working realtor may have 40+ active records) listing workspace dashboards plus record dashboards filterable by `record_type` (this filter *is* the "groups" concept — no separate group data model needed). Contact/Asset detail views get a "View Dashboard →" deep link to `/dashboard?type=contact|asset&id=<record_id>`, consumed the same way `Assets.jsx` already consumes `?asset=`, `Contacts.jsx` consumes `?contact=`, and `Finance.jsx` consumes `?book=&view=` — same established pattern, no new plumbing. A `{type:"open_record_dashboard", record_type, record_id}` notification action falls out of this for free later, matching `open_asset`/`open_finance_book`.

  **Suggested build order**: (1) `dashboard_service.py` — template CRUD mirroring `assets_service.py`'s template CRUD, instance CRUD, and a section-resolver registry starting with the sections needing zero new linking fields (Finance Activity, Linked Deals, Linked Assets/Contact, Custom Fields, Documents); (2) router + reuse the existing `dashboard` module ID (no new `require_module` gate needed — this is a sub-feature, same pattern as Household's tabs); (3) frontend template manager (mirrors `TemplateManager`), instance picker (mirrors `AssetTreePicker`), section renderers reusing existing display components (`assetDisplay.jsx`'s `AttachmentThumb`/`fieldDisplay`, the expanded-deal-row Job P&L markup) rather than rebuilding what Assets/Contacts already render well; (4) deep-link buttons on `AssetView` and the future Contact profile view; (5) defer Notes/Calendar-linked sections and any Asset-side pipeline until their prerequisite linking fields exist or the realtor's feedback says they're actually needed.

## Security follow-ups (from the 2026-07-20 audit)

Most audit findings were fixed this session (see `docs/Security-Audit-2026-07-19.md` remediation passes 1–5 + CHANGELOG). These are the deliberately-deferred remainders:

- [ ] **CHECK: Brain export (`GET /user/export`) likely bundles the SimpleFIN bank access URL, bypassing its documented admin-only-reveal protection (found via code review, not verified against a live instance)** — `routers/export.py:24-30` zips the caller's *entire* `user_path(name)` folder, excluding only `push_subscription.json` by name. Per `docs/MEMORY.md`, the SimpleFIN read-only bank-access URL is stored at that same user's `Finance/simplefin.json` and is deliberately designed to be "never logged; output only by the admin reveal endpoint, 3/hour" — specifically so a compromised member session can't be used to exfiltrate a standing bank-read credential. The self-service Brain export endpoint (2/hour, no admin gate, callable by the member themselves) appears to include that exact file, which would let a member (or anyone holding their session) get the raw bank-access URL through a completely different, unthrottled-by-design path than the one the security model intends. Needs verification against a real SimpleFIN-connected account, then either exclude `Finance/*/simplefin.json` from the export zip (matching the `push_subscription.json` exclusion pattern already used) or confirm this is accepted/intentional
- [ ] **CHECK: GitHub flagged moderate Dependabot alerts on `master`** — no specifics available in-session (no Dependabot API access here); check the repo's Security → Dependabot tab for the affected packages and whether they're reachable at runtime or dev-only
- [ ] **CHECK: `get_workspace()` never verifies the requesting user is actually entitled to the workspace they claim via the `X-Workspace` header (found via code review, not verified against a live instance)** — `routers/auth.py:76-78`'s `get_workspace()` only checks the header value is literally `"personal"` or `"business"`, defaulting to `"personal"` otherwise; it never cross-checks against `user["workspaces"]` (the admin-controlled entitlement list). No per-request gating on it in `routers/tasks.py` either (spot-checked) — the *frontend* only shows the workspace toggle / sends the header when `user.workspaces.length > 1`, but nothing server-side stops a user whose `workspaces` is `["personal"]` from sending `X-Workspace: business` directly and reading/writing their own `Business/` subfolder (`ws_path()`) anyway, self-granting access to a workspace an admin never enabled for them. Bounded impact (each user's `ws_path()` stays scoped to their own directory either way — this is not a cross-user data leak), but it does bypass the `workspaces` field as an actual access control rather than a UI-only convenience, which is how it's documented (`docs/MEMORY.md` §Workspace Switching). Needs verification against a live instance, then either add the entitlement check to `get_workspace()`/`get_current_user()` or confirm the `workspaces` field is intentionally advisory-only and document it as such
- [ ] **CHECK: `write_json()`'s per-path lock only wraps the write step, not the full read-modify-write cycle — a real lost-update race (found via code review)** — `file_service.py`: `read_json()` takes no lock at all, and `task_service.py` has no locking whatsoever (unlike `auth_service.py`, which explicitly uses `_auth_lock` around its own read-modify-write operations — proof the team already knows this race exists and solved it there, just not everywhere else). Two concurrent requests touching the same user's `tasks.json` (two devices, or the nightly recurring-processor job running while a client is mid-edit) can silently lose one side's change: A reads v1 → B reads v1 (before A writes) → A writes v1+its-change (v2) → B writes v1+its-change (v3), discarding A's change. Applies to any per-user JSON store, not just Tasks. Fix: a shared read-modify-write helper that holds one lock across the full cycle, not just the write
- [ ] **CHECK: `routers/features.py`'s `delete_role` doesn't check who's using the role before deleting it — a silent privilege-escalation path (found via code review)** — per `docs/AGENTS.md`, `member` is "the internal fallback when a feature role goes missing," so deleting a restrictive custom role (e.g. a "cleaner" role with almost every module disabled) silently falls those users back to `member`, which is typically **more** permissive, not less. The admin gets no warning anyone is affected. Fix: warn (or block) deleting a feature role still assigned to users, showing who's affected
- [ ] **App-level 2FA (TOTP)** — the last open residual from the audit's outsider/account-takeover threat model, and a v1.0-trust-stack gate (line below). A stolen/guessed password is currently full access with no second factor. ## AI Agent Architecture — findings (2026-07-31 code review)

From a full walkthrough of the chat agent (`services/agent_service.py`, `services/ai_provider.py`, `routers/chat.py`, `pages/Chat.jsx`) for efficiency/effectiveness/accuracy/humaneness gaps. Not yet scoped or scheduled — triage into Now/Backlog as needed.

- [ ] **BUG: Approve-mode "Approve" click doesn't replay the reviewed action — the model re-derives it from scratch** — `ChatRequest.history` only carries `{role, content}` text (`routers/chat.py` `HistoryMessage`); `Chat.jsx`'s `toApiHistory()` strips `steps` before sending. `run_agent` (`agent_service.py:2290-2306`) breaks out of the loop on a pending write *before* appending the tool calls to `messages`, so the exact `pending_write` tool name + input shown in the `ApprovalCard` is never persisted anywhere. Clicking Approve just sends the literal text "Yes, go ahead." in `mode="auto"` (`Chat.jsx:429`) — the model has to re-decide what to do purely from its own prior turn's text (often just the generic "I need your approval..." fallback), with no guarantee it re-executes the same action the user actually reviewed. Fix: persist the pending tool_calls (keyed by run/step id) and replay them exactly on approval instead of re-prompting the model.
- [ ] **No prompt caching on the agent system prompt** — `ai_provider.py`'s `_anthropic`/`_anthropic_agent` never set `cache_control` on the system block, even though the same system prompt (Brain context: profile + memory + tasks + priorities + help index) is resent unchanged on every one of up to `MAX_STEPS=10` steps within a single run, and again on every new chat turn. Adding a cache breakpoint would cut cost/latency meaningfully for multi-step tool loops — cheap win, no behavior change.
- [ ] **Long chats hard-fail instead of degrading** — `Chat.jsx:261` sends the full in-memory message array uncapped; `ChatRequest.history` (`routers/chat.py`) has `max_length=50` and Pydantic rejects (422) once a session crosses it — no client-side trim, no server-side summarization. A long-running chat just breaks with a raw error instead of trimming/summarizing older turns (could reuse the existing `append_memory`/`rewrite_memory` tools for this).
- [ ] **No retry/backoff on transient AI provider errors** — `ai_provider.py`'s `_anthropic`/`_openai` call `client.messages.create`/`chat.completions.create` with no try/except; a single 429 or network blip anywhere in the loop kills the whole request (raw `Error: ...` shown in `Chat.jsx`), and nothing from that run is saved since `_save_run` only fires at the end. A one-off retry with backoff for rate-limit/5xx errors would meaningfully improve reliability.
- [ ] **No streaming of agent steps to the UI** — `run_agent` (`agent_service.py`) runs its entire loop (up to 10 LLM round-trips + tool calls) server-side before `routers/chat.py` returns one JSON blob; the UI shows a spinner with zero incremental feedback even though `steps` are generated one at a time. SSE streaming of steps as they happen would be a meaningful perceived-responsiveness win for multi-step tasks.
- [ ] **`search_brain` is substring matching, not semantic** (`agent_service.py:1548`) — plain `query.lower()` scan of markdown content; misses synonym/paraphrase queries ("exercise routine" won't match a note titled "workout plan"), which quietly degrades every downstream answer that depends on it. Feeds into the existing roadmapped **RAG over the Brain (v0.2)** item above rather than being a separate project — flagging so that item's scoping accounts for `search_brain` specifically, not just notes/journal.

Cross-reference: the per-user JSON write race (`task_service.py` has no read-modify-write lock, unlike `auth_service._auth_lock`) is already tracked above under Security follow-ups and under Idea Backlog P1 Technical/architecture — not repeated here.
